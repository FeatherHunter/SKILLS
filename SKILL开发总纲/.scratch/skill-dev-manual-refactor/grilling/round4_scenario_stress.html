场景 1 · §06 附录 D 与"无逃生口"的字面冲突

字面冲突 审查报告未碰 ADR-0002 vs §06 附录 D
ADR-0002 的裁决

"所有 Skill 无论规模,都必须 5 层 5 文件 + 全套自检,无逃生口。"

§06 附录 D 原文(06-附录.md:61-72)
| 类型 | 决策 | 理由 |
|---|---|---|
| 单条 CRUD(add / update / delete) | ❌ | 不需要 Skill 框架 |
| 高频但无视觉(快速回执) | ❌ | print 即可 |
| 后台管理(需权限 / 事务) | ❌ | HTML 不适合 |
| 数据采集(数据即产物) | ❌ | HTML 没价值 |
| 一次性脚本 | ❌ | 不值得维护 |
| 2 步以内的查询 | ❌ | 直接命令行更快 |

附录 D 列了 6 种"不该 Skill 化"的情形,理由包括"不需要 Skill 框架""print 即可""HTML 没价值"。

压测

ADR-0002 说"所有 Skill 都要 5 层 5 文件"。附录 D 说"单条 CRUD 不需要 Skill 框架"。这两个能同时为真吗?

我在 ADR-0002 里已经处理了这个冲突,逻辑是:附录 D 不是在说"小 Skill 可简化",而是在说"有些东西根本不该叫 Skill"。两命题不冲突——删伸缩表后,80 行的"记喝水"要么写 5 层 5 文件,要么别 Skill 化(走附录 D)。

但 A 坐标(字面自洽)下,这个逻辑必须写进总纲,不能只存在 ADR 里。否则读者读 §02 看到"所有 Skill 必须 5 层",再读 §06 附录 D 看到"单条 CRUD 不需要 Skill 框架",会困惑"到底要不要 5 层"。

决策点 4 · 附录 D 的处理

ADR-0002 已处理逻辑冲突,但总纲正文必须同步。3 种处理:

ζ · 附录 D 保留 + §02 删表处加引用

§02 删规模伸缩表的位置加一句:"若某功能连 5 层 5 文件都撑不起,它就不该 Skill 化,参见 §06 附录 D"。附录 D 原文不动。我推荐——单一事实源(门槛在 §02,判定在 §06)。

η · 附录 D 重写理由列

附录 D 的理由列从"不需要 Skill 框架"改为"撑不起 5 层 5 文件,参见 §02"。理由列字面对齐 ADR-0002。

θ · 删除附录 D

附录 D 整节删除。理由:ADR-0002 说"所有 Skill 都要 5 层",附录 D 列"不该 Skill 化"的情形= 多余。但后果:用户遇到 80 行小工具,没有"别 Skill 化"的指引,可能硬上 5 层 5 文件。

场景 2 · "不该 Skill 化"的判定权归谁

判定权归属 审查报告未碰 附录 D 的 6 种情形,谁来判定?

场景 1 锁定后(假设选 ζ),附录 D 保留。但冒出更深问题:附录 D 列了 6 种"不该 Skill 化"的情形,但谁来判定一个具体功能属于这 6 种?

压测

用户对 AI 说:"帮我写个记喝水的 Skill。" AI 该怎么反应?

路径AI 行为问题
A · AI 自己判AI 看"记喝水"= 单条 CRUD,按附录 D 说"不该 Skill 化",回用户"建议写普通脚本"AI 凭什么替用户决定?用户可能就是要 Skill 化(为了统一管理 / 触发词 / HELP)
B · 用户说才算AI 默认所有请求都 Skill 化,除非用户显式说"写个脚本就行"那附录 D 的 6 种情形给谁看?如果只是给用户看,用户得先读到 §06 附录 D 才知道
C · 走 §06 三维度评估AI 先跑附录 A(3 维度评估:复用频率 / 视觉密度 / 改造阻力),S/A/B/不做但附录 A 的"不做"档是"低频+低密度+高阻力",和附录 D 的"单条 CRUD"不是一回事

这里暴露了 §06 附录 A 和附录 D 的判定逻辑重叠但不一致:

  • 附录 A(3 维度评估)的"不做"= 低频+低密度+高阻力
  • 附录 D 的"❌"= 单条 CRUD / 高频无视觉 / 后台管理 / 数据采集 / 一次性 / 2 步内

一个高频但无视觉的"记喝水"(高频 + 低密度),按附录 A 是"A 档"(2-4 周动手),按附录 D 是"❌ 不需要 Skill 框架"。两个附录给出冲突结论。

决策点 5 · 附录 A 与附录 D 的冲突

这是审查报告完全没发现的深层矛盾。A 坐标下必须处理。3 种方向:

ι · 合并为单一判定流程

删除附录 D,把它 6 种情形合并进附录 A 的"不做"档。附录 A 成为"是否 Skill 化"的唯一权威判定。单一事实源。

κ · 明确分工:附录 A 管改造,附录 D 管新建

附录 A(3 维度)只用于"已有 Skill 是否值得改造";附录 D 用于"新需求是否该 Skill 化"。两者管不同阶段,不冲突。在两个附录标题里显式标注分工。

λ · 附录 D 改为"附录 A 的前置过滤"

附录 D 列的 6 种情形 = "连附录 A 都不用跑,直接否决"。附录 A 只对"通过附录 D 初筛"的需求跑。逻辑顺序:D 初筛 → A 评估 → S/A/B/不做。

场景 3 · HELP 场景资产对微型 Skill 的成本

成本不对称 ADR-0002 的隐藏代价 §07 HELP 契约 + 删伸缩表 = 强制重型流程

压测

ADR-0002 锁定后,所有 Skill 都要 5 层 5 文件。但 §07 的 HELP 契约要求每个业务唤醒词穷举全部合法场景 + 7 字段场景资产 + HELP HTML。我把"记喝水"这种 2 唤醒词的小东西,按 §07 跑一遍:

记喝水的合法场景:
- 记喝水(单条记录)
- 查今天喝水(当日列表)
- 查今天喝多少(总量)
- 查喝水历史(多天趋势)
- 导出饮水记录(导出)

5 个场景 × 7 字段 = 35 个字段值要填
+ HELP HTML(场景资产 + 模板 + 渲染器 + 测试)
+ FAT 9 步(2 核心词 × 3 人类 prompt = 6 次测试)

结果:一个 2 唤醒词 / 80 行功能的小 Skill,HELP 合规成本 = 35 字段 + HELP HTML + FAT。这是ADR-0002 的真实代价——你接受了"所有 Skill 都要 5 层",但 §07 的 HELP 契约没有跟着伸缩(因为伸缩表删了)。

这里有个真正的设计选择(不是 bug):

决策点 6 · HELP 契约是否对所有 Skill 一视同仁

ADR-0002 删了伸缩表,§07 HELP 契约没有伸缩机制。3 种方向:

μ · HELP 对所有 Skill 一视同仁(字面 A)

2 唤醒词的小 Skill 也必须穷举全部场景 + HELP HTML + FAT。接受成本。作者已在 ADR-0002 接受"合规是功能 4 倍"的代价,这里延续。我推荐——A 坐标下最自洽,无逃生口。

ν · HELP 契约加"最小可行"档

§07 加一节"最小可行 HELP":唤醒词 ≤ 3 个的 Skill,场景资产可用简化格式(但不准删字段)。这与 ADR-0002 矛盾(伸缩表都删了,这里又伸缩)。不推荐——破坏 A 坐标自洽。

ξ · §07 不动,但在 §06 附录 D 加"HELP 豁免"档

附录 D 加一行:"唤醒词 ≤ 3 且无 HTML 视觉密度 → 可不建 HELP HTML,只登记 HELP 唤醒词"。但这又开了逃生口,与 ADR-0002 哲学冲突。
