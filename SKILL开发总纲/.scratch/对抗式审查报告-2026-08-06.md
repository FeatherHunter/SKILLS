# 对抗式审查报告 · SKILL 开发总纲 V1.0(第一性原理视角)

> 日期:2026-08-06
> 方法:通读全部 8 章 + SKILL.md + README + CONTEXT.md + 2 份 ADR + docs/agents ×3 + `_assets/injector.py` + 自检脚本 `verify.ps1` + 仓库 git 历史;机器核验计数 / 死链 / 镜像同步 / commit 纪律
> 坐标系:采用总纲自己声明的 **A 坐标(内部 100% 自洽,ADR-0001)**,外加一个总纲没有的坐标——**与生态现实的对应性**(总纲管的是真实运行的 50+ 技能)。

## 0 · 摘要(先给结论)

总纲在**理念层**是出色的:单工铁律(原则 10)与 FAT 协议(§05)是真正从第一性推导出来的产物,经得起对抗。

但在**执行层**,总纲正在用自己宣布的最高标准反噬自己。机器核验发现 9 处自洽性违规(其中 3 处与 ADR-0001 点名批评旧版的违规**同型**——即"总纲自己违反自己的钩子"),以及 5 处与生态现实的脱节(旗舰技能的实践已经绕开或背离总纲条款)。

最深的两个结构性结论:

1. **质量体系测的是"AI 能不能执行",不是"用户有没有得到价值"**。FAT、自检清单、Tested-By 全部指向"文档契约可执行性"这个代理指标,整个系统没有任何用户结果回路。
2. **总纲的合规审计是"自报",不是"他查"**。FAT 验证"agent 是否遵循 SKILL.md",不验证"SKILL 是否遵循总纲"。后者的唯一机制是 5 层自检清单(勾选框)。这解释了为什么生态里到处是总纲条款的影子违规——没有任何东西会抓住它们。

## 1 · 第一性审查:目标函数错位

### 1.1 质量体系全部指向代理指标,没有用户价值维度

第一性提问:总纲存在的目的是什么?按它自己的话说——"让 AI 产出的 Skill 稳定、可发现、可验证"。但通读全文,**没有任何一条规则度量"用户从 Skill 中得到了什么"**:

- FAT(§05)测的是"零上下文 agent 能否按 SKILL.md 字面执行"——是**可执行性**,不是**有用性**。
- 5 层自检清单(§02)全是内部属性(有索引吗 / 有事务吗 / 有回执吗)。
- 07 场景完备性测的是"五者一一对应",对应上了也不等于用户问题被解决。
- 06 附录 A 的 S/A/B 优先级,输入只有"复用频率 / 视觉密度 / 改造阻力"——**没有"用户痛点强度"或"使用反馈"**。

推论:FAT 全绿 + 5 层全勾 = 一个"AI 能照着走、但用户根本不需要"的 Skill 也能满分通过。总纲优化了一个可以脱离真实目标无限自洽的代理指标。**A 坐标(内部自洽)被 ADR-0001 定为最高原则时,等于宣布"文档正确"优先于"用户正确"。**

### 1.2 架构快照被写成永恒定律

原则 10 的推导(04 line 173-192)是全文最诚实的一段——它明说:

```
③ 当前架构 = 没有服务端中转 + 只有 IDE 进程内 agent
```

**单工铁律是这个架构快照的推论,不是不变量。** 一旦出现本地服务端中转(例如 opencode 插件体系、MCP server、本地 daemon),"HTML 与 LLM 之间没有通路"的前提失效,复制按钮闭环就退化为低效路径。总纲没有为这类规则标记"架构依赖期"或"复审触发器"——它把 2026 年 7 月的架构约束写成了永久第一性。

同样的问题在 03 触发词 v2:它建立在"路由靠 AI 理解 SKILL.md"之上;而实际 opencode 路由靠 **description 字面匹配**(见 §4.1)。

### 1.3 失效模型把全部风险堆在系统里最不可控的组件上

05 已知边界明说:不做 CI、不做 merge 防护、不做 SDK 防护,"依赖 SKILL.md 硬规则 + AI 自约束"。第一性看:

- 硬规则(validators.py)只在 **CLI/DB 层**生效——保护的是数据,不是 AI 行为。
- AI 行为(选对唤醒词、不降级文字答、执行【待开发】铁律)只有软规则约束。
- 运行时**没有任何审计机制**检测 AI 是否违规(无日志对账、无行为回放;08 的"复制日志"是给用户排障的,不是给系统审计的)。

即:整个系统最重要的执行者(LLM)恰好是唯一没有强制约束、没有运行时监督的组件。FAT 只是 commit 前的抽查,不是运行时的保障。这个缺口是设计使然(已知边界),但从第一性看,它意味着"商用级关卡"(FAT 自称)实际闸住的是文档,放行的是行为。

### 2.6 ⚠ 原则 9"命名不带版本"被自己的文件名违反

04 原则 9 明文:"命名不带版本…版本号暗示'多个并存版本'"。总纲自己的文件:`03-触发词设计v2.md`、`04-可视化与注入v2.md`、`08-HTML交互规范v1.md`。

如果说"这是文档不是模板文件",那原则 9 就没有被定义为"适用于所有文件"——但按 A 坐标,规则没写例外 = 没有例外;按 B 坐标,读者会困惑"为什么总纲自己可以 v2 而我不行"。两坐标下都是不自洽。

### 2.7 ⚠ 07 契约对总纲自身:零自履行(隐形自我豁免)

07 核心规则 1/5/9:每个 Skill 必须登记 ≥ 1 个 HELP 唤醒词 + 场景资产 + HELP HTML。总纲自己的 SKILL.md 没有 HELP 唤醒词,没有 `references/scenarios.*`,没有 HELP HTML。

如果总纲自认是"元技能"可豁免,07 没有为这种豁免写任何条款——而 ADR-0001/0002 的精神恰恰是**消灭隐形逃生口**。总纲对自己开了 A 坐标明令禁止的那个口子。

## 3 · 与生态现实的失联(元层审查)

### 3.1 03 的核心教条被旗舰技能系统性违反

03 line 93:"**SKILL.md 只标方向,不写具体 prompt。避免硬编码语料(用户表达会变,硬编码易过期)。**"

现实:本仓库旗舰技能(卡路里、居家管家)的 SKILL.md frontmatter description 是**数百条字面触发词**的穷举列表(卡路里 description 约 500+ 条,含"看今日主页(主页 / 今天主页 / 今日概况)"这类字面变体)。

原因不难找:opencode 的路由是 **description 字面匹配**——不写具体话,AI 就匹配不到。03 的抽象教条与运行时环境的物理约束矛盾。总纲没有解释这个矛盾,导致:所有技能用脚投票(全字面),03 变成一纸空文,而 FAT(它验证"SKILL.md 能被执行")永远发现不了这种背离。

### 3.2 Tested-By 协议名存实亡

- 05 line 155-156 允许值:`fresh-agent-v1`(带唤醒词+人类 prompt+结果)或 `exempt` + 豁免依据。
- 实际 commit 历史:`Tested-By: pytest-pass-2026-08-06(居家管家 381 项)`、`Tested-By: no-verify + 原因:纯文档改动`——**"pytest-pass"和"no-verify"都不是 05 定义的合法值**。
- 根 AGENTS.md line 31 已改为:`Tested-By: exempt(无 fresh agent · 详见 ADR-0005)`——即仓库已把"无 fresh agent"变成默认豁免,而 05 的豁免矩阵没有"无 fresh agent"这一档。
- 后果:总纲的 FAT 契约在现实中已被系统性改写,但**总纲自己不知道**——05 至今没有同步这个变化。

### 3.3 ADR-0005 跨技能重号,根级引用无法解析

根 AGENTS.md 的 "详见 ADR-0005" 同时可能指:
- `备忘录/docs/adr/0005-d-exemptions-and-rituals.md`(豁免与仪式矩阵)
- `作息管家/docs/adr/0005-replay-start-end-new-workflow.md`(复盘工作流)

**两个技能各有自己的 ADR-0005,内容完全不同**。根级 AGENTS.md 用"ADR-0005"裸引用,没有路径——按 A 坐标,这是不可解析的引用;按实践,每份 commit 的 "exempt(详见 ADR-0005)" 到底引的是哪份,无人能验。ADR 编号体系没有跨技能命名空间,这是总纲文档层契约没覆盖的领域(总纲要求 Skill 有版本号/changelog,却没定义跨 Skill 的 ADR 命名空间)。

### 3.4 FAT 验证不了"符合总纲"——合规审计的真空

FAT 的 9 步协议,测的是"fresh agent 能否按 SKILL.md 走通"。**SKILL.md 如果本身就违反总纲,FAT 一样全绿。** 例证:

- 作息管家 SKILL.md 的 HELP 输出路径:`$SKILLS_DB_PATH/schedule_html/help/作息管家_HELP_*.html`,与原则 12.B 的规范形态(`$SKILLS_DATA_DIR/<skill>_html/<中文名>_HELP_<ts>.html`)不一致(多了 `help/` 段;env 本身按 12.X 优先级链勉强合规)。
- 05 FAT 豁免矩阵写明"涉及 SKILL.md 任何字符 → 永不豁免";3.2 的现实证明这条被普遍绕开。

结论:**总纲对下游的唯一强制力是自报**(5 层自检清单勾选 + Tested-By 字段),没有任何他查机制。verify.ps1 只校验总纲自己,不校验生态。一个 50+ 技能的体系,合规审计为零。

### 3.5 总纲没有"总纲修订协议"(meta-amendment)

06 的演化规则(RULE Forms / 4 Phase)全部指向 **Skill 改造**,没有一条指向"总纲自身如何演进"。当生态实践与总纲分叉时(3.1/3.2),既无"必须回写总纲"的义务,也无"总纲条款过期"的机制。总纲已经在事实上落后于生态(Tested-By、字面语料),但没有任何流程让它追上。它的自我更新靠的是**下一次有人做对抗式审查**——不可持续。

配套证据:commit `c345abd`("HTML 交付文字纪律:…用户拍板")与 `d489357`(同规则回滚,"未经拍板的规则不得写入")——总纲在 48 小时内吸入了又吐出了一条未拍板规则,证明它的变更闸门是口头的,不是流程的。

### 3.6 规模成本无上限,存量合规无时间表

ADR-0002 取消了所有规模逃生口(80 行工具 = 5 文件 + 20 项自检 + FAT + HELP 场景资产,作者确认接受)。叠加:
- 03:唤醒词无上限;
- 07:场景穷举、数量无上限、**全部**场景必须进 HELP HTML;

而 06 附录 A 的 S/A/B 只排"HTML 改造"的优先级,**不解决存量技能的合规序列化**。现实:仓库 50+ 目录里,真正全量合规(场景资产 + HELP HTML + FAT 纪律)的只有极少数;卡路里一个技能就有数百唤醒词,穷举场景 × 7 字段 × HELP HTML = 维护成本随技能表面超线性增长。总纲的合规模型是"单技能全有或全无",没有"渐进合规"状态——这与其生态的实际演进方式(渐进)冲突。

## 4 · 第一性追问:哪些数没推导过?

按"第一性原理"招牌自检,全文真正从 Layer-0 事实推导出来的只有两处:原则 10(单工铁律)和 FAT 协议。其余关键常数**全是规定,不是推导**:

| 常数 | 出处 | 论证强度 |
|---|---|---|
| 唤醒词下限 8 个 | 03 | "8 是质量底线"——为什么不是 5 或 12?无推导 |
| 变体 2-3 个 / 3 方向 | 03 | "少于 3 方向不鲁棒、多于 3 方向同义反复"——经验断言,无数据 |
| 5 状态 / 4 段式 | 04 | 从失败模式可推导 ✓ |
| 7 字段最小集 | 07 | 从"用户可执行"可推导 ✓ |
| 13 原则 / 7 钩子 | 04 / SKILL.md | 计数,非推导 |
| "≥ 5 个含多字段+视觉密度才做 HTML" | 04 原则 0 | 阈值来源不明 |
| **"是否该 Skill 化"** | ADR-0002 | **总纲明说不碰(决策点 7:ρ+ω)** |

最后一行是最锋利的:整个体系最大的杠杆——"这需求该建 5 层 5 文件的 Skill,还是写个脚本?"——是**总纲唯一拒绝回答的问题**,而实际决策者往往是 AI(用户说"记个喝水",AI 判断走哪个技能)。总纲对系统最重要的分岔口保持沉默,却对文件名、时间戳格式、`_N` 后缀这些细节立法。**优先级倒挂。**

## 5 · 经得起对抗的部分(平衡声明)

不全是坏消息。以下设计经受住了本轮对抗,建议保持:

1. **原则 10 的推导结构**(04 line 173-192):Layer-0 事实 → 推导链 → 设计约束,这是全文唯一完整的真第一性推导,值得作为其他章节的范式。
2. **FAT 的"改文档不改代码"纪律 + 循环上限**:在"文档即契约"的世界里,这条归因规则是自洽且可执行的。
3. **相对时间换算的边界 case 表**(跨月/跨年/闰年/12 月):具体、可测试、可复用。
4. **08 的预告-等待-接收模式与图片接收契约**:解决了"这张图是干嘛的"这个真实歧义,是 08 里最有价值的新增。
5. **场景 7 字段最小集与【待开发】二态**:把"没做完"变成一等公民,防止 AI 假装执行——这是防欺骗的好设计。

## 6 · 建议(按优先级)

### P0 · 机器可验证的修复(1-commit 级,先还清自己的债)

1. HTML 镜像同步 08 整章(钩子 1 补课)。

### P1 · 自洽与治理

6. 单一化"最高优先级":原则 1 改为"前置条件(Precondition)",原则 10 独占"最高优先级"。
7. 给总纲自己补 HELP 契约(或写 ADR 显式豁免——不能沉默)。

### P2 · 结构性

10. 引入"合规审计"替代"自报":把 verify.ps1 扩展为对全部技能的 conformance 检查(场景资产存在性、7 字段 schema、12.B 命名、HELP HTML 生成源),至少每月一跑。FAT 管"能执行",conformance 管"符合总纲"——两者缺一不可(这正是 06 附录 F 对单测/FAT 说的话,应同样适用于 FAT/conformance)。
11. 给 FAT/Tested-By 补"现实档":要么接受 pytest-pass / no-verify / exempt(无 fresh agent)为合法值并写明判据,要么强制回改——现状(总纲一套、实践一套)是零约束。
12. 给"是否该 Skill 化"补显式判据(哪怕只是"≥3 个用户场景 + 数据持久化"这类粗判),或把判定权显式交给某个角色——不能既声称"必读"又不给入口。
13. 为架构依赖型规则(单工铁律、触发词 v2)加"复审触发器":架构变化(出现服务端中转)时,这些条款自动进入复审队列。

## 7 · 结论

总纲 V1.0 的**方向**是对的:在"LLM 无服务端、无 CI、无 SDK 防护"的现实里,它把工程质量寄托在"文档契约 + 仪式 + 自报"上,这是当时条件下的合理选择。但 V1.0 目前的状态是:

- **对自己**:9 处 A 坐标违规(含钩子 1 复发),与 ADR-0001 批判旧版的症状同型——"地基"问题在 V1.0 里换了个姿势回来了;
- **对生态**:3 条核心教条(方向制语料、Tested-By 格式、FAT 豁免矩阵)已被生态实践改写,总纲未同步,权威性正在折旧;
- **对用户**:整个质量体系不度量用户价值,理论上可以无限自洽地偏离真实目标。

一句话:**V1.0 的失败模式不是"规则不够多",而是"规则没有执行回路"——它给了自己最高标准,却没有给自己和生态任何机器可验的守门人。** 建议以本报告 P0/P1 为下一轮重构的 issue 素材,先还清自洽债,再谈规则增补。
