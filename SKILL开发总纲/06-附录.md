# 06 · 附录 · 演化规则(RULE Forms)

> 本附录是<strong>从历史案例中抽出的 RULE 形式</strong>,非硬编码案例。所有 skill 可复用。
> <b>不含具体 skill 名 / 具体 BUG 列表</b>(尊重"不喜欢硬编码案例"原则)。

## 附录 A · Skill 改造优先级判据(3 维度评估)

任何 skill 改造前先打分,再决定 S/A/B。

| 维度 | 权重 | 评分标准 |
|---|---|---|
| **复用频率** | ⭐⭐⭐⭐⭐ | 用户每周 / 每天调用次数 |
| **视觉密度** | ⭐⭐⭐⭐ | 多字段 + 多条目 + 需要扫读 |
| **改造阻力** | ⭐⭐⭐ | CLI 现状是否容易支持 JSON 化 |

### 判定矩阵

| 维度组合 | 优先级 | 含义 |
|---|---|---|
| 高频 + 高密度 + 低阻力 | **S**(1-2 周动手) | 立即做 |
| 高频 + 低密度 | **A**(2-4 周动手) | 排第二批 |
| 高密度 + 低频 | **B**(按需) | 第三批 |

→ 任何 skill 改造前**先做这 3 维度评估**,再开 Phase。**跳过这步直接动手** = 浪费时间。

## 附录 B · Skill 改造 4 Phase 模式

任何 skill 改造按"**先低阻力后高阻力**"顺序分 4 个 Phase。每个 Phase 一个 commit + `[技能名]` 前缀,失败可独立 `git revert`。

| Phase | 适合场景 | 动作 | 输出 |
|---|---|---|---|
| **A · 最小阻力先做** | CLI 已合规(返回结构化 JSON) | 补字段 → 写 1 个简单模板 → 渲染器 → commit | 1 commit,1 模板 |
| **B · 数据已合规** | 数据完整,但缺可视化层 | 选模板模式 → 复用 `_assets/template_skeleton.html` → 渲染器 → commit | 1 commit,1 模板 |
| **C · 规范化已有 HTML** | 有 HTML 但不符合规范 | 拆分为模板 + 注入模式 → 数据契约 `{status, data, message}` → commit | 1 commit,文件拆分 |
| **D · CLI 重构 + 解锁阻塞** | 多个 P0 阻塞于 CLI 不返回 JSON | 加 `as_dict=True` 参数(**保持默认 print 行为**)→ 多模板 → commit | 1 commit,N 模板 |

### 为什么按这个顺序

- A 阻力最小,先吃**便宜柿子**积累信心
- B 数据已有,只缺可视化,投入小收益大
- C 是"已有但不规范",改造而非新增
- D 阻力最大,放最后 — 因为它会**影响前面所有 Phase 的成果**

→ **违反顺序的代价**:D 提前做 → 之前写的模板全部失效 → 返工。

## 附录 E · BUG 修复优先级判据

发现 BUG 时,按**严重度**修复,而不是按发现顺序:

| 严重度 | 含义 | 反应时间 |
|---|---|---|
| 🔴 **致命** | 主流程阻塞 / 数据丢失 / 安全 | 立即 |
| 🟡 **中等** | 功能部分损坏 / 体验降级 | 当前 Phase |
| 🟢 **低** | 边角 / 文案 / 美化 | 下个 Phase |

→ 🔴 不修不 commit;🟡 跟着主功能走;🟢 攒一批再修。

## 附录 F · Fresh Agent 黑盒测试(FAT 协议)

> FAT 协议的完整定义(第一性原理推导、9 步协议、循环上限、常见 fail mode、与现有钩子关系、豁免规则)见 [05 §Fresh Agent 黑盒测试协议](./05-工程仪式.md)。本附录只保留 §06 独有的对比内容。

### 为什么传统测试不够

| 维度 | 单元测试 | Fresh Agent 测试 |
|---|---|---|
| 测试对象 | 函数 / 模块 | 完整 SKILL 跨角色可执行性 |
| 谁跑 | 自动化脚本 | 空白上下文 AI agent |
| 测什么 | 代码逻辑 | 文档契约是否自洽 |
| 失败修什么 | 代码 bug | SKILL.md 文档 gap |

→ 单元测试 = 代码质量,Fresh Agent 测试 = 文档 + 契约质量。**两者不可替代**。

### 与单元测试的协同

```
改完代码
  ↓
跑单元测试(代码逻辑 OK?)
  ├─ ❌ fail → 修代码
  └─ ✅ pass
      ↓
跑 Fresh Agent 测试(契约自洽?)
  ├─ ❌ fail → 改 SKILL.md(不是改代码)
  └─ ✅ pass → commit
```

→ 两个测试**串联**,缺一不可。

## 附录 G · 跨技能 ADR 命名空间规则(2026-08-09 增)

> 背景:ADR-0005 在生态出现 4 份重号(备忘录/作息管家/卡路里/智剪工坊),根级裸引用「ADR-0005」不可解析。

- **引用必须带路径**:任何「详见 ADR-XXXX」必须写 `<技能目录>/docs/adr/000X-<标题>.md` 完整路径
- **裸引用非法**:不带路径的「ADR-0005」按 A 坐标 = 不可解析引用
- **编号仅技能内唯一**:跨技能无全局 ADR 编号;同名编号(0005)在不同技能各自独立
- 执行:根 AGENTS.md 等仓库级引用逐条改带路径;新增引用一律带路径

## 附录 H · conformance 合规审计(2026-08-09 增 · wayfinder 范本)

> 背景:FAT 测「能执行」,不测「符合总纲」——生态合规长期靠自报,无他查机制。

- **FAT 与 conformance 分工**:FAT 管「SKILL.md 能否被 fresh agent 执行」;conformance 管「SKILL.md 是否符合总纲契约」
- **conformance 检查项**(机器可验):场景资产存在性(scenarios.yaml)、7 字段 schema、12.2/12.3 输出路径命名、HELP HTML 生成源、Tested-By 合法值
- **执行**:verify.ps1 扩展为对全部技能的 conformance 检查;仓库级定期运行(可并入现有仪式,频率实施 effort 定)
- **渐进合规**:承认技能渐进演进,不做「全有或全无」;合规分级(完整/部分/未合规)用于优先级,不用于追责

## 附录 I · 总纲自我修订协议(meta-amendment,2026-08-09 增 · wayfinder 范本)

> 背景:总纲自己也会过期(Tested-By 现实、字面语料现实均已证明);过去靠不定期对抗式审查,变更闸门是口头/临时决策。

- **回写义务**:Skill 级 ADR 或生态实践与总纲条款冲突时,必须回写总纲对应章节,否则视为分叉
- **变更闸门**:总纲条款变更必须经 grilling 决议 + 记录在案(GitHub issue 决议评论 + map Decisions-so-far),禁止口头吸入/吐出
- **自我观测**:总纲自身的 SKILL.md / 文件同样履行自己的契约(它是自己的第一个遵守者,豁免必须显式成文)
- **定期复核**:以本次对抗式审查为范式,纳入 conformance 机制定期触发
