# 09 · SKILL 重构/优化指导(跨技能主文档 · 2026-08-06)

> **适用**:任何 AGENT 接到「重构 / 优化某个 SKILL」任务时的必读主文档。

> **配套**:所有可复制模板块见 [`09.1-重构优化可复制模板集.md`](./09.1-重构优化可复制模板集.md);本次任务的启动 prompt 见 §13。

## 0. 文档使用方式(先读)

1. 本文档为**主动注入层**:根 `AGENTS.md` 已索引,启动 prompt(§13)也会引用;sub-agent 不保证自动加载时,由主 session 明确告知路径。
2. 阅读顺序:先读本文件全部 → 用到哪个模板块再读 09.1 → 需要细节时按 §1.4 分层引用原始资产。
3. 一句话定位:把卡路里 + 居家管家的踩坑经验,变成一套「**结构上防失效**」的可执行流程,而不是一份建议清单。

## 1. 第一性原则(总纲)

1. **决策与执行分离**:规格阶段只产决策(map 关闭即定案),实施阶段只执行(禁止新增功能,只修规格内缺陷)。
2. **预防层级**(所有要求按此排序设计):
   ```
   结构隔离(不可能冲突) > 门禁强制(不过不交付) > 纪律(靠人遵守) > 人工兜底(用户发现)
   ```
   每条要求必须回答:「Agent 不执行,结构上会不会被发现?」答不出 = 这条要求无效,改形式或删掉。
3. **可复制式优先**:一切要求写成原文模板块(09.1),session 复制粘贴而非转述——消灭转述损耗,输出天然一致。
4. **经验仲裁规则**:卡路里经验已陈旧(测试直连生产库、数据随功能改、4 轮迁移),居家管家实战更完善(fixture 隔离、D1 数据层后置、两阶段 map)。**冲突时以居家管家为准**;引用卡路里经验必须标注「历史教训」。
5. **证据链思维**:任何结论必须能指到证据(issue 评论 / commit / 测试输出 / 截图),没有证据的 PASS 视为 FAIL。

## 2. 规模分级(动手前必做,输出给人类确认)

| 级别 | 特征 | 流程 |
|---|---|---|
| **S** | 单 session 可完成(≤ ~30 场景、无数据层变更、决策已定、无存量兼容问题) | 单票直做 + 轻量门禁(仅 §6 双门禁 + §7 偏离记录) |
| **M** | 多 session、决策未定、存在存量兼容 | wayfinder 两阶段(规格 map → 实施 map) |
| **L** | 多域并行 + 数据层变更 + 开源准备 | 完整两阶段 + 隔离契约 + 并发约定 + D1 数据层后置 + G6 审查配对 |

- **自评模板**:见 09.1 T-H。
- 自评结论 + 理由 + 建议流程,必须呈报人类确认后再动手。规模判断错误 = 前期最大浪费来源。

## 3. 重构 vs 新建:两条路径

**新建**:无存量,直接按规格流程走,不设迁移章节。

**重构**(本次任务主体):动手前先做**存量盘点**,逐项定处置,写入 map Notes:

| 存量项 | 处置方式(居家管家实证) |
|---|---|
| 旧 HTML 模板(无复制按钮/旧交互) | 按 08-HTML交互规范 + 门禁 B 改造或废弃 |
| 旧唤醒词 / 旧 prompt | 场景权威清单重定,旧口径退役**单独 ISSUE** |
| 硬编码 id / 旧分类体系 | 种子化方案(seed_key + resolve),单独设计文档 |
| 测试直连生产库 | fixture 隔离(独立临时库),**立项即做**,否则并发全量 pytest 闪断 |
| 存量数据兼容 | 迁移规则随「字段增改」场景讨论,不设独立迁移章节 |
| PII / 个人数据(开源准备) | 单独 ISSUE,最后批次处理(filter-repo 等) |
| 共享文件(路由表 / scenarios.yaml / 主 SKILL.md) | 路由表一次性连续编号;yaml 只经合并器写入;SKILL.md 改动必 fresh-agent(FAT) |

**存量处置硬规则**:数据层变更 = 最后处理 + 每项单开 ISSUE(总账模式,参考 D1 #103);实施期用域内自持幂等 DDL(ensure_schema)过渡,物理建表收编到最后批次。

## 4. 工作流总览

```
1 上下文加载(§13 启动 prompt 第 1 步)→ 2 规模自评(§2,人类确认)
→ 3 规格阶段(M/L 级):R 研究票 → G grilling 定规则 → 分域 sub-map 枚举场景
→ 4 实施阶段(M/L 级):T 票按域拆,隔离契约执行
→ 5 闭环双门禁(§6,不过不关票)
→ 6 审查配对票(ready-for-human,含双端视口)
→ 7 过程复盘(§9,人类先不看成品)
→ 8 人类理解对齐(§10,考题循环,对齐 = 任务结束条件)
→ 9 交付(§11 清单)
```

每步产物与证据:规格 = 场景权威清单 + 决策评论;实施 = 代码 + fixture 测试 + 决议评论 + Tested-By;审查 = 截图 + 5 问结论。

## 5. 军规(不可违背;违反 = 立即纠正并记录偏离)

1. **两阶段分离**:规格只产决策,实施只执行;实施期禁止新增功能,只修规格内缺陷。
2. **先 R 后 G**:开图前先 fire 研究票(现状盘点/竞品/机制),决策基于证据。
3. **隔离契约**:每域只动自己的文件集 `scripts/{域}/ + templates/{域}/ + render_{域} + scenes/{域}.yaml + tests/test_{域}.py`(⚠️ 场景清单文件用 `scenes/{域}.yaml`,域 = 中文域名,如 `scenes/物品.yaml`;不用编号命名);公共层变更 = 单独 ISSUE + review。
4. **数据层后置**:改字段/表 = 最后处理 + 每项单开 ISSUE;实施期域内自持幂等 DDL 过渡。
5. **Git 红线**:只允许 `git add` / `git commit`;**禁止** push(用户统一 push)/ rebase / reset / clean / checkout / stash / filter-* / amend / **add -A**;不确定的操作不做、问用户。
6. **提交优先**:代码写好就 commit(允许 `--no-verify`,但 Tested-By 必须如实标注 `pytest-pass-日期` 或 `no-verify + 原因`);第一原则 = 各 session 的代码不丢,高于一切纪律。
7. **commit 自检**:commit 后立即 `git status` + `git log -1 --stat` 验证,失败(含 hook 拦截)显式处理,不静默继续(命令见 09.1 T-G)。
8. **本地镜像 = 真相源**:map 本地镜像 md 与 GitHub 正文同步维护;正文被并发清空时以镜像为准(已发生事故)。
9. **顺序规则是软约束**:blocking wire 在创建票时自动生成,早于手动约定——依赖关系以「域自包含 + 后接线」为硬保障(独立 CLI 入口/自持 DDL/合并器后接入);不因某票声称阻塞就停等,先确认依赖是否真硬。
10. **共享组件归属制**:公共组件由首个使用域创建并冻结接口,演进走公共层 ISSUE。
11. **测试 fixture 隔离**:禁止直连生产库;每域 e2e 尽量含浏览器 DOM 渲染断言(单测断言 payload 文本测不到 JS 渲染层——已发生事故 #127)。
12. **对抗式审查内建**:每结论先列反驳,必要时派独立 subagent 证伪;区分「实现 / 交付 / 发布」三档完成度口径。
13. **闭环双门禁**(§6):每实施票关闭前 + 每 HTML 呈交前强制,不过不关票、不交付。
14. **偏离必记录**(§7):每票闭环评论必附偏离记录三问,无则视为未闭环。

## 6. 双门禁(闭环 / 呈交前置)

**门禁 A · 垂直 5 层对账**(每实施票关闭前,逐层输出 PASS/FAIL 证据):

> 针对本次开发的所有场景,从垂直层面,从第一性原理出发,对抗式审查:
> 1、最上层 调用 HELP 命令,拿到的 HELP HTML 中是否有你开发的所有场景,点击复制指令 后是否可以拿到商定好的 prompt
> 2、SKILL.md 根据 prompt 能否锁定到相应的唤醒词
> 3、唤醒词触发后的 SKILL 流程是否清晰
> 4、SKILL 流程底层是否能找到符合功能要求的 CLI
> 5、调用 CLI 后是否最终拿到了符合该场景功能要求的、与「呈现数据」一致的 HTML 文件

**门禁 B · HTML 第一性 5 问**(每个 HTML 呈交人类前,审查结论随交付一起给):

> 从第一性原理出发,对抗式审查:
> 1、复制数据和复制日志按钮是否符合要求
> 2、整个 HTML 呈现的数据是否符合设计时的场景要求和呈现数据的要求
> 3、HTML 中各个组件和内容有没有做好手机版适配,包括但不限于:图表
> 4、整个 HTML 的前端样式是否符合顶级设计师的设计风格
> 5、有没有你认为可以让用户使用起来更舒服、更有体验、更能看到有价值数据的方案技巧

**执行方式**:两门禁的原文块(T-A / T-B)复制到票的闭环评论,逐条作答 + 证据;两门禁结论随交付物一起呈报,不等人类提问。

---

## 7. 偏离记录(每票 / 每交付必附,固定三问)

执行中遇到计划外情况,必须当场记录,在闭环评论中用 T-D 模板块回答:

1. **遇到了什么新情况?**(客观描述,含证据)
2. **为什么改变了方案?**(原因链:触发条件 → 判断依据)
3. **替我做了哪些关键决定?**(逐条列出,标明「此项若你不同意,可要求回退/重做」)

判定标准:凡涉及「改动规格口径 / 新增或删除场景 / 数据库字段 / 跨技能契约 / 搁置事项」之一,即使觉得「显然合理」,也必须记录。不做记录的偏离 = 未闭环。

---

## 8. 执行留痕(证据链纪律)

- 每个决策 → 票上决议评论(结论 + 依据 + 遗留/风险);
- 每个 commit → 全中文标题 + `Tested-By:` 行末(如实标注);
- 每个 map 更新 → GitHub 正文 + 本地镜像同步;
- 每张票关闭 → 闭环评论含:门禁 A/B 结论 + 偏离记录 + 交付物清单 + 审查配对票号;
- 复盘与考题阶段的证据(截图 / 测试输出)留 `.scratch/<feature>/` 或随评论附件。

---

## 9. 过程复盘(交付前 · 人类先不看成品)

全部执行完毕后、交付前,Agent 按 T-E 模板输出复盘,四段必答:

1. **整体步骤回顾**:实际执行的步骤(与计划对照,含偏离点);
2. **使用的资料和工具**:读过的文档 / issue / 报告,跑过的命令与工具(含版本/路径);
3. **遇到的困难**:按严重度列出,注明是否被门禁/纪律拦截,还是漏出到人工;
4. **解决思路**:每个困难的成因分析与解决路径,标注「可复用到其他技能」的经验。

复盘放在交付物之前,人类先读复盘,再决定是否看成品。

---

## 10. 人类理解对齐(任务结束条件)

复盘之后、交付之前,AI 出考题考察**人类开发者**(不是考察 AI),确保开发者理解到位:

**题型**(T-F 含示例):
- 选择题(单选/多选):关键概念、门禁触发条件
- 判断题:常见误判场景
- 简答题:为什么这么做(含权衡)
- 案例题:给一个真实场景,请开发者指出正确处置

**判定标准**(已拍板):
- 选择/判断:全对;
- 简答/案例:由开发者审阅 AI 的参考答案后,自评「解释正确、无关键遗漏」;
- 任一题不过 → AI 重新讲解(换角度/换案例)→ 重考,循环直至全对;
- 循环边界:同一题连续 2 轮不过 → AI 必须换讲解方式(不得复读);若开发者判定「盲区在文档而非理解」→ 修订本文档后重考。

**对齐的判定**:开发者「想法与 AI 想法对齐」= 上述考题全对 + 开发者确认理解;此时任务才算结束,进入交付。

## 11. 人类参与点清单(显式声明,缺人即停)

以下节点必须人类拍板,Agent 不得代替:
1. 规模自评结论(§2)与地图目的地确认;
2. 任何 git push / 合并 / 历史操作(Agent 只 add/commit);
3. 数据库字段/表变更(定案与实施时机);
4. 规格口径的修改(门禁 A 第 1/2 层的任何不一致);
5. 审查配对票的人工双浏览器验收(ready-for-human);
6. 考题判定与「无盲区」宣布(§10);
7. 最终交付确认(§12)。

人不在 = 停在该节点,不代答、不跳过。所有「替你做的关键决定」走 §7 记录并等你确认。

