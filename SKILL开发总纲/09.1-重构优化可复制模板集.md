## T-A · 门禁 A:垂直 5 层对账(每实施票关闭前,逐层 PASS/FAIL + 证据)

```text
## 门禁 A · 垂直 5 层对账(<技能名> · <票号/域>)

针对本次开发的所有场景,从垂直层面,从第一性原理出发,对抗式审查:

1. 最上层:调用 HELP 命令,拿到的 HELP HTML 中是否有你开发的所有场景,点击复制 prompt 后是否可以拿到商定好的 prompt
   → PASS / FAIL:<证据:HELP HTML 路径 + 场景清单对照 + 复制 prompt 抽样结果>
2. SKILL.md 根据 prompt 能否锁定到相应的唤醒词
   → PASS / FAIL:<证据:prompt → 唤醒词对照表,逐条>
3. 唤醒词触发后的 SKILL 流程是否清晰
   → PASS / FAIL:<证据:流程章节/文档路径 + 走查结论>
4. SKILL 流程底层是否能找到符合功能要求的 CLI
   → PASS / FAIL:<证据:CLI 子命令清单 + 与场景映射>
5. 调用 CLI 后是否最终拿到了符合该场景功能要求的、与「呈现数据」一致的 HTML 文件
   → PASS / FAIL:<证据:CLI 输出 HTML 路径 + 呈现数据对照>

结论:5 层全 PASS 才可关票;任一 FAIL → 修复后重跑,本段保留两轮记录。
```

## T-B · 门禁 B:HTML 第一性 5 问(每个 HTML 呈交前,结论随交付一起给)

```text
## 门禁 B · HTML 第一性 5 问(<HTML 路径>)

从第一性原理出发,对抗式审查:

1. 复制数据和复制日志按钮是否符合要求
   → PASS / FAIL:<证据:按钮位 + 5 段 JSON / 6 段日志抽样>
2. 整个 HTML 呈现的数据是否符合设计时的场景要求和呈现数据的要求
   → PASS / FAIL:<证据:场景定义 vs 呈现数据逐项对照>
3. HTML 中各个组件和内容有没有做好手机版适配,包括但不限于:图表
   → PASS / FAIL:<证据:双浏览器截图(桌面 1280x900 + 手机 390x844)>
4. 整个 HTML 的前端样式是否符合顶级设计师的设计风格
   → PASS / FAIL:<证据:样式走查结论,对照 08-HTML交互规范 与 style 令牌>
5. 有没有你认为可以让用户使用起来更舒服、更有体验、更能看到有价值数据的方案技巧
   → 建议:<列出 ≤3 条,标注是否已采纳;采纳的随本 HTML 一并交付>

结论:1-4 全 PASS 才可呈交;第 5 条为必答项(可答「无」,但必须说明依据)。
```

## T-F · 考题规则与示例(考察人类开发者)

**规则**:
1. 题型:选择题(单选/多选)、判断题、简答题、案例题;
2. 范围:关键概念解释 / 为什么这么做 / 其他可行方案 / 取舍与权衡;
3. 判定:选择/判断全对;简答/案例由开发者审阅 AI 参考答案后自评「解释正确、无关键遗漏」;
4. 循环:任一题不过 → AI 换角度重新讲解 → 重考,直至全对;同一题连续 2 轮不过 → 必须换讲解方式,不得复读;开发者判定「盲区在文档而非理解」→ 修订 09 文档后重考。

**示例题(以居家管家实战为素材,供出题参考风格)**:

- 选择题:为什么数据层变更必须「最后处理 + 单开 ISSUE」?
  A. 减少并发冲突面 B. 让业务先定型再定 schema C. 便于每项变更单独回滚 D. 以上都是 ✅
- 判断题:blocking wire 说某票被阻塞,就一定要等它关闭才能开工。→ 错(顺序规则是软约束,域自包含才是硬保障)
- 简答题:为什么「要求 Agent 做对抗式审查」不够,必须给原文模板块?
- 案例题:两个 session 并行开发,一个用 `git add -A` 提交,发现把另一个域的 31 个文件扫进自己 commit——正确处置是什么?应提前用什么规则防止?(禁 add -A + 隔离契约 + commit 自检)

## T-G · commit 自检命令(每个 commit 后立即执行)

```text
git status
git log -1 --stat
# 检查:仅本域文件;若无输出或含他域文件 → 立即处理(不要继续其他工作)
# 若 pre-commit hook 拦截:确认原因 → 允许 --no-verify,但 Tested-By 必须如实标注 no-verify + 原因
```
