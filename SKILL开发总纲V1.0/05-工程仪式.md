# 05 · 工程仪式

> 动手前的最后一道防线。这章是**自动检查清单**,不是原则解释。

## 改动前必答 3 问

1. **影响哪些文件?**(代码 / 文档 / DB schema / HTML / changelog)
2. **有没有数据迁移?**(改 schema → migration 脚本,不直接 ALTER)
3. **回滚方案?**(`.bak` 文件在哪、怎么还原;如果当前目录是 git 仓库,是否已用 git commit 额外备份本次修改)

**答不上来 = 改动还没准备好。**

## Fresh Agent 黑盒测试协议(FAT 协议)

> **开发 → commit 之间的"商用级关卡"**。跳过这一步 = 个人工具,不是可商用功能。

### 第一性原理推导

```
观察 1: SKILL.md = 开发者 ↔ 任意 agent 的契约
观察 2: 开发者有完整上下文, agent 没有
观察 3: 任意 agent 只按 SKILL.md 字面执行
推论:   SKILL.md 模糊处 → agent 走偏
推论:   SKILL.md 必须对"零上下文 reader"自洽
验证:   唯一办法 = 让零上下文 agent 真跑一遍
```

### 9 步协议

1. **选测试唤醒词** — 3-5 个核心:最高频 + 最复杂 + 最易出错
2. **准备 fresh context** — 新会话 / 新窗口 / 新 agent(**关键**:不能保留开发记忆)
3. **最小化加载** — 只给 SKILL.md + 必要 scripts / docs(不告诉 agent 应该怎么走)
4. **执行唤醒词** — 每个核心词用 **≥ 3 个人类 prompt** 各测一次
   - **人类 prompt 定义**(满足任一):
     - ① 含口语化 token:帮我 / 给我看下 / 呢 / 哈 / 一下 / 怎么
     - ② 含 slash command 前缀:/skill-name X
     - ③ 语法略错 / 不完整:缺主语 / 缺宾语 / 同音字
   - AI 风格 prompt("执行 wake word X 传入参数 Y")**不算**
   - 每个 prompt 至少含 1 个"非典型用法"(口语化或略错)
5. **捕获执行证据** — 实际调用的命令、修改的数据、产生的输出
6. **对比预期工作流** — 开发者定义的"应该怎么走" vs 实际走的
7. **判定 pass / fail**:
   - ✅ PASS:工作流一致 + 输出一致 + 无意外副作用
   - ❌ FAIL:有 step 缺失 / 调错命令 / 漏处理异常 / 输出偏差
8. **fail → 改文档不改正** — SKILL.md 没说清是文档问题,**改 SKILL.md**,再循环
9. **人工审查** — AI 评估后,人工抽查至少 1 个测试结果(防 AI 自评漏)

### 循环上限

SKILL.md 改 3 次仍未通过 → **暂停,人工介入**,可能是:
- SKILL 本身设计有问题(超出 agent 可执行范围)
- 测试选择不当(选了非典型唤醒词)
- 代码逻辑有 bug 而非文档问题

### 与现有钩子的关系

| 钩子 | 时机 | 谁审 |
|---|---|---|
| ② 改动前 3 问 | 开发前 | 开发者自问 |
| ⑥ Fresh Agent 验证 | **开发后,commit 前** | fresh agent + 人工抽查 |

→ 自问 + 他测 = 双盲验证,接近商用级门槛。

### 常见 fail mode(预警)

| Fail mode | 表现 | 改 SKILL.md 方向 |
|---|---|---|
| **隐性假设** | 开发者以为"路径在哪"写清了,实际没说 | 补具体路径 / 例子 |
| **步骤跳跃** | "参考 §02",但 §02 是独立文档,fresh agent 没意识到要加载 | 在 SKILL.md 内自包含关键步骤 |
| **歧义词** | "刷新"=重读 DB 还是重新渲染? | 改用精确动词 |
| **缺失错误处理** | 没告诉 agent 当 CLI 失败时怎么办 | 显式写出"若 X 失败则 Y"分支 |
| **人类语料缺失** | SKILL 只在 AI 风格 prompt 下工作,人类口语化(slash/口语/略错)就 fail | 变体覆盖 3 方向(同义/口语/模糊),标方向不写具体话 |

## FAT 豁免规则(何时可跳过 fresh agent 测试)

> **第一性原理**:FAT 验证 SKILL 自洽性。当改动**不改变 reader 看到的 contract**,自洽性不变,FAT 可豁免。

### 判定矩阵

| 改动类型 | FAT? | 理由 |
|---|---|---|
| ⑤ 文档层变更(SKILL.md / HTML 内容改) | **必跑** | 契约变了 |
| ④ 接口层变更(新 CLI 子命令 / 参数) | **必跑** | 行为变了 |
| ① 数据层变更(schema / 新字段) | **必跑** | 数据结构变了 |
| ② 操作层(对外)(新集成 / 外部服务) | **必跑** | 集成变了 |
| ③ 规则层变更(validators 改) | **必跑** | 约束变了 |
| 纯文档格式化(typo / 空白 / 链接) | ✅ 可豁免 | reader 看到的内容等价 |
| 纯代码重构(行为不变,unit test 覆盖) | ✅ 可豁免 | 行为等价 |
| 纯测试文件 | ✅ 可豁免 | 不属 reader-facing |
| 纯配置变更(.gitignore / pytest.ini) | ✅ 可豁免 | 不属 reader-facing |
| 显式 revert / 回滚 | ✅ 可豁免 | 回到已验证状态 |

### 反滥用护栏

| 风险 | 防护 |
|---|---|
| 滥用"行为不变"豁免 | 必须跑通现有 unit test |
| 滥用"纯 typo"豁免 | 改的字符数 < 5 个且只在 prose 区 |
| 模糊地带(refactor 怀疑有边角影响) | **默认 FAT**,不豁免 |
| 涉及 SKILL.md 任何字符 | **永不豁免** |

## 工程实施 SOP

### 改一个 Skill 时的标准顺序

1. **先读指导手册** — 确认这件事符合 6 大特性
2. **画清领域边界** → ⑤ 文档层先写 SKILL.md 第一段("管什么、不管什么")
3. **列触发词表** → ⑤ 文档层定触发词(用 v2 矩阵,见 [03](./03-触发词设计v2.md))
4. **设计 schema** → ① 数据层先建表 + 索引 + .bak 策略
5. **写硬规则** → ③ 规则层先写 `validators.py`(无跳过通道)
6. **写 CLI** → ④ 接口层最后接(argparse + `{status, data, message}`)
7. **写集成** → ② 操作层(对外部分)按需要加
8. **跑自检清单** — 5 层 + 改动前 3 问
9. **验证 HTML 输出路径 + 命名** → 原则 12(分类):12.A 数据/过程 走 `<command_cn>_<datetime>.html`,12.B HELP 走 `<skill 中文名>_HELP_<datetime>.html`,SKILL.md §📌 输出位置 显式标 12.A 或 12.B

### 写一个 HTML 模板时的标准顺序

1. **判定是否值得做** → 原则 0(多字段 + 多条目 + 视觉密度 ≥ 5)
2. **检查 CLI** → 原则 1(必须支持 `as_dict=True`)
3. **选模板模式** → 决策矩阵(单卡 / 趋势 / 排行 / 状态 / 综合 / 对比)
4. **复制 [_assets/template_skeleton.html](./_assets/template_skeleton.html)** → 改具体字段
5. **引用 [_assets/style.css](./_assets/style.css)** → 调色板和字体自动统一
   - CSS 路径处理(三选一):
     - **方案 A(推荐)**:拷贝 `_assets/style.css` 到 Skill 的 `templates/` 目录,骨架 `<link href="style.css">` 即可
     - **方案 B**:软链 `ln -s ../../SKILL开发总纲V1.0/_assets/style.css templates/style.css`
     - **方案 C**:将 CSS 内联到 `<style>` 标签(适合单文件分发,但失去集中更新)
6. **写渲染器** → 4 步模式(subprocess + assert + inject + write)
7. **测试** → Chrome 打开 + 5 状态都触发
8. **同步** → SKILL.md + HTML + changelog 同 commit

> 如果该 HTML 是 HELP HTML，则额外执行 [07-HELP与场景完备性.md](./07-HELP与场景完备性.md) 的验收：场景资产作为唯一事实源、保留全部合法场景、`【待开发】` 显式标注、跨手机/PC 视口验证以及每场景独立复制按钮。

## Commit 规范

| 规则 | 说明 |
|---|---|
| 每 Phase 一个 commit | 失败可独立 `git revert` |
| commit 前缀 `[技能名]` | `git log --grep` 精确搜 |
| 信息含:文件清单 + 行为变化 + 向后兼容 | 便于 reviewer |
| 不进 git:测试 HTML / 临时方案 / 备份目录 | `.gitignore` 排除 |
| **每个 commit 都通过 Fresh Agent 黑盒测试** | **钩子 ⑥,硬规则**(可豁免见"FAT 豁免规则"章节) |
| commit 加 `Tested-By:` 字段 | normal `fresh-agent-v1` 或 exempt + 原因 |

### Tested-By 字段格式

```
[skill-name] 改动描述

... (原 4 段)

Tested-By: fresh-agent-v1
  - 唤醒词: [list of tested wake words]
  - 人类 prompt: [≥ 3 个口语化/slash/略错 prompt,各唤醒词至少 1 个]
  - 结果: pass / pass-after-N-loops
```

或(豁免时):

```
Tested-By: exempt + 原因
  - 豁免依据: <纯文档格式化 / 行为不变重构 / 纯测试 / 纯配置 / 显式 revert>
  - 自检: <说明为什么 reader 看到的 contract 没变>
```

> **没填豁免依据 = 协议不完整**,人工审查会发现。

### Commit 信息示例

```
[卡路里] Phase H.6: 新增"查运动趋势"HTML 模板

文件清单:
+ 卡路里/templates/exercise_trend.html
~ 卡路里/scripts/render_exercise_trend.py

核心变动:
...

Tested-By: fresh-agent-v1
  - 唤醒词: 查运动 / 查运动趋势 / 查运动贡献
  - 结果: pass (1 loop)
```

## Git Hooks(pre-commit)

`.githooks/pre-commit` 自动跑对应 skill 的 pytest(真实工程配置,非示例):

```bash
case "$path" in
    居家管家/*) NEED_TEST[居家管家]=1 ;;
    卡路里/*)    NEED_TEST[卡路里]=1    ;;
esac
```

**新增 skill 时**:在 case 列表中加新条目。

## 测试模板(最小可行)

```
<skill>/tests/
├── conftest.py        # 添加 scripts/ 到 sys.path + 共享 fixture
├── test_validators.py # 硬规则单元测试(不依赖 DB)
├── test_render.py     # 模板生成测试(如有 HTML 模板)
└── test_payloads.py   # payload 函数结构测试(需 DB)
```

`pytest.ini`(最小):
```ini
[pytest]
testpaths = tests
python_files = test_*.py
addopts = -v --tb=short
```

## 跨 Agent 知识传播清单

**新 agent 第一次处理 SKILLS/ 时**:

1. 读 `SKILLS/SKILL开发总纲V1.0/SKILL.md`(主入口)
2. 读 `SKILL开发总纲V1.0/02-5层骨架.md`(核心权威)
3. 读目标 skill 的 `SKILL.md`(第一段定义管什么)
4. 跑 `cd <skill> && python -m pytest tests/ -v`(验证基线)
5. 检查目标 skill 的 `.html` 镜像是否与 SKILL.md 一致

## 已知边界(用户决策)

- ✗ **不做 web 端 CI**(GitHub Actions / GitLab CI)
- ✗ **不做 web merge 防护**(branch protection / required check)
- ✗ **不做 SDK 防护**(依赖 SKILL.md 硬规则 + AI 自约束)
- ✓ **本地 hook + 总纲硬规则**是当前完整防护

接受的风险:
- Web 端绕过(用户决策忽略)
- `--no-verify`(依赖 AI 自约束 + commit message HOTFIX 约定)
- Git 库直调(依赖 AI 自约束)

## 已知陷阱(自检)

- ❌ `cmd.exe /c start chrome "..."` — 引号陷阱,URL 会被 URL-encode 进乱码
- ❌ 把含中文的路径直接传给 shell — PowerShell 中文参数 → Python subprocess 列表传参
- ❌ `--no-sandbox` — 除非调试环境,否则有安全风险
- ✅ 用 `file:///` 协议而非路径直传
- ✅ 路径 URL-encode — 中文 / 空格必须编码

## 失败处理

- 测试失败 → 排查后修复,**不** `--no-verify` 跳过
- Hook 失败 → 检查 `core.hooksPath` 配置
- 数据不一致 → 先回滚到上次 commit,再排查根因
