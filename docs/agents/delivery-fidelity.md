# AI 交付保真规范（Delivery Fidelity）

本规范解决一个问题：**AI 交付只有 60%**——「做完」和「做对」之间的差距。任何 agent 在本仓库交付任何工作（代码、文档、调查、HTML、issue 闭环）都适用。

来源：2026-08-11 用户在 Base Skill map 调查中多次指出「自动做做了 60%，但总有很多问题」，复盘出根因与六个保真手段。本文件是仓库级落地版。

## 一、三个层次的偏差

| 层次 | 现象 | 本质 |
|---|---|---|
| 方案层 | 拆解执行时「方案制定、讨论、细节拿捏不面面俱到」 | 把「该问的决策」当「可自己定的实现细节」 |
| 对话层 | 「没有仔细跟我 real、没有仔细跟我讨论」 | 问问题流于表面（问「A 还是 B」），没问「为什么、边界在哪、什么算成功」 |
| 交付层 | 「自动做做了 60%，但总有很多问题」 | 自评乐观 + 验收标准模糊 → 60 分也敢交付 |

## 二、第一性原理

1. **AI 的默认行为是「完成」，不是「对齐」**。AI 的奖励信号是「交付一个东西」，不是「交付一个你认可的东西」。它会找一个自认为合理的落点就停——这个落点通常离真实意图有 40% 偏差，因为意图包含大量没说出口的隐含假设（风格、边界、成功标准、用户讨厌什么）。
2. **讨论的质量 = 信息传递的保真度**。用户完整意图 → AI 问问题（损失）→ AI 理解（再损失）→ 方案（再损失）→ 交付。问「A 还是 B」只传递约 20% 意图；问「边界、反例、成功标准」能传递约 80%。
3. **AI 自评是乐观的**。没有外部校验点时，AI 是唯一裁判，而它只会判自己通过。验收标准在用户的验收清单里，不在 AI 脑子里。

## 三、六个保真手段

### 1. 交付前「三问自检」——零成本，每次必做

AI 在交付任何东西前，强制自问并**把答案写出来给用户看**：

1. **我做了什么假设？**（列出来，用户一眼看出哪条是错的）
2. **哪些是我自己拍的板？**（本可问但没问的）
3. **什么算成功？**（我理解的成功标准，与用户核对）

把「隐含决策」显式化。这是成本最低、收益最高的手段。

### 2. grilling 从「问选择」升级到「问边界」

禁止只问「你要 A 还是 B」（20 分提问）。升级为四连问：

- **反例**：「什么情况下这个方案是错的？」
- **边界**：「这个做到什么程度算过头？」
- **验收**：「你拿到手会先检查什么？」
- **历史**：「之前类似的东西你哪里不满意？」

这四个问题挖出 A/B 背后的「为什么」，把 60% 拉到 80%。

### 3. 「先交决策清单，再动手」——执行前的契约

执行任何非平凡任务前，先给用户一份**决策清单**（我要做什么、几个关键选择点、我的推荐、理由），用户点头后才动手。比「边做边问」高效——用户的一次性反馈覆盖所有决策点。

注意：这不是让用户替 AI 做决定，是让 AI 把「它要替用户做的决定」提前暴露出来审。

### 4. 验收标准进 ticket——「什么算完成」写进 issue

每个执行 ticket 的 body 必须有**验收清单**（可勾选、可验证），派活时由用户确认。AI 交付时对照清单自检，用户验收时对照清单打分。**没有验收清单的 ticket = 注定返工**。

反面案例：Base Skill map 的 T1-T3 ticket 只说「调查什么」没说「证据要达到什么标准」，subagent 凭自己理解交付，三份报告都要对抗式审查纠偏。

### 5. verifier 独立审查——不信自评

AI 交付后，用**独立的 verifier agent** 对抗式复核（不信交付者的自述，专门找洞）。**关键：verifier 与执行者分离，执行者不能自证。**

反面案例：T1 报告把 eae5f16「新增测试」当「拦截实证」——若有独立 verifier 查 git 历史，当场能发现，不用等用户质疑。

### 6. 「小步交付 + 里程碑确认」替代「憋大招」

大任务拆成可确认的里程碑，每个里程碑交付一个**可看的中间产物**（不是半成品，是「这一段的完整结论」）。方向确认后再继续。

反面案例：T2 生产库审计一口气跑 11 个脚本全查完才汇报，中途时区错判没人发现，最后返工重查。正例：先交付「库结构 + 污染初扫」，用户发现时间戳问题，再深挖——省一半返工。

## 四、应用时机

| 任务规模 | 必用手段 |
|---|---|
| 一句话能说清的小事（改配置、查数据、简单回复） | 手段 1 |
| 单文件修改 / 单技能小功能 | 手段 1 + 3 + 4 |
| 跨技能 / 跨会话的大任务（wayfinder map、重构） | 手段 1-6 全用 |

## 五、与既有约定的衔接

- **提问必须带背景**：任何 ask_user / 选择题 / 拍板提问，先给足背景（来龙去脉、每个选项的含义与代价），到「一个没参与上下文的人也能判断」的程度，宁多勿少。手段 2 与它配套：背景负责「用户能看懂」，边界四问负责「挖出真意图」。
- **交付完整性审计**：issue 收尾时自查——代码全部 commit、交付物入库、思想共识沉淀、issue 状态闭环。手段 1-6 是过程规范，完整性审计是收尾规范，配套使用。
- **测试隔离红线**：跑 pytest 不手动设 `SKILLS_DB_PATH`（会绕过 conftest 隔离写生产库）；生产库审计只读（`mode=ro` + SELECT only）。手段 1 的三问自检里必须有「我这次操作会不会碰生产库」。

## 六、一句话总结

> AI 停在 60% 不是能力问题，是「对齐机制」缺失。六个手段的本质是同一个：**把隐含的、自证的、未说出口的，全部显式化、外部化、给用户审。**手段 1-2 零成本马上能用；3-4 让流程变稳；5-6 让质量可控。
