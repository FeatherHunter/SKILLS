# AI 执行框架（Execution Framework）

用户定制的「执行前 / 执行中 / 执行后」三项工作要求。任何 agent 执行 wayfinder / map / ticket / 技能任务时默认遵守。**本规范是外部机制：不修改 wayfinder 等任何技能文件**，靠仓库约定（本文件 + AGENTS.md）+ 辅助 SKILL 落实。

来源：2026-08-11 用户提供完整框架（告诉起点 → 发现盲区 → 采访澄清 → 原型验证 → 执行计划 / 记录偏离 / 过程复盘 → 确认理解 → AI 反向考验 → 答明白再交付），并要求「不改 wayfinder 技能文件，让 AI 执行时自动做好三项工作要求」。

## 一、三阶段总览

| 阶段 | 环节 | 一句话 |
|---|---|---|
| 执行前 | 告诉起点 | 先对齐「用户知道什么、不知道什么」 |
| 执行前 | 发现盲区 | 找「未知的未知」（遗漏变量/风险/易忽略因素/需提前决策点） |
| 执行前 | 采访澄清 | 挖隐含假设（成功标准/为什么/边界） |
| 执行前 | 原型验证 | 给 2~4 个方向（差距要大），快速验证，逐轮收敛 |
| 执行前 | 执行计划 | 步骤/时间/资源/交付物与验收标准/风险与应对 |
| 执行中 | 记录偏离 | 实时记录新情况/改方案原因/关键决策/对结果的影响 |
| 执行后 | 过程复盘 | 步骤回顾/资料工具/困难/解决思路 |
| 执行后 | 确认理解 | 关键概念/为什么这么做/其他可行方案/取舍权衡 |
| 执行后 | AI 反向考验 | AI 出题（选择/判断/简答/案例）检验用户理解 |
| 执行后 | 答明白再交付 | 用户答对 → 确认交付；答错 → 补讲再交付 |

## 二、执行前

### 1. 告诉起点（对齐起点状态）

任务开始前，先收集并记录四行起点（模板）：

```
1、最终目标（要做什么）：
2、当前进度（目前想到哪一步）：
3、经验水平：新手/有经验/专家
4、明确告知哪些地方不熟悉：
```

**为什么**：AI 的沟通带宽取决于「用户懂多少」。技术点（如注入器/占位符/pip）对新手要大白话解释；「提问必须带背景」是 AI→用户 给背景，告诉起点是 用户→AI 给起点，互为镜像。

### 2. 发现盲区（Blind Spot Pass）

检查四类盲区，缺一不可：

1. **遗漏的关键变量**——还有什么变量没考虑到？
2. **潜在的风险**——什么会翻车？
3. **容易忽略的影响因素**——什么小事会放大？
4. **需要提前决策的点**——什么现在不定以后会卡？

产出：结构化盲区清单（wayfinder map 级 = map 正文「盲区清单」区；任务级 = 汇报给用户）。

### 3. 采访澄清（grilling 问边界）

禁止只问「你要 A 还是 B」。四连问挖真意图：

- **反例**：「什么情况下这个方案是错的？」
- **边界**：「这个做到什么程度算过头？」
- **验收**：「你拿到手会先检查什么？」
- **历史**：「之前类似的东西你哪里不满意？」

**每个问题必须先给背景**（来龙去脉 / 为什么问 / 每个选项的含义与代价），到一个没参与上下文的人也能判断的程度。

### 4. 原型验证（先做原型再定方向）

1. 给出 **2~4 个方向**（差距要很大，不要同质选项）
2. 快速验证思想（最小原型/示例）
3. 由用户选择和反馈
4. **几轮选择后逐步收敛**到用户满意的方向

**为什么**：空想不如试。用户原则「Schema 不要空想」——写最小原型 → 用真实数据试 → 再定契约。

### 5. 执行计划

非平凡任务动手前给用户决策清单 + 计划：

1. **明确步骤**（分几步）
2. **时间安排**（每步何时完成）
3. **所需要的资源和工具**
4. **交付物和验收标准**（可勾选、可验证，写进 ticket）
5. **风险和应对方案**

## 三、执行中

### 记录偏离（AI 做过程记录员）

实时记录，不等到最后才补：

1. 遇到了什么新的情况？
2. 为什么改变方案？
3. 做了哪些关键决定？
4. 对结果的影响？

**落地**：每个 ticket 的闭环评论（close 前）必含「偏离记录」区，按以上四问填写。wayfinder map 级 = 决策发生即时更新 Decisions so far（含为什么/取舍）。

## 四、执行后

### 1. 过程复盘

交付成品之外，还要看懂过程：

1. 整体步骤回顾
2. 使用的资料和工具
3. 遇到的困难
4. 解决思路

### 2. 确认理解

对关键决策逐条解释：

1. 关键概念解释（大白话）
2. 为什么这么做
3. 其他可行方案（当时没选什么，为什么）
4. 取舍和权衡

### 3. AI 反向考验我

AI 出题检验用户理解（防假验收：点头 ≠ 理解）。四种题型，按任务复杂度选 1~4 种：

- **选择题**：关键决策的变体场景，哪个对？
- **判断题**：一个说法，对还是错？
- **简答题**：用一句话解释某个概念/为什么这么做
- **案例题**：给一个新场景，用户判断该怎么走

出题原则：考「决策的理解」，不考「实现细节」；题目基于本任务真实决策，不用抽象题库。

### 4. 答明白再交付

1. 回答正确 → 确认理解无盲区 → 确认交付（close ticket / close map）
2. 回答错误 → 补讲对应知识点 → 重新出题验证 → 再交付

**门禁**：用户没答对，不 close。这是 map/ticket 关闭前的最后一道闸。

## 五、应用方式

### wayfinder map 级（机制 4：map 正文承载）

不修改 wayfinder 技能文件，map 正文（数据层）承担框架内容：

| 框架环节 | map 正文落点 |
|---|---|
| 告诉起点 | 「起点声明」区（四行） |
| 发现盲区 | 「盲区清单」区（四类结构化） |
| 采访澄清/原型验证 | 决策前 grilling（决策清单 → 2~4 方案 → 用户拍板） |
| 执行计划 | 票清单补「交付物/验收标准/风险应对」 |
| 记录偏离 | ticket 闭环评论「偏离记录」区 + Decisions so far 记为什么/取舍 |
| 复盘/确认理解/反向考验/答明白 | map close 前四步门禁，缺一不 close |

### 任务级（辅助 SKILL 承载）

加载「执行框架」辅助 SKILL（触发词：按执行框架来 / 执行前检查 / 五段式），内含各环节检查清单、提问模板、出题示范。

## 六、与既有约定衔接

- **交付保真规范**（delivery-fidelity.md）：本框架是它的上位框架（对齐机制全生命周期版）；6 手段是本框架各环节的具体操作法
- **提问必须带背景**：本框架的「采访澄清」强制先给背景再问
- **交付完整性审计**：本框架的「答明白再交付」是审计的验收闸门；完整性审计是收尾自查清单
- **测试隔离红线**：任何环节涉及 DB 时遵守「不设 SKILLS_DB_PATH / 生产库只读」
