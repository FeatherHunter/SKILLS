A

过程审查 · 5 个方法漏洞

原断言 → 实证 → 严重度
每个漏洞都做了实证复核（7 项验证全部实跑），区分「实证推翻」「推断越界」「口径失真」。
1 · 权威源未确认就下结论：卡路里场景数 449 = 开发期 JSON，非运行时高 · 实证推翻
报告原断言：「卡路里 449 场景 · _triggers.py 为运行时权威源」
实证结果：_triggers.py 实际 436 条 TRIGGER（含「复盘 9」分类）；scene_data JSON 449（含「技能协同 36」）；render_help_center.py 是双源合并（scene_data 优先覆盖，_triggers 补齐旧分类）——「单一权威源」表述错误，449 只是开发期数据。
修正：改口为「开发期 449 / 运行时 436 / 双源合并渲染，分类体系两套（复盘 vs 技能协同）」。影响：#289 归一化层必须处理双源合并逻辑。
2 · 占位符只查一种：漏了 INJECT-SHARED / INJECT-08 两套管线高 · 实证推翻
报告原断言：「备忘录 0/7 未接（几乎无管线）」「私家大厨 0/20 未接」
实证结果：备忘录 7 模板中 6 个用 INJECT-SHARED（第三方 clipboard.js 体系，T3 #263 记载的 3 套机制之一）；私家大厨全套用 INJECT-08（08 规范时代占位符）+ INJECT-DATA——两技能都有自研注入管线，只是名字不是 SHARED-HELPERS。
修正：Base 管线盘点应覆盖全部 3 套占位符体系（SHARED-HELPERS / INJECT-SHARED / INJECT-08），T3 #263 已有记载却被我漏掉——盘点的第一步本该是读 T3 结论，我跳过了。
3 · 未看内容就断言：「1110B 跳转壳」是编造的细节高 · 实证推翻
报告原断言：「作息管家 6 个 1110B 占位模板（schedule_record_*）是重定向页（约 1KB 跳转壳）」
实证结果：这些是已接 Base 管线的 engine 型模板骨架（hero + root + _record_engine.js + SHARED-HELPERS + SHARED-CSS + INJECT-DATA），1110 字节只因内容全在外部 JS。它们不是占位壳，且属于「已接 Base」的 19 个——我既描述错了性质，也漏掉了「作息管家 engine 模板已接 Base」这个本应强调的事实。
修正：删除「跳转壳」表述；页面清单补注「6 个 engine 骨架模板已接 Base 管线（#269 试点实际覆盖 19/20 含 engine）」。教训：1KB 小文件可能是骨架而非壳，看内容再下结论。
4 · 推断越界当实证：「5 个 error.html 复制粘贴」中 · 部分实证
报告原断言：「居家管家 5 个域级 error.html 按域复制粘贴（#286 同类痛点）」
实证结果：5 个文件 md5 全不同（3410~8231 字节）——不是逐字节复制，是「同构重复」：样式家族相同（同款 hero/fail/kv/actions），但各自独立实现、参数内容不同。这是 T3「同源副本漂移」的又一实例，但不是「复制粘贴」。
修正：改口为「同构重复（样式家族相同、独立实现、参数各异）」——收敛价值不变（6 个错误页 → 1 个 Base 控件），但表述要准确。
5 · 代理指标失真：svc 计数当图表量、error 正则混义、模板数口径污染中 · 口径失真
报告原断言：「卡路里 27 模板 35 处 svg」「私家大厨 320 处 empty/error」「模板总数 76/67/20/25/7/20」
实证结果：① <svg> 出现 ≠ 图表（可能是图标/装饰），35 处中有多少是真正图表未逐验——卡路里图表量可能被高估；② empty|暂无|error 正则混义（error 会匹配 JS 错误处理/变量名），320/186/134 等绝对数不可信，只能当相对量级；③ 卡路里 76 含 .bak/临时样例/设计审查报告，非交付页面。
修正：数字降级为「量级估计」，标注口径；页面清单剔除开发残留。第一性原理：盘点的目的是「判断能否收敛」，不是数数——计数应服务于形态判断。

C

草案盲区 · 从第一性原理出发

盘点目的 = 支撑参数化 HELP 落地
第一性原理问题：统一 scene_data 草案是否覆盖了「参数化 HELP」的全部输入？答案：没有，4 个盲区。
盲区 1 · 非场景元信息无承载高
草案只有 groups + scenes——但各技能 HELP 有大量「非场景内容」：私家大厨 prompt_rules（禁写 CLI/模板路径/数据库字段）+ methodology（rule_1~5）+ status_legend、备忘录 dependencies（初始化场景）、卡路里 AI 验证协议（§⚠️ 第 7 条）。这些才是参数化 HELP 的真正难点——场景列表只是数据搬移，技能特有规则怎么注入模板没设计。
修正：#289 票 body 补「非场景元信息承载」为必做项；草案 v2 加 meta_blocks（技能特有 HTML/规则段，Base 原样透传）。
盲区 2 · editable_fields 概念混淆中
草案把三个不同语义并成一个字段：fill_hints（AI 视角提示用户补字段的占位符）、dimensions（数据维度约束，如「activity: 任意活动」）、prompt 内参数（复制 prompt 里的 ________ 填空）——三者来源、用途、渲染方式都不同，归一化为 editable_fields 会丢语义。
修正：#289 拆「可编辑字段来源三选一映射」的 grilling 问题，不直接合并。
盲区 3 · 图表分类粒度自相矛盾低
报告标题说「4 种形态」，表格列了 6 行（共享/内联/JS条/模板串/CSS进度/无）——「形态」粒度不一致，容易误导后续 #288 的范围判断。
修正：明确「4 种实现形态 + 1 种无图表」的分法（共享组件 / 内联静态 / 动态生成 / 纯 CSS），饼干记账模板串与作息 JS 拼接同属「动态生成」。
盲区 4 · 归一化层位置是设计决策，盘点结论越权拍板低
「归一化层放 Base、每技能一份映射配置」——方向是 T4「Base 管渲染」的合理延伸，但「放 Base 内」vs「技能侧转换脚本」vs「注入期转换」是 3 个可选项，属于 #289 的 grilling 范畴，不该在盘点结论里直接定。
修正：#289 票 body 把「归一化层放 Base」改为待 grill 决策项（给出 3 方案 + 我推荐 Base 内配置的理由）。

流程审查 · 开票先于验收

wayfinder 纪律
3 张组件票在用户验收盘点前开出中
#288/#289/#290 的 body 全部基于盘点结论（含上述错误断言：如 #289 引「卡路里 449」「备忘录未接」）——如果用户对盘点有异议，票 body 要返工。wayfinder 流程本可「先交报告 → 用户拍板 → 再拆票」。
缓解因素：3 张票均为「落地实施」类，body 里的数字错误不影响实施方向（接口/范围正确）；且盘点票是 task(AFK)，用户验收点在组件票交付时。但「先验收再拆票」仍是更稳的次序。
修正：本轮审查后修订 3 张票 body（同步修正断言）；后续拆票类操作默认「报告 → 用户确认 → 开票」。
