对抗式审查 · 两份契约 v1

扮演 verifier：挑毛病，不走过场——从第一性原理问「这契约拿去实施，会在哪翻车」

高优先级（必改，不改实施必翻车）

① Base 资产与居家管家《_shared.py》双源漂移风险 高
为什么是问题：契约说 base.js「逐字来自 v2 基准（居家管家 _shared.py）」——但 _shared.py 是技能内文件，Base assets/base.js 是新文件，两者同源并存。这正是拷贝漂移的病根（饼干记账前科）：改 Base 后居家管家还用旧 _shared.py → 又分叉。唯一真相源没定义。
修法：契约声明「Base = 唯一真相源；各技能原实现（含居家管家 _shared.py / 饼干记账 _shared_js.py 等）在对应技能迁移完成后退役」；迁移完成前，修改只允许发生在 Base，技能文件只读。
② payload 信封契约缺失 高
为什么是问题：Base 组件（buildDataText/buildLogText/metaHeader）依赖 data.meta（command_cn/occurred_at）和 data.scene 结构——但契约没定义「payload 信封」：6 技能 payload 结构不一样，注入器也不校验结构。组件契约缺了它依赖的输入契约（T3 早就提过「先定 payload 信封契约」，v1 漏了）。
修法：契约补「payload 信封契约」：{status:'ok', data:{meta:{command_cn, occurred_at, wake_word?, skill_version?}, scene:{...}}}；注入器加结构校验（可选开关），build* 函数依赖字段列出清单。

中优先级（应改，不然后面返工）

③ 硬拦截的豁免通道未定义 中
为什么是问题：硬拦截 = 模板必须恰 1 个 SHARED-HELPERS。但全仓库模板都真的需要公共 JS 吗？纯静态页（error 简单页？）被硬拦会逼着无意义注入。没有豁免机制，「强制」会误伤合理场景。
修法：定义豁免规则：模板头部声明 <!--NO-SHARED--> 显式豁免（白名单式，缺省=必须注入）；豁免名单由 render 公共层维护并审查。
④ 签名变更/版本机制缺失 中
为什么是问题：Base 是跨技能资产，改一个签名波及 6 技能 100+ 模板。契约说「修改走公共层 ISSUE」，但没有版本号/破坏性变更规则——签名改了，哪些技能必须同步？怎么知道谁还没跟上？
修法：契约加版本字段（Base v1.0）；签名变更 = 破坏性变更：必须全技能同步 + 一次性完成 + 变更记录进 CHANGELOG；兼容期规则（旧签名保留一个版本周期）。
⑤ HELP 场景卡片的「可编辑字段」结构缺失 中
为什么是问题：复制按钮契约 v2（#123 拍板）要求「复制 prompt 参数化：可编辑字段 + 实时预览 + 空值拦截」——HELP 场景卡片大概率要支持这个。参数化 HELP 契约的 scenes 数据结构没定义 editable_fields，会与复制按钮契约 v2 冲突。
修法：scenes 参数补 editable_fields?: [{name, label, value, hint}]（复用 Base P0 copyText + 表单交互），与复制按钮契约 v2 对齐。
⑥ output_filename 路径安全 中
为什么是问题：文件名参数化——如果外部传入 ../../x 就能写出任意路径。安全盲区。
修法：文件名 sanitize：只允许 [a-zA-Z0-9_\-\u4e00-\u9fa5] + .html 后缀，禁路径分隔符；校验失败报错。

低优先级（可选，先记着）

⑦ P0/P1 实施分界未定义 低
第一版 P0+P1 一起入库，P0/P1 标签变成纯分类——实施时谁先验收、谁先冻结没写清。
修法：写清「P0 先行冻结验收 → P1 跟随」的两步走（原型已按此验证）。
⑧ scene_data 兼容性未调查 低
参数化 HELP 假设了统一 scenes 结构，但各技能 scene_data JSON 是否兼容没盘过——有「脑补」风险（你的原则：不脑补）。
修法：HELP 参数化实施前（P2 阶段）先做 scene_data 结构盘点，确认统一结构可行再定稿；本契约标注「待盘点确认」。

结论

必改 2 条（双源漂移 + payload 信封）→ 应改 4 条（豁免/版本/可编辑字段/文件名安全）→ 可选 2 条（P0/P1 分界 + scene_data 盘点）。第①条最重要：不定义唯一真相源，Base 出生第一天就带着「会再次分叉」的种子。
