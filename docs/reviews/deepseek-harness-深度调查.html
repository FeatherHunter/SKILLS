Part 1 · 实现原理深度解析

§1 它到底是什么？

不是新模型，不是 API 客户端，是让模型真正进入真实环境干活的运行时。

在 DeepSeek 看来，过去两年大家卷模型参数、卷价格、卷 benchmark 都没错，但模型调用 API → 拿到一段文字，这个链条还差最后一段——把模型接到文件系统、终端、网页、长任务、子 agent，让它真能干活。DSH 就是补这一段。

底座是 Cordis 插件元框架（注意：Cordis 是 DSH 团队的微内核，跟"Card 卡片"不是一回事——这是个常被混淆的点）。Cordis 提供一个可叠加、可 patch、可替换的容器；DSH 在它之上定义了一整套 Agent 语义。

官方公式：Model + Harness = Agent

§2 核心哲学：Everything is a Plugin（不是口号，是真的）

「插件」在 DSH 里不是 Chrome 扩展那种。看清楚了，下面是定义：

一个 DSH 实例 = 一棵插件树。所有"看起来像是 DSH 内置"的能力——模型适配器、工具注册表、会话日志、Agent Loop、文件系统、Shell、子 agent 调度、UI——全部都是插件，都可以从配置里替换掉。

这跟 Claude Code / Codex 的根本区别是：

维度Codex / Claude CodeDeepSeek Harness
本质一台做好了的 Mac一台自己拼装主板显卡的 PC
扩展点MCP / Skills / Hooks 装在产品上Agent 本身由插件组成
核心 Loop写死在 core logic，用户不能动是插件 ctx.agentLoop，可换
模型绑定自家模型适配器是插件，可换任何 provider
"改个皮肤"主题切换皮肤插件也是改了运行时的一部分，连 UI 渲染逻辑都换

实战意义：别人写的"插件"在 DSH 里不只是给 Agent 加能力，而是可以替换 Agent 的某个器官——换掉 Agent Loop、换掉子 agent 调度器、换掉文件系统 provider。

§3 运行时结构：profile + 组合包 + patch

profile = 存放在 ~/.harness/home/ 的具名组装方案。它列出自己叠放的组合包、自己安装的树外插件、保存自己的 cordis.patch.yml。

组合包（bundle） = Cordis 配置项 + 挂载代码的分发格式。dsh-base 是每个 profile 的第一层：

┌─────────────────────────────────────────┐ │ dsh-base (必有) │ │ ├─ 模型适配器 (ctx.llm) │ │ ├─ 工具 (ctx.tools) │ │ ├─ 持久化 (sessions 存储) │ │ ├─ 沙箱与审批策略 (ctx.sandbox) │ │ ├─ 设置 / 凭据 / 遥测 │ │ ├─ Agent 接口 + 事件 (ctx.agents) │ │ └─ Agent Loop 默认驱动器 │ │ (ctx.agentLoop) │ ├─────────────────────────────────────────┤ │ dsh-web-app (UI 形态) │ │ → 加 Web 浏览器应用 │ │ → 启动: npx @deepseek-ai/dsh web │ ├─────────────────────────────────────────┤ │ dsh-headless (无服务器) │ │ → 一次性运行器，CI/脚本用 │ └─────────────────────────────────────────┘

叠加顺序（关键，不可变）：

  1. 按 profile 列出的顺序应用每个组合包
  2. 之后是 profile 的 cordis.patch.yml
  3. 然后是 home 级的那份
  4. 最后是任意 --patch overlay
  5. patch 按 id 定位条目，替换其整个 config

想看你机器实际加载的配置树？一条命令：dsh --profile web --dump-config。打印出来的任何一条都允许被你自己的 patch 替换。

4 种运行模式 = 4 种不同插件组合的 preset，不是切换模型，是切换"手上有什么工具 + 怎么跑"：

  • 标准模式：叠满全部能力（文件、Shell、Skills、计划、目标、子 agent、工作流）—— 给普通编程用户
  • PTC 模式（Programmatic Tool Calling）：只给模型一个 run_code 工具，把其他工具自动打包成 TypeScript SDK，模型写代码一次性串起来，中间数据留在执行环境里不进上下文——省 token，重度用户/自动化用
  • 极简模式：只给 bash + str_replace_editor——给"我模型就是强，不需要脚手架"的纯编程测试用（官方测 V4 Flash 用的就是这个）
  • 创造模式：标准模式 + 运行时检查 + 插件实验 + preset 创作——给做插件的开发者

§4 三个核心子系统

4.1 会话子系统（core/session）

会话语义 = 追加式的 SessionEvent 日志。这是模型所见上下文的唯一来源。

运行时不变性：「模型可见即已记录」——抵达模型请求的一切都必须能从日志重建。要加一项模型可见输入，就必须加一个 SessionEvent（扩展 SessionEventMap 并从日志渲染），不允许绕过日志"插队"塞东西到模型上下文。

为什么这么做？因为fork / 恢复 / replay / 文本导出 / 遥测全部从这条事件流派生。日志 = 单一事实源，状态在哪里一目了然。

4.2 Agent 循环子系统（最关键的设计）

turn/start 领取 next-step input + 一条排队消息 装配 prompt 段 + tool schemas → agent/pre-step ← waterfall，可拒绝/改写消息 step/start append entered messages as user/message 从日志 deriveMessages() → 派生模型历史 agent/request → llm/stream → assistant/chunk* → assistant/message tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* step/end 还有欠下的工作？→ 下一轮 → agent/turn-stopping turn/end

这是 DSH 与其他 Agent 框架的"骨"。注意几个关键设计：

  • 步骤（step）= 一次模型请求 + 它的工具调用；轮次（turn）= 零个或多个步骤。这个抽象让"长任务"和"短对话"用同一套状态机。
  • waterfall 事件（agent/pre-step / agent/request / llm/stream / 三个 tools/*）：监听器必须调 next()才能委托下去——这是给"在模型看到东西之前插一脚"用的标准 seam。
  • agent/turn-stopping 是 serial 事件，没有 next()——这是给"判定任务应该停"用的，不能被一个监听器无限延迟。
  • 所有 turn/* / step/* / user/message / assistant/* / tool/* 都是持久会话事件；其余是三个事件域里的实时扩展点。

实战意义：你可以监听 agent/pre-step 注入上下文、改写消息、加合规审查；监听 tools/pre-execute 在每次工具执行前做权限/审计；监听 agent/turn-stopping 决定何时停。这些都是通用扩展点，不写死业务逻辑。

4.3 能力 seam（三件套）

一个 seam = 一项可替换能力，由三种角色组成：
• Service Definition：声明接口
• Service Provider：实现接口
• Consumer：使用它（通常是面向模型的工具）

seam 的妙处：替换一个提供方就能改变整个产品，因为消费者只认接口。

最关键的 seam：

Seam替换效果
ctx.fs改文件系统后端 = 改所有依赖 FS 的工具
ctx.subprocess改进程 spawn 后端 = 改 Bash、PTY、LSP 的执行世界
ctx.shell同上，但抽象更高（管"运行一个 shell 命令"）
ctx.sandbox在启动进程前包装 argv，限制权限
ctx.terminals持久化终端（不是一次性 bash）
ctx.agents (subagent provider)子 agent 后端——真的能拉起你本机的 Codex 或 Claude Code

subagent seam 是最有野心的一刀：DSH 文档明确说，"subagent provider 在同一接口后差异巨大，从新建一个子 agent，到把一个轮次委派给另一个产品（如官方 Codex、官方 Claude Code）"。这意味着 DSH 在设计上真的可以调度别的 Agent 框架。

文件系统 + 进程共享执行世界的妙处：你把 FS provider 指向远程沙箱，Bash / PTY / LSP 全部跟着搬过去，不需要每个 provider 各搞一个 fork。

§5 Session Log + event-sourcing 的工程价值

这一条值得单独说，因为它不是装饰：

  • 可恢复：崩了从日志重放，不用重跑 LLM
  • 可 fork：ctx.sessions.fork(source, boundary?, childSessionId?) 从某个边界点分叉
  • 可审计：所有权限切换、审批结果都进日志
  • 可分析：DSH 团队明确说，他们"开始系统化记录和分析 Agent 的执行过程"——这意味着 DSH 未来大概率会拿真实 agent run 做训练/评估数据（这才是真正的大招，跟 Codex 的方向一致）

代价：所有想进模型上下文的东西都强制走事件，绕过它会破坏不变性——所以扩展时不能"直接塞 message"，必须注册一个新的 SessionEvent 类型。

§7 关键 takeaway（你真要装的话）

  1. 安装 = 装 Node.js + npx @deepseek-ai/dsh web → 自动开 127.0.0.1:3080，填 API Key 就能用。源码跑：clone → pnpm install → pnpm run build → pnpm dsh web。
  2. 要做插件：在仓库打 dsh-plugin topic，社区在 Awesome 列表里收录（已有 300+）。
  3. 缓存命中率高得离谱：V4 Pro 缓存命中输入 $0.0145/M，测评里 99%+ 缓存命中率，4 个任务跑下来不到 ¥5。但 8-17 起涨价 50%-350%，分峰谷时段（高峰 9-12/14-18），用之前算账。
  4. 产品层还很早期——UI 偶发小 bug、工具链英文为主、个别场景上下文细节丢失（40 子 Agent 写 10w 字小说，主体连贯但局部规则漂移）。但架构层是稳的。
  5. v0.1 = Developer Preview，官方明示「接下来快速迭代过程中可能出现破坏性修改」。生产环境慎用。

Q1 · 主页面聊天框属于哪个插件？

答：跨 3 个包协作完成——不是"一个聊天框插件"这么简单。

三个角色

角色包职责
服务端表面 @deepseek-ai/dsh-web-app（bundle） 叠加在 dsh-base 之上，插入 Web host rows（webserver、API gateway、workspace、projection cache、storage）、浏览器插件 roster、dsh-client-hmr（dev mode HMR）；通过 web-runtime glue 插件解析 @deepseek-ai/dsh-web-frontend 的 dist
客户端前端 @deepseek-ai/dsh-web-frontend 浏览器里跑的前端 bundle，含客户端插件容器（client-side plugin roster）
聊天框节点 client-side 插件，通过 ConversationNodeDefinition + keyed renderer 注册到 conversation.chat.node 真正渲染输入框、消息流、工具块的 UI 节点

关键代码（来自 extension-cookbook 模板）

这就是一个"聊天 UI 客户端插件"的标准范式：

import type { Context } from '@deepseek-ai/cordis'
import { createUserMessage } from '@deepseek-ai/dsh-llm'
import { SessionId } from '@deepseek-ai/dsh-session'

export const name = 'my-ui'
export const inject = ['agents']

export function apply(ctx: Context) {
  // 1) 渲染：订阅 session 事件流
  ctx.on('session/event', (_session, event) => {
    if (event.type === 'assistant/chunk' &&
        event.data.chunk.type === 'text-delta') {
      render(event.data.chunk.text)   // ← 聊天框显示新文字
    }
  })
  // 2) 输入：用户敲回车 → 投递给 agent
  onUserInput(text =>
    ctx.agents.get(SessionId('client-session'))?.followup(
      createUserMessage({
        content: [{ type: 'text', text }],
        source: { kind: 'user' },
      })
    )
  )
}

关键洞察

  • 聊天框 ≠ 服务端的"聊天"插件——它跑在浏览器里，DSH 服务端只负责把 session/event 流通过 WebSocket 喂给它。
  • 每个 client-side 插件就是一个 apply(ctx)——你完全可以写一个自己的 client 插件替换掉默认的聊天 UI（这正是 dsh-tianshu-tui / dsh-deepcel / dsh-kun-like-pet 干的事）。
  • dsh-web-app 的 glue 插件（@deepseek-ai/dsh-bundle-web-app）负责把 built dist 路径解析出来挂到 webRuntime，并通过 printUrl 输出 dsh web: 的 URL。
  • HMR 是真的：dsh-client-hmr 一直挂着，重建 watcher 重写 client bundle 就会自动热更新——你改客户端插件代码不需要重启 DSH。

Q2 · AI 利用什么原理给 DSH 写插件？

答：4 层抽象 + 1 份"AI 协作宪法"（AGENTS.md）。

DSH 团队官方把仓库的 AGENTS.md 写成了"给所有 agent（包括 DSH 自己）写 dsh 插件的开发指南"。这本身就是答案的一部分。

第 1 层：声明式配置（YAML 装配，不是命令式注册）

不是"写 JS 调 register()"，而是写 YAML 描述插件的拓扑：

# cordis.yml (用户级 patch)
plugins:
  - name: my-plugin
    inject: [agents, tools]
    apply: !!js import('./my-plugin.mjs')  # !!js 标签是关键

cordis.yml 里的 !!js 标签是硬拦截——把 YAML 字符串解析为可执行代码引用。这是整个声明式 / 命令式边界的桥。

第 2 层：可注入 ctx 命名空间

插件拿到的 ctx 是个带类型的"魔法对象"，有 20+ 个注入点（ctx.llm、ctx.tools、ctx.agents…）。写插件 = 在这些 ctx 上注册 handler。

第 3 层：事件 + 副作用契约

AGENTS.md 第 18 条硬规则（原文）：

Registrations are effects: every contribution goes through ctx.effect() / ctx.on(); a registry's register() returns the disposer.

也就是：

  • 注册即副作用（effect）—— Cordis 维护一个 disposer 链
  • 卸载即反向触发——你不用写清理代码，effect 反向跑就行
  • waterfall 监听器必须调 next()—— agent/pre-step / agent/request / llm/stream / 三个 tools/* 是瀑布事件，不调 next() 直接截断

第 4 层：TypeScript 类型系统兜底

AGENTS.md 几条硬约束：

  • strict: true + noImplicitAny
  • Typed events use declaration merging and merge-extensible maps
  • 每个插件 module 必须有 JSDoc（verify-export-jsdoc 守门）
  • SessionEventMap 成员默认 required-on-read——构建期不知道的事件类型会被编译期拒收，加 ignorable: true 才行

给 AI 写插件的"原理"是什么？

不是让 AI"设计新架构"，而是给 AI 一张"这件事归这个 extension point"地图。architecture.zh.md 末尾有完整映射表（cookbook 也有）：

想做什么写到哪
添加模型在 ctx.llm 上注册 adapter（dsh-llm-deepseek / dsh-llm-pi-ai）
添加工具在 ctx.tools.register()，schema 自动入提示词
加 hook监听 agent/pre-step / tools/pre-execute 等 waterfall 事件
加 sub-agent在 ctx.subagents 注册 provider（dsh-subagent-fork/-codex/-claude-code/-dsh-sdk…）
加 UI 节点注册 ConversationNodeDefinition + keyed renderer
加 MCP server一个 server 一个插件，discover tools → ctx.tools.register()
加 Skillsection + tool 注册 + inject()
加 memorysection provider + tool
加定时任务插件注册 model-callable 工具，timer → followup(..., {source:{kind:'cron'}})

AI 写插件的实际工作流

AGENTS.md "Non-trivial changes MUST include an Agent Note in the same PR"：

  1. 读 docs/architecture.zh.md 找正确的 seam
  2. 找最相似的现有 dsh-tool-* / dsh-llm-* 包当模板
  3. 写 apply(ctx: Context) 主体
  4. 加 Agent Note（.agents/notes/implemented/... 解释这次改动）
  5. 加 snapshot test（docs/testing.md："keyless snapshot through a real runnable example"——必须真实跑）
  6. 跑 verify-cordis-config（loader 合法性）+ pnpm run test:coverage
  7. lefthook pre-push 自动跑 typecheck（包含 Typert 生成的 Host-for-Client Remote 契约）

一个反直觉的设计：AGENTS.md 是治理工具

CLAUDE.md symlink AGENTS.md 在根、packages/、examples/ 三层——编辑真文件，三处都生效。这不是给人类写的，是给所有 agent 写的协作宪法。

③ Capability Seam 三件套

每个能力 = Service Definition（接口）+ Service Provider（实现，可换）+ Consumer（使用方）。最有意思的 seams：

  • ctx.fs（文件）—— 改 fs 后端 = 改所有读文件的工具
  • ctx.subprocess（进程）—— 改 spawn = 改 Bash/PTY/LSP
  • ctx.sandbox —— 在启动进程前包装 argv
  • ctx.subagents —— 能委派给本机 Codex / Claude Code
  • ctx.llm —— 模型不绑死

④ 客户端 / Web 表面

  • Web Client Chat business node：ConversationNodeDefinition + conversation.chat.node keyed renderer
  • Client-side 插件容器：@deepseek-ai/dsh-web-frontend 内部的 client plugin roster
  • 协议驱动（protocol driver）：把 wire peer（stdio / JSON-RPC / WebSocket）适配到 ctx.agents，ACP 包是 worked example
  • MCP server 桥：one plugin per server

⑤ 装配层（profile / bundle / patch）

  • cordis.yml：loader config（支持 !!js 注入 JS 引用）
  • cordis.patch.yml：profile 级 patch（按 id 定位条目，替换整个 config）
  • --patch 命令行 overlay
  • package.json#dsh.profile / dsh.bundle 字段：声明"我是哪个 profile 的一层"或"我是个组合包"
  • agentCtx：把注册项限定到单个 agent 的 ctx

Q4 · 插件实现语言 + 为何能加载？

实现语言

官方主语言 = TypeScript（ESM everywhere）：

  • AGENTS.md 第 5 条硬规则：ESM everywhere ("type": "module")
  • 每个 npm 包名 = @deepseek-ai/dsh-<name>（vendored 包 rescope 且 private: true）
  • 源码 = .ts（开发时）+ 编译产物 = lib/*.js（运行时）
  • TypeScript 模式：@deepseek-ai/cordis 是每个 harness 包的 peerDependency
  • 严格 TS：strict: true + noImplicitAny
  • 测试：test:coverage（不是 test）才是 CI 覆盖门槛

配置语言

YAML + 嵌入 JS：

  • cordis.yml 顶层 loader config
  • cordis.patch.yml 用户级 patch
  • !!js 标签：在 YAML 字符串里嵌入 JS 引用（必须是 !!js，绝不能 !js——单叹号是 YAML 默认类型不安全行为，AGENTS.md 显式禁止）

Web Client 端

  • TS → 浏览器 ESM bundle（@deepseek-ai/dsh-web-frontend）
  • 双面构建：Host 编译（tsdown --env.DSH_BUILD_FACE host）→ Client 编译（tsc -b tsconfig.client.json + tsdown --env.DSH_BUILD_FACE client）→ pnpm run build:web
  • Typert：只在 Host tsdown 跑，分析 Host 类型生成 Host-for-Client Remote 投影（这是让 Browser 端能调 Host 方法的类型生成器，TS 自带做不到）

为何能加载？（4 步流程）

1. 用户跑：npx @deepseek-ai/dsh web ↓ 2. 启动器读 ~/.harness/home/<profile>/ 里的 profile 配置 → 按 dsh.profile 字段按顺序叠加组合包 → 应用 cordis.patch.yml → --patch overlay ↓ 3. Cordis 装载器遍历组合包： - 读 package.json#dsh.bundle 找到 patch 文件 - require.resolve 该包（通过 npm 依赖机制） - 取模块导出的 name / inject / apply - 在注入依赖后，把 ctx 传给 apply(ctx) ↓ 4. 插件 apply() 内部用 ctx.on('event', ...) / ctx.effect(...) → Cordis 维护 effect 链 + disposer → 卸载时反向触发

源码模式（dev 模式）

  • AGENTS.md 第 5 条：The dsh CLI source launch runs through tsx's ESM-only hook (node --import tsx/esm)——开发时直接跑 .ts，不用先编译
  • 这意味着 Node 的 native TypeScript modes（--experimental-strip-types 等）在引擎范围不可用（不同 Node 版本行为差异），统一走 tsx

理论上能用什么语言？

  • 必须产出 ESM（CJS-only 依赖禁止——AGENTS.md 显式说"modules it reaches must stay ESM"）
  • 任何能编译成 ESM 的语言理论上都可以：TS、JS、AssemblyScript（→ wasm）、Rust（→ napi-rs 或 wasmtime）……
  • DSH 显式只支持 TS，但 Node.js 的 loader hooks 留了扩展空间（社区理论上可以做）
  • Web Client 端因为是浏览器 ESM bundle，限制更死（基本就是 TS/JS + 浏览器 API）

Q5 · 插件化能力边界——什么 100% 不能做？

我从 5 个维度反推"硬限制"。这些是架构 + 治理 + 平台层面的，不可能绕过。

① 不变性硬限制（被 runtime invariant 兜住）

限制后果
Model-visible ⟺ logged任何想让模型看到的输入必须经 SessionEvent；想"绕过日志直接给模型塞私有上下文"——做不到，运行时断言会拒收
Sessions forking / replaying派生自事件流，不能伪造"假装模型没看到过"
SessionEventMap required-on-read编译期拒收未知事件类型，治理你想塞进会话的"自定义消息"路径
SESSION_FORMAT_VERSION bumping改会话格式 = 破坏所有历史，治理层卡死

② 架构治理硬限制

限制后果
Plugins, not loop changes改 agent-loop 行为必须同步更新 docs/architecture.md，否则 PR 被驳回；新行为必须挂在 documented extension points
改 Cordis 微内核本身必须改主仓（DSH 是 DeepSeek 官方项目，你 fork 不了治理规则）
能力事件 seam 锁定只能监听现成的 fs/* / tools/* / telemetry/* / llm/stream，不能发明新事件域（除非 PR 进主仓）
waterfall 监听器必须 next()监听 agent/pre-step 但不调 next() 会截断——你不能"偷看"中间状态但卡住后续；agent/turn-stopping 是 serial 事件，根本没 next()——不能无限延迟停轮

③ 平台硬限制

限制后果
ESM everywhere不能引入 CJS-only 包
TypeScript strictnoImplicitAny 不放过；每个 module/exports 必须 JSDoc（verify-export-jsdoc 守门）
@deepseek-ai/cordis peerDependency必须用官方 Cordis，不能塞自己的 IoC 容器
Node.js 版本必须支持 Node 22.19/24/26 矩阵（CI 跨版本验证）
Web App 拒绝 0.0.0.0监听所有接口 = 显式被 webStartup 拒绝（DSH CLI 还不支持 all-interfaces）
LAN 信任只 boot 时采样interface 变化不重新公告；不能动态信任
Frontend dist 必须先 build没有源码服务 fallback（pnpm run build 之后才能跑 web）

④ 沙箱安全硬限制

限制后果
workspace-write sandbox默认只能动工作区 + 允许的临时目录；跑 command 要审批（ctx.approval）
ctx.sandbox 后端在启动进程前包装 argv你想跑 rm -rf / = 沙箱先拒；插件绕不过
tools/pre-execute 返回 ask 才进审批想静默执行越权操作 = 做不到

⑤ 模型本身的能力天花板

DSH 解决执行层，不解决模型能力。所以以下 100% 做不到（不是 DSH 限制，是模型限制）：

  • V4 Pro 是纯文本模型——不直接看图（社区插件 modlens 用 OCR + 视觉模型补）
  • 1M 上下文硬上限（精确 2^20 = 1,048,576 tokens）——超 = HTTP 400
  • DeepSWE 基准 8%（vs GPT-5.5 70%）——某些场景下模型本身就做不出来，跟 DSH 无关
  • 视频多模态准确率下降（>60 秒视频）——模型问题
  • 工具调用结构化输出偶发格式漂移——模型问题

总结：硬限制的"理论边界"图

┌─────── 改 Cordis 内核 ───────┐ ✗ 改主仓 │ ── 发明新事件域 ── │ │ ── 改 Agent Loop 不动文档 ── │ ✗ 治理 │ ── CJS-only 包 ── │ ✗ 平台 100% 不能做 ────┤ ── 绕过 SessionLog ── │ ✗ 不变性 │ ── 0.0.0.0 all-interfaces ── │ ✗ 安全 │ ── 跑越权命令不审批 ── │ ✗ 沙箱 │ ── V4 Pro 直接看图/视频 ── │ ✗ 模型 │ ── SESSION_FORMAT 自由改 ── │ ✗ 兼容 └──────────────────────────────┘ ┌─────── 加自己的模型 ────────┐ ✓ ctx.llm │ ── 加自己的工具 ── │ ✓ ctx.tools │ ── 加自己的 hook ── │ ✓ agent/* 100% 能做 ──────┤ ── 加自己的 UI 节点 ── │ ✓ ConversationNode │ ── 加自己的 MCP server ── │ ✓ one plugin │ ── 委派子 agent 给 Codex ── │ ✓ ctx.subagents │ ── 换整个 Agent Loop ── │ ✓ 改 docs └──────────────────────────────┘
