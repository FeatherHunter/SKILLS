ask-matt · 路由器型 技能的设计原理

Router over skills · "我不知道该用哪个 — 那就问"

01 文件清单与构成

ask-matt 是整个仓库里文件最少的技能之一 —— 总共只有一个 SKILL.md 和一个 agent 配置。少,是因为它本身不解决问题,只解决"我该用哪个 skill"。

ask-matt/
├── SKILL.md ← 78 行,核心路由文档,定义七大类技能拓扑
└── agents/
    └── openai.yaml ← Codex CLI agent 配置:display_name + allow_implicit_invocation:false

SKILL.md 关键元数据

name
ask-matt
description
"Ask which skill or flow fits your situation. A router over the skills in this repo."
disable-model-invocation
true — 模型不能自动加载,只能用户显式触发

openai.yaml 的设计含义

interface:
  display_name: "Ask Matt"
  short_description: "Find the right skill or workflow"
policy:
  allow_implicit_invocation: false  ← 显式触发,不能被模型推理时自动拉起

allow_implicit_invocation: false 表达了一个非常重要的产品决策:这个技能是"用户主动求助",不是"模型自动调度"。如果你让模型自己决定什么时候调用 ask-matt,它会没事就问一遍 —— 噪声太大。把它锁成显式入口,用户只有在"我真的不知道该用啥"时才召唤它。

02 七大类别 — 整张路由地图

SKILL.md 用七个标题把 22 个技能组织成一张拓扑图。这不是按"功能相似"分的,而是按"在哪个阶段被触发"分的。

04 Smart Zone — 上下文窗口的安全区

第 32 行引入了一个非常硬核的概念:smart zone。Matt 引用了 aihero.dev 的定义,把上下文窗口分成能推理清楚的区段和已经退化的区段。

0 tokens
SMART ZONE · ~120k
DEGRADED · 模型开始胡说

规则:步骤 1–3 必须留在一个完整的上下文窗口里(grill-with-docs → to-tickets),不要中途 compact。
一旦快到 smart zone 上限 → /handoff 写到文件,在新会话里继续。

★ 设计哲学

这条规则不是元数据,是 ask-matt 强制写入流程的硬约束。把"什么时候该换会话"从经验变成规则,新手也能照着做。

06 三种"跨会话"工具 — 它们的本质差异

SKILL.md 在 "Crossing sessions" 一节对比了三种"上下文穿越"工具:

工具 走向 历史保留 适用场景
handoff 分叉 · 写文件 + 开新会话引用 完整 markdown 落盘 进入 /prototype 这种需要干净上下文的支线
compact 续写 · 内置摘要 被压成 summary,原文丢失 阶段间有意暂停时
新会话 清零 · 不带历史 无 完全无关任务(慎用)
★ 设计哲学

"Don't compact mid-phase — the agent can lose its way" 是这条对比最关键的告诫。阶段内不要 compact,因为模型会在收尾时引用已经被摘要掉的上下文,产生幻觉。

07 为什么 ask-matt 是 router 而不是 monolith

单一职责原则

ask-matt 自己不做任何实际工作。它不读代码、不写代码、不调试。它只回答一个问题:"这种情况,我应该叫谁?"。这让它可以被随时打断、随时替换。

声明式而非命令式

SKILL.md 用大量"if X then Y"句式,而不是"先做 X 再做 Y"。这是 router 的典型写法 —— 表达的是决策拓扑,不是执行流。模型自己根据当前状态决定走哪条分支。

元数据里埋钉子

disable-model-invocation: true 和 allow_implicit_invocation: false 这两条配置互为冗余,是为了适配两个不同的平台(Claude Code 用 frontmatter,Codex 用 YAML)。同一个意图,在两个不同配置里都写了 —— 这就是 跨平台 skill 设计 的典型手法。

决策树用文字而非代码

整篇 SKILL.md 没有一行可执行代码。这是有意的:模型读 markdown 比读代码更准,文字里的"if/then"反而比 if-else 链更稳。

flow / on-ramp / vocab · 三层抽象

它把 22 个技能压成三个层次:

  • flow(主流程) — 用户大部分时间走的路
  • on-ramp(上路匝道) — 突发事件汇入主流程的入口
  • vocabulary(词汇底层) — 被其他技能默默引用的术语层

这种分类本身就是一份心智模型(Mental Model),让用户能"看图选路"。

09 启发 — 我们可以抄什么?

★ 给 Skill 作者的启示

1. 不要把 router 写厚:它越短,用户越敢用。
2. 分类优于罗列:把同质技能压成"flow / on-ramp / vocab"三层,而不是 22 个并列项。
3. 禁掉模型自调用:router 不该是模型脑补出来的。
4. 写"何时不用我":SKILL.md 第 40 行写明 "don't triage tickets /to-tickets produced" —— 边界比功能更重要。
5. 把经验升格为规则:"smart zone ~120k" 是个数字,但它把"何时 compact"从玄学变成可执行判断。
