02 核心设计 · 两轴独立 + 并行 sub-agent

为什么要拆两轴?

SKILL.md 第 82 行起的 "Why two axes" 是整篇的灵魂。一个提交可能:

Standards 轴
PASS
符合 CODING_STANDARDS.md
Spec 轴
FAIL
issue 问的是 A,代码做的是 B
↑ "守规矩地做错了事" — 最常见的失败模式,却最容易被合并 ↑
Standards 轴
FAIL
代码风格违反项目规范
Spec 轴
PASS
功能 100% 对应 issue 要求
↑ "做对了事但很丑" — 快完成时容易妥协放行 ↑
★ 设计哲学

合并成一个分数会让一轴掩盖另一轴。"Standards 9 分 + Spec 3 分 = 平均 6 分"这种总结掩盖了 Spec 已经完蛋的事实。两轴分开报告,既不掩盖,也不做跨轴排序。

为什么并行?

SKILL.md 第 11 行明确说:"并行运行,避免互相污染上下文"。两个 sub-agent 互相看不到对方报告,所以不会因为 Standards 那边的 5 个小问题下意识把 Spec 的关键缺失稀释掉。这是用架构隔离偏见。

03 5 步流程

1 Pin the fixed point
用户给一个 commit / branch / tag → git diff <fp>...HEAD (三 dot,merge-base 对比)
先 git rev-parse 验证 + diff 非空,失败要在 sub-agent 之前拦住
2 Identify the spec source
查找 spec 来源,优先级: commit 引用的 issue → 用户传的路径 → docs/specs/.scratch/ → 问用户
没有 spec → Spec sub-agent 跳过,最终报告注明
3 Identify standards sources
仓库里任何"代码该怎么写"的文档(CODING_STANDARDS.md 等)
叠加 12 项 smell 基线(Fowler Refactoring ch.3),仓库规范优先于基线
4 Spawn both sub-agents in parallel
单条消息 + 两个 Agent tool call · general-purpose sub-agent
Standards sub-agent: 拿 diff + 仓库标准 + smell 基线 → 报告违规/可疑处
Spec sub-agent: 拿 diff + spec → 报告缺失/越权/错位
双方都要求 < 400 words
5 Aggregate
## Standards 和 ## Spec 两节,原文或轻度清理
不合并 / 不重新排序 — 这是分离存在的意义
末尾一行汇总:每轴的发现数 + 最严重一项,但不挑跨轴冠军

04 12 项代码味道 · Smell Baseline

这一段是 SKILL.md 第 38–56 行最厚的部分。Matt 引用 Fowler《重构》ch.3 的 12 个 smell,把它们当成"仓库零文档时也必须执行的最低标准"。

关键规则 (第 40–41 行):
① 仓库规范永远覆盖基线 — 仓库白名单说"允许",基线就要闭嘴
② 始终是 judgment call — 每个 smell 都标 "(可能)",不是硬性违规
③ 跳过工具已经强制的事 (比如 lint 已经拦的格式问题)
Mysterious Name
函数/变量/类型名看不出做什么或装什么
改名;想不出诚实名字 → 设计本身含糊
Duplicated Code
同一逻辑形状出现在多个 hunk / 文件
抽出共享形状,两边都调它
Feature Envy
方法伸手去拿别人对象的数据多于自己的
把这个方法挪到被羡慕的对象上
Data Clumps
同样几个字段/参数总是一起出现(一个类型想出生)
打包成一个类型,传这一个
Primitive Obsession
用原始类型/string 顶替一个本应有自己类型的领域概念
给概念一个小类型
Repeated Switches
同一个 type 的 switch / if 级联在多处出现
换成多态,或两处共享一张 map
Shotgun Surgery
一个逻辑改动要散弹式改许多文件
把总是一起改的东西聚成一个模块
Divergent Change
一个文件/模块为几个无关理由反复修改
拆开,让每个模块只为一个原因变
Speculative Generality
为 spec 没要求的需求提前加抽象/参数/钩子
删掉;真有需求时再 inline 回来
Message Chains
很长的 a.b().c().d() 链,调用方不该知道
把这条链藏到第一个对象的一个方法里
Middle Man
类/函数基本只是继续往下委托
干掉,直接调真正的目标
Refused Bequest
子类/实现方忽略或覆写继承下来的大部分
丢掉继承,改用组合

06 三层"先决条件"的兜底

SKILL.md 在多个地方都埋了"前置失败就停"的检查:

阶段兜底检查为什么
启动 docs/agents/issue-tracker.md 存在? 没装就跑 /setup-matt-pocock-skills,避免 sub-agent 找不到 spec 来源
第 1 步 git rev-parse <fixed-point> + diff 非空 "bad ref or empty diff should fail here — not inside two parallel sub-agents"
第 2 步 spec 来源按优先级回溯 → 找不到就问用户 用户说"没有 spec" → Spec sub-agent 跳过 + 报告注明,而不是编造
第 3 步 仓库标准 > smell 基线 仓库白名单豁免,基线让位
★ 关键设计哲学

"A bad ref or empty diff should fail here — not inside two parallel sub-agents."
翻译:失败要发生在昂贵的事开始之前。sub-agent 调用贵、慢、可能误导结果。一次性 git rev-parse 就能挡住的失败,绝不能让它溜进 sub-agent。

07 12 smell 的"判定哲学"

每个 smell 都是 heuristic,不是 rule

SKILL.md 第 41 行写得很死:"Always a judgement call. Each smell is a labelled heuristic ('possible Feature Envy'), never a hard violation"。

三层优先级

  1. 工具强制层(lint / typecheck / formatter) — 直接跳过,sub-agent 不要再报一遍
  2. 仓库文档层(CODING_STANDARDS.md) — 硬违规,必须 cite file + rule
  3. Smell 基线层(Fowler 12 项) — judgment call,必须标 "possible"

"what → fix" 双行结构

每个 smell 的描述都是两行:

**Mysterious Name** — [what it is]
→ [how to fix it]

这迫使 sub-agent 不光指出问题,还得知道怎么救。把"识别 + 修复"绑定,避免出现"指出 smell 但不告诉怎么改"的尴尬。

08 关键设计模式

Two-Axis Independence · 双轴独立
把"代码好不好"和"代码对不对"拆成两个独立 sub-agent,互不通信。聚合时不跨轴排序。
避免一轴掩盖另一轴;避免 reviewer 用"风格 9 分"稀释"功能 3 分"的警报
Sub-Agent as Scoped Worker
主 skill 只负责协调,所有真活都外包给 general-purpose sub-agent。Skill 自己不读 diff、不写报告。
让 skill 文件保持 < 100 行;让 sub-agent 各自拥有干净的上下文
Fail-Fast Gating · 前置失败拦截
昂贵的 sub-agent 调用前,用便宜的 git rev-parse / diff -q / 文件存在性检查先行。
省时、省 token、避免 sub-agent 拿到坏输入后产出误导结论
Layered Authority · 三层优先级
工具强制 > 仓库文档 > smell 基线。每一层都用自己的标注(hard / judgement / possible)。
避免双标(同一问题两套规则);让 reviewer 知道哪条是死的哪条是软的
Baseline Always On · 永远存在的基线
仓库即便没有任何文档,12 smell 基线也会跑。仓库文档只能豁免,不能覆盖。
保证零文档项目也能被审查;让标准有下限
Spec Resolution Hierarchy · Spec 来源回溯
按 4 级优先级找 spec 来源:commit 引用的 issue → 用户传的路径 → docs/specs → 问用户。找不到就明确跳过,不编。
让 Spec 轴"诚实地说我不知道",比假装审过更可信
Word Budget on Sub-Agent
两个 sub-agent 都被显式要求 "Under 400 words"。
逼 sub-agent 摘要;省 token;逼着只报最有价值的问题

09 启发 — 我们可以抄什么?

★ 给 review 流程设计的启示

1. 评审要拆维度:一次只审一个轴,合并 = 掩盖。
2. 主 skill 是协调器,不是执行器:把重活外包给 sub-agent,自己只做调度。
3. 先 git rev-parse 再 sub-agent:挡在贵的事前面。
4. 永远有兜底基线:仓库零文档也能评审。
5. smell 要带 fix:只说"这有 smell"不够,要说"改成这样"。
6. heuristic 必须标 "possible":不让模型把判断当判决。
