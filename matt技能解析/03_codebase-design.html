为什么是 3 个文件而不是 1 个?

SKILL.md 第 14 行写得很清楚:"Consistent language is the whole point."。三个文件是同一套词汇的不同用法面:

  • SKILL.md = 词汇定义(module / interface / seam / adapter / depth / leverage / locality)
  • DEEPENING.md = 词汇用法 1:遇到一个浅模块,怎么把它加深
  • DESIGN-IT-TWICE.md = 词汇用法 2:第一次设计的接口大概率不是最好的,并行 sub-agent 拉几个出来比一比
★ 设计哲学

这个技能自己不解决任何问题,只提供一套统一的术语表。
它被 tdd / improve-codebase-architecture / code-review 默默引用,保证这些技能讨论"深度"时用的是同一个意思。

02 词汇表 · 7 个核心术语

SKILL.md 第 14–29 行定义 7 个术语。每个术语都附带"不要用 XX 代替"的禁令 —— 这就是"consistent language"的执行机制。

Module · 模块
任何有 interface + implementation 的东西。故意 scale-agnostic:函数 / 类 / 包 / 跨层切片都行。
unit, component, service
Interface · 接口
调用方需要知道的一切:类型签名 + 不变式 + 顺序约束 + 错误模式 + 必要配置 + 性能特征。
API, signature(太窄,只指类型层)
Implementation · 实现
模块里的代码。注意和 Adapter 区别:一个东西可以是"小 adapter + 大 implementation"(PG repo),或"大 adapter + 小 implementation"(in-memory fake)。
—
Depth · 深度
接口处的杠杆率:调用方(和测试)每学 1 单位接口能驱动多少行为。模块 deep = 小接口后藏着大行为;模块 shallow = 接口和实现一样复杂。
—
Seam · 接缝
(Michael Feathers)可以不改这一处就改变行为的地方 —— 模块 interface 居住的位置。位置是独立的设计决策。
boundary(与 DDD bounded context 冲突)
Adapter · 适配器
在 seam 处满足 interface 的具体东西。描述角色(填哪个槽),不描述实体(里面是什么)。
—
Leverage · 杠杆
深度给调用方带来的好处:每学 1 单位接口获得更多能力。1 个实现给 N 个调用点和 M 个测试付账。
—
Locality · 内聚性
深度给维护者带来的好处:变更 / bug / 知识 / 验证都集中在一处,而不是散在调用方。改一次修好所有地方。
—
★ 设计哲学

"Avoid: API / signature / boundary" 这类禁用清单是这个词汇表的灵魂。语言决定思维 —— 用 boundary 你就会把 module 想成 DDD 的 bounded context;用 seam 你就会想"在哪里切开"。

03 Deep vs Shallow · 视觉对比

SKILL.md 第 30–58 行用 ASCII 图直接画出两种模块。让我把它做成可交互对比:

✅ Deep Module · 深度模块

小接口 + 大行为 = 杠杆率高,所有调用方受益

❌ Shallow Module · 浅模块

大接口 + 小实现 = 杠杆率低,只是封装了一层

04 4 大原则 · The Principles

① Depth is a property of the INTERFACE, not the implementation
深模块的内部可以由小而可 mock 的部分组成 —— 但它们不是 interface 的一部分。模块可以有 internal seams(私有,只供自己测试用),也可以有 external seam(在 interface 处)。
② The Deletion Test · 删除测试
想象删除这个模块。如果复杂度消失 → 它是 pass-through,该删。如果复杂度在 N 个调用方那里复现 → 它确实有价值。
③ The interface is the test surface · 接口就是测试面
调用方和测试跨越同一条 seam。如果你想测"越过 interface",说明模块形状错了。
④ One adapter = hypothetical seam. Two adapters = real seam.
除非确实有变化跨越它,否则不要引入 seam。一个 adapter 的 seam 只是间接层。

05 4 类依赖 · 决定怎么测

DEEPENING.md 第 5–25 行定义了 4 类依赖。每类的测试策略不同。

In-process永远可深化

纯计算、内存状态、无 I/O。

→ 直接合并模块,通过新 interface 测。无需 adapter。
Local-substitutable本地可替代

依赖有本地测试替身(PGLite 替 Postgres、in-memory FS)。

→ 替身存在即可深化。用替身在测试套件里跑。seam 是 internal,不在 external interface。
Remote but owned自有远程

自己的服务跨网络(微服务 / 内部 API)。

→ 在 seam 定义 port。深模块持有逻辑,transport 作 adapter 注入。测试用 in-memory adapter,生产用 HTTP/gRPC/queue adapter。
True external真外部

你不能控制的第三方(Stripe / Twilio)。

→ 深模块把外部依赖当作注入的 port接受;测试提供 mock adapter。
★ 设计哲学

4 类不是等级,而是测试手段不同。In-process 永远可深化,但 external 永远需要 mock — 你不能测 Stripe 真的扣你信用卡。这种"可行性矩阵"的写法,比"按场景分"更可执行。

06 Replace, Don't Layer · 测试策略

DEEPENING.md 第 32–37 行有一条很反直觉的测试规则:

替换,不要叠加

  • 旧的对浅模块的单测,在深模块 interface 测试存在之后 → 是废品,删掉
  • 新测试写在深模块的 interface 处
  • 测试断言通过 interface 观察到的结果,不验内部状态
  • 测试应该活过内部重构 —— 它们描述行为,不是实现

⚠️ 如果一个测试在实现改变时也必须改,那它测过了 interface。

07 Design It Twice · 并行 sub-agent 探索

DESIGN-IT-TWICE.md 第 19–39 行给出一个极端的做法:用 3+ 个并行 sub-agent 各自给出"激进不同"的接口方案。

Agent 1 · 极简派
"Minimize the interface — aim for 1–3 entry points max. Maximise leverage per entry point."
目标:每个入口点杠杆率最大
Agent 2 · 灵活派
"Maximise flexibility — support many use cases and extension."
目标:支持多种用例 + 扩展
Agent 3 · 默认派
"Optimise for the most common caller — make the default case trivial."
目标:最常见调用方零摩擦
Agent 4 · Ports派
"Design around ports & adapters for cross-seam dependencies."
目标:跨 seam 依赖用 ports & adapters

每个 sub-agent 必须输出 5 件事

  1. Interface — 类型、方法、参数 + 不变式、顺序、错误模式
  2. Usage example — 调用方怎么用
  3. Implementation 藏在 seam 后面
  4. Dependency strategy + adapters(DEEPENING.md 分类)
  5. Trade-offs — 杠杆高在哪、低在哪
★ 设计哲学

DESIGN-IT-TWICE 的核心论断:"你第一个想法几乎从来不是最好的"。所以并行拉 3+ 个方案,在 depth / locality / seam placement 三个维度上对比。
最后主控要给出有立场的推荐,不是菜单 —— "the user wants a strong read, not a menu"。

08 拒绝的 framing · "Rejected"

SKILL.md 第 105–110 行专门列了一个"被拒绝的框架"清单 —— 告诉你不要用什么:

被拒绝为什么不
Depth = 实现行数 / 接口行数(Ousterhout) 奖励"灌水 implementation"。我们用 depth-as-leverage 替代。
"Interface" = TS interface 关键字 或 public 方法 太窄。interface 包含所有调用方需要知道的事实。
"Boundary" 和 DDD bounded context 撞词。改说 seam 或 interface。

09 关键设计模式

Vocabulary-as-Skill · 词汇即技能
技能不解决问题,只提供统一术语。被其他技能(tdd / improve-codebase-architecture / code-review)默默引用。
Avoid-List · 禁用清单
每个术语都附 "Avoid: 替代词"。强制词表统一,避免"boundary" / "interface" / "API" 这些被滥用的词造成歧义。
Glossary + Methodology + Comparison 三文件
SKILL.md = 词汇表 · DEEPENING.md = 方法论 · DESIGN-IT-TWICE.md = 比较模式。3 文件分 3 角色,而不是塞一个长文件。
Feasibility Matrix · 可行性矩阵
4 类依赖按"能否深化 + 怎么测"分类,提供一张可查的表。
Replace-Don't-Layer · 替换不要叠加
深化后,旧的浅模块测试直接删。不让旧测试和新测试并存造成"两层保险"的假象。
Seam Discipline · 接缝纪律
1 adapter = 假设的 seam · 2 adapter = 真正的 seam。强迫"接缝"必须有实在变化支撑。
Three-Dimension Comparison · 三维度对比
多个方案在 depth / locality / seam placement 三个维度对比,然后给出有立场的推荐。

10 启发 · 我们可以抄什么?

★ 给词汇体系设计的启示

1. 技能可以是词汇:不解决问题的技能有价值,如果它提供统一术语。
2. 每个术语配禁用清单:只定义不够,要禁止"差不多但不一样"的词。
3. 3 文件分 3 角色:glossary / methodology / pattern,而不是一个长文件。
4. 测试要"能活过重构":测实现 = 失败,测行为 = 成功。
5. 设计要"做两遍":第一个想法从来不是最好的,并行拉多个方案再对比。
6. 推荐要有立场:"strong read, not a menu"。
