02 6 阶段时间线

Phase 1 · Build a feedback loop
整个技能的核心。其他阶段都是机械执行。
SKILL.md 第 14 行原话:"This is the skill. Everything else is mechanical."
如果你对这个 bug 有一个紧的 pass/fail 信号,二分会/假设/插桩都只是消化这个信号。
没有信号,瞪再多代码也救不了你。
Phase 2 · Reproduce + minimise
让 loop 跑红,然后剪到最小。
一刀一刀剪 inputs/callers/config,每次剪完跑一遍 loop —— 只留承重的部分。
最小 repro 会成为 Phase 5 的回归测试。
Phase 3 · Hypothesise · 生成 3-5 个 ranked 假设
单一假设会锚在"第一个看起来合理"的想法。
每条假设必须 falsifiable:
格式:"如果 X 是因,改 Y 会让 bug 消失 / 改 Z 会让它加重"。
排完序先给用户看 —— 他们常有一票否决的领域知识。
Phase 4 · Instrument
每个探针映射到 Phase 3 的具体预测。
工具偏好:Debugger/REPL > 边界日志 > 永远不"全打日志再 grep"。
每个 debug 日志带唯一前缀 [DEBUG-a4f2],清场时一条 grep 搞定。
Phase 5 · Fix + regression test
先写测试,再写修复 —— 但只在有正确 seam 时。
"If no correct seam exists, that itself is the finding."
没有能锁定 bug 的 seam,是架构问题,不是测试问题。
Phase 6 · Cleanup + post-mortem
完成前 checklist + 反向追问"如何预防"。
5 项硬性清理:原始 repro 不再复现 + 回归测试 pass + [DEBUG-*] 全删 + 一次性原型删 + 假设写进 commit。
然后问"什么本可以预防这条 bug"。如果是架构问题 → hand off 给 /improve-codebase-architecture。
★ 阶段 1 的特殊地位

SKILL.md 第 14 行用一句极不寻常的话标注 Phase 1:"This is the skill."
它把所有 6 阶段当成 1 个框架,但把 90% 的力气压在唯一不可替代的那一步 —— 构造一个红得起来的 feedback loop。
其他 5 个阶段再多理论也比不上一条 pytest test_bug.py 跑得红。

03 Phase 1 详解 · 10 种 Feedback Loop

SKILL.md 第 18–29 行按推荐顺序列出 10 种构造方法。从最便宜的失败测试,到最后的 HITL bash。

① 首选
Failing test
unit / integration / e2e 任一 seam 上能写测试,就写
②
Curl / HTTP script
对着跑着的 dev server 跑 curl
③
CLI invocation + diff snapshot
fixture 输入,stdout 和已知好快照 diff
④
Headless browser
Playwright / Puppeteer 驱动 UI,断言 DOM/console/network
⑤
Replay captured trace
真实网络请求 / payload / event log 落盘,隔离重放
⑥
Throwaway harness
只起一个服务、mock 依赖,单函数调用直达 bug 路径
⑦
Property / fuzz loop
"有时输出错"就 1000 次随机输入,找失败模式
⑧
Bisection harness
bug 出现在两个状态之间 → 自动化"启动状态 X,检查,重复"
⑨
Differential loop
同输入跑老版本 vs 新版本, diff 输出
⑩ 末路
HITL bash script
人工必须点击 → 用 scripts/hitl-loop.template.sh 把他们驱动起来

hitl-loop.template.sh 怎么用

# 模板(第 17-27 行)给出两个 helper:
step "instruction"          → 展示指令,等待 Enter
capture VAR "question"      → 展示问题,把回答写入 VAR

# 用户编辑中间的 step/capture,然后:
$ bash hitl-loop.sh
>>> Open the app at http://localhost:3000 and sign in.
    [Enter when done] 
>>> Click the 'Export' button. Did it throw an error? (y/n)
    > y
>>> Paste the error message (or 'none'):
    > TypeError: ...
--- Captured ---
ERRORED=y
ERROR_MSG=TypeError: ...

捕获的值以 KEY=VALUE 输出,agent 可以直接解析 —— 让"人类点击"也能变成结构化数据。

04 Tightness · Loop 的 4 项硬指标

SKILL.md 第 53–59 行给出 Phase 1 的完成标准。一个 loop 必须同时满足 4 项才能算"tight":

RED-CAPABLE
能驱动真实的 bug 代码路径,断言用户描述的确切症状。修复后能从红变绿。
⚠️ 不是"不报错" —— 必须能逮住这个具体的 bug。
DETERMINISTIC
每次跑同一个判定。Flaky bug:钉一个高复现率(见下面 50%/1% 的对比)。
FAST
秒级,不是分钟级。30 秒的 flaky loop 比没 loop 好一点点;2 秒的确定 loop 是调试超能力。
AGENT-RUNNABLE
无人值守可跑。人类在环只能通过 hitl-loop.template.sh。
第 60 行原话:
"If you catch yourself reading code to build a theory before this command exists, stop — jumping straight to a hypothesis is the exact failure this skill prevents."
没有 red-capable 命令 → 没有 Phase 2。

05 不可复现 bug · "提升复现率"

SKILL.md 第 44–45 行对非确定性 bug 给了一个反直觉的目标:

目标不是干净的 repro,而是更高的复现率。

把触发器循环 100 次,加并行、加压力、缩小时间窗、注入 sleeps。
50% 的 flake 可调试,1% 的不能 —— 一边调一边把复现率拉到能调试为止。

06 Phase 3 · Falsifiable Hypothesis

SKILL.md 第 86–91 行要求每个假设都能被证伪。

格式: "If <X> is the cause, then <changing Y> will make the bug disappear
       / <changing Z> will make it worse."

例: If caching is the cause, then disabling cache will make it disappear;
    if it's a race, then injecting sleep will make it worse.

三个关键约束

  1. 3-5 个 ranked —— 不是 1 个,不是 10 个
  2. 必须能 falsify —— "我赌这条",而不是"也许是那条"
  3. 先给用户看 —— 用户的领域知识可能瞬间重新排名,或者他们已经排除过几条

如果用户 AFK,主控用自己排的顺序继续。

07 Phase 5 · "没有 Seam 本身就是发现"

SKILL.md 第 110–114 行有一段非常关键的判断逻辑:

原文:
"A correct seam is one where the test exercises the real bug pattern as it occurs at the call site.
If the only available seam is too shallow ... a regression test there gives false confidence.
If no correct seam exists, that itself is the finding."

翻译过来:没有能锁定 bug 的测试位,本身就是测试报告里最重要的一项发现。这是用 bug 当架构探针 —— bug 找不到 seam,说明代码结构有问题。这种情况下要 flag 给 Phase 6 的 post-mortem,转给 /improve-codebase-architecture。

08 Phase 6 · Post-Mortem Checklist

SKILL.md 第 126–134 行的 checklist 是强制的:

检查项目的
原始 repro 不再复现重新跑 Phase 1 的 loop
回归测试通过(或者没 seam 已被记录)保护未来
所有 [DEBUG-...] 已删除一条 grep 搞定
一次性原型已删别留垃圾
正确假设写进 commit / PR message下一个调试者能学

"什么能预防这条 bug?"

这是 SKILL.md 第 134 行末尾的反问:"Make the recommendation after the fix is in, not before — you have more information now than when you started."
修复完之后再建议架构改动 —— 因为这时候信息最完整。

09 关键设计模式

Feedback-First Diagnosis · 反馈优先
不是"先读代码想理论",而是"先造一个能红起来的 loop"。Phase 1 被升格为整个技能的核心。
10 Loops Escalation · 10 种升级路径
从最便宜的"失败测试"开始,逐级升级到 HITL bash。给 agent 一条穷举式的"我还有什么办法"路径。
4-Criteria Tightness · 4 项硬指标
loop 必须同时满足 red-capable / deterministic / fast / agent-runnable 才能进 Phase 2。把"好 loop"量化为可勾选项。
Reproduction Rate Maximisation · 复现率最大化
对 flaky bug,目标不是"消除不确定性",而是"提升到能调"。50% 可调试,1% 不能。
Falsifiable Hypothesis · 可证伪假设
每个假设必须能用一句 "If X, then Y" 表达。不让 vibe 充当理论。
Debug Log Tagging · 日志前缀打码
所有 debug 日志带唯一前缀 [DEBUG-a4f2],清场一条 grep。
Seam-as-Finding · 缺失 Seam 即发现
找不到能锁定 bug 的测试 seam 是架构问题,不是测试问题。bug 当作架构探针。
Post-Mortem Architecture Hand-off
修复完之后,反向问"如何预防"。若是架构问题 → hand off 给 /improve-codebase-architecture。

10 启发 · 我们可以抄什么?

★ 给 debug 流程的启示

1. 反馈 loop 比理论重要:先有红,再说为什么红。
2. loop 要"tight":四象限定 red-capable / deterministic / fast / agent-runnable。
3. 假设要可证伪:"If X then Y" 一句话能讲清。
4. debug 日志要打码:带前缀,清场一次搞定。
5. flaky bug 不是要消除,而是要提升复现率:50% 可调试,1% 不能。
6. 没 seam 本身就是发现:bug 当架构探针。
7. 在 fix 之后再建议架构改动:信息最完整时再判断。
