02 关键边界 · "主动" vs "消费"

SKILL.md 第 8 行用一段极重要的澄清划清边界:

"This is the active discipline — challenging terms, inventing edge-case scenarios, and writing the glossary and decisions down the moment they crystallise."

"Merely reading CONTEXT.md for vocabulary is not this skill — that's a one-line habit any skill can do. This skill is for when you're changing the model, not just consuming it."

翻译:domain-modeling 不是"读一下 CONTEXT.md",那是任何 skill 都能做的习惯。这个技能只在改变模型时被召唤 —— 提出新术语、澄清模糊概念、写决策记录。

★ 设计哲学

这条边界写得很死,因为模型被消费时不需要这个技能;只有模型在被修改时才需要。把"读"和"改"分开,让模型 invocation 次数收敛到真正必要的时刻。

懒创建原则

SKILL.md 第 40 行:"Create files lazily — only when you have something to write."

  • 没 CONTEXT.md → 等第一个术语解决时创建
  • 没 docs/adr/ → 等第一个 ADR 需要时创建

这是避免空文件的纪律 —— 没东西写就别建文件,免得空文件演变成"假装存在"的幻觉。

04 5 个会话期行为

SKILL.md 第 42–67 行给出 5 个具体动作,任何对话中遇到就触发:

1
Challenge against the glossary
当用户用到的术语和 CONTEXT.md 冲突时,立即指出来。
"你的 glossary 定义 cancellation 为 X,但你似乎说 Y —— 哪个对?"
2
Sharpen fuzzy language
当用户用模糊或过载的词时,提出精确的标准术语。
"你说 account —— 指 Customer 还是 User? 这是两件不同的事。"
3
Discuss concrete scenarios
讨论领域关系时,造场景压测边界条件,逼用户精确划清概念边界。
4
Cross-reference with code
用户说"这玩意是这么工作的",去核对代码是不是这么说。
"你的代码把整个 Order 取消,但你刚才说可以部分取消 —— 哪个对?"
5
Update CONTEXT.md inline · 即时更新
术语解决后立刻写进 CONTEXT.md,不要攒批。

05 CONTEXT.md · 词汇表的纪律

CONTEXT.md 不是什么

SKILL.md 第 64 行写得非常死:

"CONTEXT.md should be totally devoid of implementation details. Do not treat CONTEXT.md as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else."

词条格式(CONTEXT-FORMAT.md)

# {Context Name}

{1-2 句说明这个 context 是啥、为什么存在}

## Language

**Order**:
{1-2 句定义这个词是什么}
_Avoid_: Purchase, transaction

**Invoice**:
向客户发出的、要求付款的请求。
_Avoid_: Bill, payment request

**Customer**:
下订单的个人或组织。
_Avoid_: Client, buyer, account

4 条规则

  1. Be opinionated. 同概念有多个词 → 选一个,其他列在 _Avoid_
  2. Keep definitions tight. 1-2 句。定义它是什么,不是它做什么
  3. Only include terms specific to this project's context. 通用编程概念(timeout / error type / utility pattern)不属于词汇表
  4. Group terms under subheadings when natural clusters emerge

06 ADR · 三原则 + 极简模板

三原则(全部为真才写)

1
Hard to reverse
改变主意的代价有实质意义
2
Surprising without context
未来读者会问"他们为啥这么做?"
3
Real trade-off
有真正的备选 + 选了它有具体理由

任何一条不满足 → 不写 ADR(可逆的事直接反悔就好,不意外的事没人会问,没替代方案的事没什么好记)。

ADR 模板(ADR-FORMAT.md)

极度极简的模板
# {Short title of the decision}

{1-3 句:背景是什么,我们决定啥,为啥。}

"An ADR can be a single paragraph. The value is in recording that a decision was made and why — not in filling out sections."

可选 section(只在真有用时)

Section什么时候
Status frontmatter (proposed / accepted / deprecated / superseded by NNNN)决策会被重新审视时
Considered Options被拒绝的备选值得记住
Consequences不明显的下游影响

07 什么算 ADR 候选? · ADR-FORMAT.md § What qualifies

把"三原则"翻译成具体例子:

  • ✅ 架构形状:"我们用 monorepo" / "写模型是事件溯源,读模型投影到 Postgres"
  • ✅ context 间集成模式:"Ordering 和 Billing 通过领域事件通信,不用同步 HTTP"
  • ✅ 有锁定的技术选型:数据库、消息总线、auth provider、部署目标(swap 要花一个季度的)
  • ✅ 边界 / 范围决策:"Customer 数据归 Customer context;其他 context 只用 ID 引用"
  • ✅ 明显偏离常识的故意:"我们用手写 SQL 不用 ORM,因为 X"
  • ✅ 代码里看不到的约束:"合规要求不能用 AWS" / "响应时间必须 < 200ms 因为合作伙伴 API 合约"
  • ✅ 非显而易见的拒绝备选:"考虑了 GraphQL 选 REST,因为微妙理由" —— 否则 6 个月后会有人又提议 GraphQL
★ 设计哲学

第 44 行特别强调"explicit no-s are as valuable as the yes-s"。
写 ADR 不光记"我们用了 X",还要记"我们刻意拒绝了 Y"。这两个信息合起来,让下一个工程师不会去"修"被刻意设计的样子。

08 关键设计模式

Active vs Consumptive Discipline · 主动 vs 消费
区分"读 CONTEXT.md"(任何 skill 都能做的习惯)和"建 domain model"(需要专门技能)。避免 model 在没必要的时机被引用。
Glossary + ADR 双层
CONTEXT.md 是"什么" = 词汇表;ADR 是"为什么" = 决策记录。两者职责严格分开。
Lazy File Creation
没东西写就不建文件。第一条术语出现才建 CONTEXT.md,第一个 ADR 需要才建 docs/adr/。避免空文件演变成"假装存在"。
Single vs Multi Context Detection
根据是否存在 CONTEXT-MAP.md 自动判断仓库是单 context 还是多 context。skill 不让用户配置,而是自动推断。
Avoid List · 禁用清单
每个词条下都列 _Avoid_: 替代词。强制词表统一。和 codebase-design 的 Avoid-List 同源思路。
Define IS not DO · 定义是什么不是做什么
词条定义"这个概念是什么",不是"这个概念做什么"。保持词汇表的纯领域性,避免变成实现说明。
3-Criteria ADR Trigger
只有 hard-to-reverse / surprising-without-context / real-trade-off 三条都成立才写 ADR。把"什么时候写文档"从模糊变成可决策。
Minimalist ADR Template
模板就 1 行 title + 1-3 句正文。可选 sections 也只在"真有用"时加。把"模板的复杂度"降到最低。
Inline Update · 即时更新
术语解决后立刻写进 CONTEXT.md,不攒批。把"记录"嵌入到对话流里,不让它变成收尾任务。

09 启发 · 我们可以抄什么?

★ 给领域文档设计的启示

1. 区分"读"和"改":消费模型不需要技能,改模型才召唤。
2. 词汇表不是 spec:保持纯领域性,不让实现细节污染。
3. 写文档配三原则:三条件都成立才写,避免文档变成噪音。
4. 模板极简化:1-3 句话就够,别让模板吓跑用户。
5. 避免清单显式列出:不仅记"用 X",还要记"不用 Y"。
6. 懒建文件:没东西不建,避免空文件幻觉。
7. 即时更新:术语解决当下写,不要攒批。
8. 多 context 自动推断:让 skill 自己探测仓库结构,而不是让用户配置。
