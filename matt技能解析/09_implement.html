03 5 个动作拆解

1 Implement the work
按 spec / tickets 描述的实现。用户/前置 skill 已经把要做什么定下来了,这是执行环节。
2 Use /tdd where possible, at pre-agreed seams
"where possible" 不是 hard requirement。
"at pre-agreed seams" 是关键 —— 只有之前约定好的 seam才能用 TDD,不能临时发明 seam。
3 Typecheck + 单文件测试经常跑
见下节"频率节奏"。
4 Once done, use /code-review
实现完后跑双轴 review(Standards + Spec),再决定能不能 commit。
5 Commit your work
最后一步:commit 到当前分支。review 之后才 commit,不是 review 之前。

04 频率节奏 · "regularly" 的精确定义

SKILL.md 第 11 行只给了"regularly"这种模糊词,但它规定了三种不同频率:

typecheck
REGULARLY
每次写完一个功能块就跑。最便宜,频率最高。
single test files
REGULARLY
写完一个测试 / 改完相关文件就跑。中等频率。
full test suite
ONCE AT END
只在最后跑一次。最贵,频率最低。
为什么这样分级?
· typecheck:2-10 秒。写到关键函数就跑,防类型漂移。
· 单文件测试:5-30 秒。每改完一处就验证因果链。
· 全 suite:分钟级。不能经常跑,否则反馈环断掉。只在最后跑一次,作为整盘验证。
这种"成本 → 频率"的对应是实现流程的核心节拍。

05 编排关系 · implement 在哪里

implement 在主流程里是个编排者,自己不写测试细节、不写 review 细节,而是驱动其他子技能。

🎯 implement · 主编排
15 行 · 只做调度,不写代码细节
→ /tdd
在合适 seam 写测试-实现-重构循环
→ typecheck / test
用不同频率跑验证
→ /code-review

↓ 最后 ↓

06 "where possible" 和 "pre-agreed seams" 的设计

SKILL.md 第 9 行两个修饰语非常关键:

Use /tdd where possible, at pre-agreed seams.

"where possible"

TDD 不是硬要求。某些改动(重构 / 命名修正 / 单行 typo)用 TDD 不合理。判断权给执行者。

"at pre-agreed seams"

这是从 codebase-design 借来的概念:seam 不能临时发明。在 to-spec / to-tickets 阶段就约好了 seam(这是怎么测的边界),实现时只在这些 seam 上做 TDD。

★ 设计哲学

"pre-agreed" 这个词防止了"事后补测试"的常见陷阱:
实现写完了,再想"诶,我能写个测试吗?" —— 这时你已经为测试而调整设计了。Seam 必须在写代码之前就约好。

07 "Once done, use /code-review" 的位置意义

第 13 行:"Once done, use /code-review to review the work."

这条规则把 code-review 锁定到 commit 前:
❌ 边写边 review(浪费 token)
✅ 实现完才 review(整盘检查)
✅ review 通过才 commit
❌ review 不过 → 修 → 再 review → commit

位置即流程:"Once done" 这个词把 review 钉在 commit 之前的最后一道关。这和 ask-matt 主流程里"/implement 关闭前跑 /code-review"完全对齐 —— 两个文档互相印证。

08 关键设计模式

Orchestrator, Not Executor · 编排者而非执行者
implement 自己不写测试细节、不写 review 细节,只是驱动其他子技能。
Verb-First Imperatives · 动词开头祈使句
每行一个动词开头:Implement / Use / Run / Once done, use / Commit。动词即指令。
Cost-Frequency Mapping · 成本 → 频率
typecheck(快)经常跑 · 单 test(中)经常跑 · 全 suite(慢)只在最后。频率倒挂成本。
Soft Constraints · 软约束
"where possible" 让执行者有判断空间。不把所有约束都写成 hard rule。
Pre-Agreed Seams · 预先约好的 Seam
不允许实现时临时发明 seam。Seam 必须在 to-spec / to-tickets 阶段定下来。
Review-Before-Commit · 评审后才 Commit
/code-review 在 commit 前一道关,而不是事后补救。
Explicit-Only Invocation
disable-model-invocation: true。实现不能脑补,用户必须显式触发。

09 启发 · 我们可以抄什么?

★ 给实现流程设计的启示

1. 编排者而非执行者:实现流程不需要自己懂 TDD 细节,只需要驱动 /tdd。
2. 动词开头,5 句搞定:implement → TDD → typecheck → review → commit。
3. 成本决定频率:快检验经常跑,慢检验只在最后。
4. 软约束留判断空间:"where possible" 比 "always" 更诚实。
5. Seam 预先约:测试边界不能在实现时临时发明。
6. Review 在 commit 前:不是事后补救,是最后一道关。
7. 显式触发:实现不能脑补。
