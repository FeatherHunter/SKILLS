02 3 阶段流程

1
Explore
先 scope 再 scan · YAGNI。
用户已指方向 → 直接进入;否则 git log --oneline 找出热点(频繁改的代码区)。
用 Agent(subagent_type=Explore) 有机探索,问 5 个问题:
  1. 理解一个概念需要在多个小模块间跳来跳去?
  2. 哪些模块 shallow(接口和实现一样复杂)?
  3. 纯函数为了可测被抽出,但 bug 藏在调用方式(无 locality)?
  4. 紧耦合模块越过 seam 泄漏?
  5. 哪些部分没测,或难以通过当前 interface 测?
对怀疑对象跑deletion test:删它 → 复杂度集中还是搬家?"集中"才是想要的信号。
2
Present candidates as an HTML report
写到 OS 临时目录(不污染仓库):
<tmpdir>/architecture-review-<timestamp>.html

自动打开:xdg-open / open / start(按平台)。

技术栈:Tailwind via CDN + Mermaid via CDN。
Mermaid 用于关系图(graph-shaped);手绘 SVG/div 用于"更编辑性"的(mass、cross-section)。
每张候选卡必含:Files / Problem / Solution / Benefits / Before-After / Recommendation badge。
必须有 Top Recommendation(立场)。
3
Grilling loop
用户挑一张候选 → 跑 /grilling 走决策树。
边访谈边调 /domain-modeling:
· 起新模块名不在 CONTEXT.md → 加进 CONTEXT.md(懒建)
· 锐化模糊术语 → 立刻更新 CONTEXT.md
· 用户用承重理由拒绝候选 → 提议 ADR(避免下次再提议)
· 想探索多个 interface 方案 → 调 /codebase-design 的 design-it-twice

03 候选卡片模板

HTML-REPORT.md 第 40–55 行严格定义每张候选卡片的结构:

Collapse the Order intake pipeline
STRONG ports & adapters
Files
src/orders/intake/OrderHandler.ts · OrderValidator.ts · OrderRepo.ts · PricingClient.ts
BEFORE

3 shallow modules · 串行调用

AFTER

1 deep module · 隐藏复杂度

Problem: Order intake is shallow — interface nearly matches the implementation; pricing leaks across the seam.

Solution: Deepen: one interface, one place to test. Move validator + repo + pricing into a deep OrderIntake module.

WINS
  • Locality: bugs concentrate in one module
  • Leverage: one interface, N call sites
  • Interface shrinks; implementation absorbs wrappers
  • Delete 4 shallow wrappers

04 Recommendation Badge 三档

每个候选有一个推荐强度的徽章,三种颜色对应三个立场:

Strong · 强烈推荐
emerald 色徽章 · 优先做
Worth exploring · 值得探索
amber 色徽章 · 看时间
Speculative · 投机性
slate 色徽章 · 别投时间

05 4 种 Diagram 模式

HTML-REPORT.md 第 58–92 行给出 4 种 diagram 类型。强调"不要每张图都一个样",变化本身就是要点。

① Mermaid flowchart
依赖图 / 调用流 · "X 调 Y 调 Z,看这一团乱"
② Hand-built boxes
Mermaid 排版打架时 · 想做出"加粗 deep module + 灰化内部"的感觉
③ Cross-section · 横截面
分层浅薄:6 层啥都不做 → 1 层承担
④ Mass diagram · 体积图
"interface 和 implementation 一样宽":两个矩形,一宽一窄
关键约束(HTML-REPORT.md §105):"Lean editorial, not corporate-dashboard. ... diagrams should read as schematic, not as UI."
报告是杂志式的,不是仪表盘式的。留白多、节制色彩。

06 强制词表 · Use / Avoid

HTML-REPORT.md §108-121 行给出了比 codebase-design 更严格的词汇强制:

✅ 必须用
  • module, interface, implementation
  • depth, deep, shallow
  • seam, adapter, leverage, locality
❌ 永远不要
  • component, service, unit (for module)
  • API, signature (for interface)
  • boundary (for seam)
  • layer, wrapper (for module, when you mean module)

推荐的 phrase

  • "Order intake module is shallow — interface nearly matches the implementation."
  • "Pricing leaks across the seam."
  • "Deepen: one interface, one place to test."
  • "Two adapters justify the seam: HTTP in prod, in-memory in tests."
★ 设计哲学

§121 行写得很死:"Don't write 'easier to maintain' or 'cleaner code' — those terms aren't in the glossary and don't earn their place."
把"空洞收益话术"明确禁用 —— 逼所有 win 都用词表里的术语。

07 ADR 冲突的处理

SKILL.md §56 行处理了一个棘手情况:

if a candidate contradicts an existing ADR, only surface it when the
friction is real enough to warrant revisiting the ADR. Mark it clearly
in the card (e.g. a warning callout: "contradicts ADR-0007 — but worth
reopening because…"). Don't list every theoretical refactor an ADR
forbids.

决策树

  1. 候选和 ADR 冲突?
  2. ↓ 是
  3. 摩擦真实到要重审 ADR?
  4. ↓ 是 → 在卡片上 amber callout 标记,说明原因
  5. ↓ 否 → 不列出来

避免"每个理论上被 ADR 禁止的重构"都列出来 —— 否则报告会被噪音淹没。

08 关键设计模式

Vocabulary Inheritance · 词汇继承
强制使用 codebase-design 词汇(domain-modeling 词汇在报告里同样适用)。三个技能共享一个语言。
Visual Report as Output · 视觉报告即产出
不写 README,写 HTML 报告。Tailwind + Mermaid CDN,自动打开 OS 默认浏览器。
Before / After as Centerpiece
每张候选的核心是 before/after 对比"If a sentence could be a bullet, make it a bullet. If a bullet could be cut, cut it."
Diagram Variety · 变化本身是设计
4 种 diagram 模式(Mermaid / 手绘 / 横截面 / 体积)交替使用。避免报告视觉同质。
Anti-Corporate Tone
杂志式排版,留白多,色彩节制。仪表盘风格被明确拒绝。
OS Temp File · 写临时目录
不污染仓库。和 handoff 一致:进程间协作的东西不进 git。
Top Recommendation · 必须有立场
末尾必须给 Top Recommendation。"Don't hedge, don't throat-clear, don't 'it's worth noting that…'"
ADR Conflict Surfacing
和 ADR 冲突 → 真摩擦才标,假冲突不列。amber callout 标记 reopen 理由。
Skill Composition in Stage 3
Stage 3 调三个其他技能:/grilling + /domain-modeling + /codebase-design。Skill 作为编排节点。

09 启发 · 我们可以抄什么?

★ 给架构巡检设计的启示

1. scope before scan:先确定扫哪里(YAGNI),不要漫天扫描。
2. hot-spot 由 git log 找:常改的代码区才是值得深化的。
3. visual report > text report:架构候选用 HTML + before/after 图。
4. diagram 要有变化:4 种类型交替,避免视觉同质化。
5. 词汇强制:禁用 "easier / cleaner",逼用词表术语。
6. 必须有立场:Top Recommendation + 3 档推荐强度。
7. 多技能编排:Stage 3 同时调 3 个其他 skill。
8. 写到临时目录:不污染仓库。
