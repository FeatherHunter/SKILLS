03 6 条通用规则 · 两条分支都遵守

SKILL.md 第 19–26 行给出 6 条无论哪个分支都执行的规则:

① THROWAWAY FROM DAY ONE
从第一天起就是 throwaway,标记清楚。位置靠近被原型的模块,但命名让陌生人能看出是 prototype 不是 production。
throwaway UI route 走项目已用的 routing 约定,不发明新顶层结构。
② ONE COMMAND TO RUN
一条命令启动。用项目已有的任务运行器(pnpm / Makefile / justfile)。用户不用记路径。
③ NO PERSISTENCE BY DEFAULT
默认无持久化。状态在内存里。除非问题就是持久化,否则不要接数据库。问题涉及 DB 时,接 scratch DB 或本地文件,文件名带 "PROTOTYPE — wipe me"。
④ SKIP THE POLISH
跳过抛光。无测试、无错误处理(除了让它跑起来)、无抽象。目的是快速学到东西。
⑤ SURFACE THE STATE
让状态可见。每次操作(逻辑)或变体切换(UI)后,打印/渲染全部相关状态,让用户看见变了什么。
⑥ CAPTURE IT WHEN DONE
完成后捕获。把验证过的决策融入真实代码 → 把原型本身作为一手资料提交到 throwaway 分支(不在 main) → 在 issue 上留指针。
main 只保留验证过的决策,不保留 prototype 过程。

04 LOGIC 分支 · 7 步流程

LOGIC.md 第 14–71 行定义了完整的 logic prototype 流程。最具特色的是第 3 步:"Isolate the logic in a portable module"。

逻辑形状选择

形状适用
Pure reducer — (state, action) => state离散事件 + 单一状态
State machine — 显式 states + transitions哪些动作"现在合法"是问题的一部分
小集合的 pure functions无隐式当前状态,只是变换
Class/module with method surface逻辑确实拥有持续内部状态

隔离原则

LOGIC.md §37:"Keep it pure: no I/O, no terminal code, no console.log for control flow."

逻辑模块只往一个方向依赖 TUI。TUI 调用逻辑,反过来不依赖。这让验证过的逻辑可以脱离原型被提取到真实模块。

05 LOGIC 5 个抗模式

LOGIC.md §73–78 行明确禁止 5 种行为:

Don't add tests. A prototype that needs tests is no longer a prototype.
Don't wire it to the real database. Use an in-memory store unless the question is specifically about persistence.
Don't generalise. No "what if we wanted to support X later." The prototype answers one question.
Don't blur the logic and the TUI together. If the reducer / state machine references console.log, prompts, or terminal escape codes, it's no longer portable.
Don't ship the TUI shell into production. The shell is optimised for being driven by hand from a terminal. The logic module behind it is the bit worth keeping.
关键设计:"Test" 在 prototype 语境里是脏词。一旦需要测试,它就不是 prototype 了。

06 UI 分支 · 两种 Sub-shape

UI.md 第 14–32 行明确说:优先 A,B 是最后手段。

Sub-shape场景做法
A · 调整个已有页面(首选)已有 route 或能自然嵌入?variant= URL 参数 + 同一 route + 真实数据
B · 新建页面(最后手段)确实没有归属页面throwaway route 走项目已有约定 · 名字含 "prototype"
★ 关键哲学

UI.md §16:"A UI prototype is much easier to judge when it's butting up against the rest of the app — real header, real sidebar, real data, real density. A throwaway route on its own is a vacuum: every variant looks fine in isolation."
一个空路由 = 美学真空,什么都好看。塞进真实上下文,设计问题才暴露。优先嵌入。

08 UI 4 个抗模式

Variants that differ only in colour or copy. That's a tweak, not a prototype. Real variants disagree about structure.
Sharing too much code between variants. A shared Header is fine; a shared Layout defeats the point. Each variant should be free to throw out the layout.
Wiring variants to real mutations. Read-only prototypes are fine. If a variant needs to mutate, point it at a stub.
Promoting the prototype directly to production. The variant code was written under prototype constraints (no tests, minimal error handling). Rewrite it properly when you fold it in.

09 关键设计模式

Question Decides Shape · 问题决定形状
先看问题(logic vs UI),再看工具。选错分支浪费整个 prototype。
Throwaway From Day One
从一开始就是 throwaway。命名 / 位置 / 注释都明确标记。避免"无意识活成生产代码"。
Portable Logic Module · 可移植逻辑模块
LOGIC:纯模块(无 IO/terminal),可以被提取到真实代码。TUI 是薄壳。
Existing Context Default · 默认嵌入
UI:优先 sub-shape A(嵌入已有页面)。空路由是美学真空,什么都好看,什么问题都不暴露。
Radically Different · 结构上不同
Variant 不只是改色 / 改文案。结构、信息层次、主操作都要不同。
Switcher as First-Class · 切换器是一等公民
URL ?variant= + 浮动切换条。键盘 + 鼠标双支持。生产构建隐藏。
Capture as Primary Source · 原型作为一手资料
main 只留验证过的决策。prototype 全集进 throwaway 分支,作为决策依据的原始档案。
Anti-Patterns Explicit · 抗模式显式列出
LOGIC 5 个 + UI 4 个抗模式。把"常见走偏"写出来,模型少走弯路。

10 启发 · 我们可以抄什么?

★ 给原型设计的启示

1. 问题决定形状:先选 LOGIC / UI,别乱套。
2. 一天起就是 throwaway:命名 / 位置 / 注释标记。
3. 一条命令启动:用项目已有任务运行器。
4. 默认无持久化:除非问题就是持久化。
5. 跳过抛光:无测试、无抽象。
6. 逻辑隔离:pure module + 薄壳 TUI,可被提取。
7. 嵌入优于新建:UI prototype 优先塞进已有页面。
8. Variant 必须结构上不同:不是改色。
9. 切换器是公民:URL + 浮动 + 键盘 + 生产隐藏。
10. prototype 进 throwaway 分支:作为决策依据的档案,main 不留。
