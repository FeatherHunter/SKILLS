02 5 步骤详解

1
See the current state
看当前状态。查 git 历史 + 冲突文件。
命令:git status · git log --oneline · git diff · 看冲突标记 <<<<<<< / ======= / >>>>>>>
2
Find the primary sources
找原始意图。理解每个改动为什么做、原意图是什么。
查:commit messages · PR · 原始 issue / ticket。
这一步是 SKILL.md 的关键 —— 体现 research 技能的 "primary sources" 哲学在冲突场景下的应用。
3
Resolve each hunk
解决每块冲突。
· 可能时保留双方意图
· 不兼容时选符合 merge 目标的,记录 trade-off
· 不要发明新行为
· 永远解决;永远不 --abort
4
Run automated checks
发现并跑自动检查。通常: typecheck → tests → format。
修任何 merge 引起的破坏。
5
Finish the merge / rebase
完成 merge / rebase。stage 全部 + commit。
rebase 场景 → 持续直到所有 commit 都 rebase。

03 两条硬规则

RULE 1
Do not invent new behaviour. 冲突解决只搬运两边已有意图,不要借机"修"或"改进"。
RULE 2
Always resolve; never --abort. 永远解决冲突,不能用 git merge --abort 逃跑。
★ 设计哲学

"Never --abort" 是最反直觉的硬规则。
开发者遇到大冲突常常想 --abort 撤回,这不是处理,而是逃避。
SKILL.md 把"必须解决"写入硬规则 —— 即使问题很难,也必须正面面对。

04 冲突场景可视化

OURS · branch A
function calcPrice(items) {
  const subtotal = items
    .reduce((s, i) => s + i.price, 0);
  return subtotal * TAX_RATE;
}
意图: 用 reduce + 显式 TAX_RATE
THEIRS · branch B
function calcPrice(items) {
  return items.reduce(
    (s, i) => s + i.price, 0
  ) * getCurrentTaxRate();
}
意图: 用 getCurrentTaxRate() · 动态税率
RESOLVED
function calcPrice(items) {
  return items.reduce(
    (s, i) => s + i.price, 0
  ) * getCurrentTaxRate();
}
保留 theirs 的动态税率 + ours 的 reduce 形式

这是"preserve both intents where possible"的典型例子 —— 选 theirs 的核心逻辑(动态税率),保留 ours 的 reduce 形式。

05 不兼容时怎么选?

SKILL.md 第 10 行:"Where incompatible, pick the one matching the merge's stated goal and note the trade-off."

场景如何选
两者语义相同,只写法不同选更现代 / 更一致于 base 的写法
两者逻辑不兼容看 merge commit message 写的目标 → 选符合目标的
目标不明看最近的 base 用了哪种 → 沿用
怎么都判断不出向用户提问 — 不要脑补
关键:无论选哪个,"note the trade-off" —— 在 commit message 里写明你选了什么、放弃了什么、未来可能需要复查。这是给下一个开发者的痕迹。

06 Step 4 · "Discover" 的含义

SKILL.md 第 12 行用了 "Discover the project's automated checks",不是 "run"。

这种用词区别很关键:
· Run = 假设你知道跑什么
· Discover = 去项目里找项目实际定义了什么

可能的形式

  • package.json 的 scripts
  • Makefile / justfile / pyproject.toml
  • .github/workflows/ci.yml(CI 上跑什么)
  • .pre-commit-config.yaml
  • README 里的 "Running tests" / "Dev workflow" 节

这呼应了 codebase-design 里的"借用项目已有约定"哲学 —— 不发明新的命令或工具。

07 关键设计模式

Primary Sources · 原始意图
Step 2:每个冲突都要追到 commit message / PR / issue。不靠脑补意图。
Preserve Both Intents
Step 3 第一选项:保留双方意图。不兼容才取舍。
No Invention · 不发明
冲突解决不是借机改进功能的地方。仅搬运两边已有代码。
Never --abort
硬规则。逃避不是处理。必须正面解决。
Discover, Don't Assume
Step 4 用 "discover" 而非 "run"。先去项目里找再跑。
Note Trade-offs · 记录取舍
不兼容时选了哪条 + 放弃哪条 + 何时复查 → commit message。

08 启发 · 我们可以抄什么?

★ 给冲突解决流程的启示

1. 追原始意图:不看代码猜,看 commit / PR / issue 知意图。
2. 保留双方:能保留都保留,实在不行才取舍。
3. 不发明:冲突解决不是改进时机。
4. 绝不 --abort:逃避不是处理。
5. discover 而非 run:先去项目里找检查工具。
6. 记录 trade-off:commit message 是下一个开发者的线索。
