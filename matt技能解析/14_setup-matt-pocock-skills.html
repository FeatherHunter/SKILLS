02 5 阶段流程

1
Explore
先看现状,不假设。查 git remote -v / AGENTS.md / CONTEXT.md / docs/adr/ / docs/agents/ / .scratch/ / 是否装了 triage / 单仓还是 monorepo。
2
Present findings and ask
三节,顺序问。
· Section A — Issue tracker:GitHub / GitLab / Local / Other
· Section B — Triage labels(仅 triage 装了才跑)
· Section C — Domain docs(仅 monorepo 信号才问)
每节推荐答案打头,用户可以一键接受。
3
Confirm and edit
让用户审稿。展示草稿,允许编辑后才写。
"Let them edit before writing" —— 写文件是终局动作,必须用户看过。
4
Write
选文件:CLAUDE.md > AGENTS.md > 让用户选。
绝不创建重复的 ## Agent skills block,in-place 更新。
绝不覆盖周围用户编辑。
5
Done
告诉用户完成 + 哪些 skill 现在会读这些文件。
可以随时改 docs/agents/*.md,无需重跑。

06 文件选择规则 · 严格优先级

SKILL.md 第 74–82 行写了硬规则:

Pick the file to edit:
1. CLAUDE.md 存在 → 编辑它
2. 否则 AGENTS.md 存在 → 编辑它
3. 否则 → 问用户要建哪个
Never create AGENTS.md when CLAUDE.md already exists.
If ## Agent skills block 已存在 → in-place 更新,不追加。
★ 设计哲学

"Never create AGENTS.md when CLAUDE.md already exists" 是非对称的反感重复规则。
一个仓库一个真相源 —— 让用户后续维护时知道只编辑一处。
这种"反复制"的设计保护了一致性。

07 domain.md · 沉默消费规则

domain.md 第 11 行写了一条非常微妙的规则:

If any of these files don't exist, proceed silently.
Don't flag their absence; don't suggest creating them upfront.
The /domain-modeling skill ... creates them lazily when terms or
decisions actually get resolved.

翻译:domain doc 不存在 → 沉默继续,不要主动建议建。
建文件的时机是"terms or decisions actually get resolved" ——
这呼应了 domain-modeling 技能的lazy creation原则。

4 条消费规则

  1. 开始探索前先读 CONTEXT.md 或 CONTEXT-MAP.md
  2. 读 docs/adr/ 相关决策;多 context 时也读 src/<context>/docs/adr/
  3. 输出用 glossary 里的词汇 · 不要用被 _Avoid_ 列出的同义词
  4. 发现 ADR 冲突 → 显式标记 "Contradicts ADR-0007 ... but worth reopening because ..."

08 GitHub tracker · Wayfinder 集成

issue-tracker-github.md 第 36–44 行展示了 wayfinder 用 gh api 的具体操作:

- Map: 一张 issue 标 wayfinder:map · 持有 Notes / Decisions-so-far
- Child ticket: 子 issue · 通过 sub-issues 关联
- Blocking: 用 native issue dependencies(gh api POST blocked_by)
- Frontier query: 列出 map 的开放子 issue · 过滤掉有 blocker 的
- Claim: gh issue edit <n> --add-assignee @me
- Resolve: comment → close → 在 map 上追加 context pointer

这是issue tracker 的使用规范,不只定义"issue 在哪",还定义了"issue 怎么被 skill 操作"。这是仓库级 setup 的精髓 —— 让所有 skill 共享一个一致的操作协议。

09 "PRs as a request surface" 标志

第 49 行一个微妙细节:

PRs as a request surface: no. (Set to yes if this repo treats external
PRs as feature requests; /triage reads this flag.)

这是一个默认 off 的功能开关,setup 不会主动提它:
· off(默认):外部 PR 走正常 review,不当作 feature request 排队
· on:外部 PR 走 triage queue,和 issues 共享 labels
· setup 不主动问,只是文档里写"想用改这里"

设计哲学:"leave it off and don't raise it"。
默认 off + 不主动提 = opt-in feature,不被默认配置淹没。

10 关键设计模式

Per-Repo Scaffolding · 仓库级脚手架
技能不是无状态规则,而是把仓库配置成它期望的样子。Setup 写完后,其他 skill 才能工作。
Prompt-Driven, Not Script
第 15 行:"This is a prompt-driven skill, not a deterministic script." — setup 不是 TS 文件,是和用户一起探索+写。
Lead with Recommendation · 推荐打头
每节都把推荐答案放第一句,用户可一键接受。"Lead each section with the recommended answer"。
Section Skipping · 智能跳过
没装 triage → 跳 Section B;不是 monorepo → 跳 Section C。绝不问没用的问题。
Anti-Duplication Rules
"Never create AGENTS.md when CLAUDE.md exists" · "in-place update, not append"。一条真相源。
Silent Defaults · 沉默默认
domain doc 不存在 → 沉默继续,不主动建议建。"proceed silently" —— lazy creation。
Opt-In Features Default Off
"PRs as a request surface" 默认 off,不主动提。避免默认配置淹没可选特性。
Seed Templates as Annex
每个目标状态(github/gitlab/local/triage-labels/domain)一个 seed 文件。主 SKILL.md + 附录结构。
Confirmation Before Write
"Let them edit before writing" — 写文件是终局动作,必须用户看过草稿。

11 启发 · 我们可以抄什么?

★ 给仓库级 setup 的启示

1. 先探后写:setup 不是一个 TS 脚本,是一个 prompt-driven 流程。
2. 推荐打头:用户能一键接受。
3. 智能跳过:没装 triage 不问 label,不是 monorepo 不问 layout。
4. 严格优先级:CLAUDE.md > AGENTS.md > 让用户选。
5. 不复制:in-place 更新 · never create duplicate。
6. 沉默默认:缺文件不主动建议建,留给 lazy creation。
7. opt-in 默认 off:可选特性不淹没默认配置。
8. 主 + 附录:主 SKILL.md 写流程,各目标状态用 seed 文件。
9. 写前确认:让用户编辑草稿后才写文件。
