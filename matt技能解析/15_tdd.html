★ Refactoring 不在循环里

SKILL.md 第 36 行:"Refactoring is not part of the loop. It belongs to the review stage (see the code-review skill), not the red → green implementation cycle."
把红绿循环和重构分离。
红绿只关心"测试 + 最小实现",重构归 review。
这样循环不会被重构打断。

03 3 条循环规则

① RED BEFORE GREEN
先写失败测试,再写仅够通过的代码。不要为未来测试留位置,不加投机特性。
② ONE SLICE AT A TIME
一个 seam,一个测试,一个最小实现。每个循环。
③ NO REFACTORING IN LOOP
重构归 review,不在红绿循环里。

04 3 个抗模式

❌ Implementation-Coupled · 实现耦合
Mock 内部协作者,测私有方法,通过旁路(查数据库)验证。
症状:重构没改行为,但测试挂了。
❌ Tautological · 同义反复
期望值用代码自己重算:expect(add(a,b)).toBe(a+b)。测试由构造保证通过,永远不同意代码。
期望值必须从独立 truth source 来 —— 已知好字面量 / worked example / spec。
❌ Horizontal Slicing · 横向切片
先写所有测试,再写所有实现。"批量测试验证想象的行为"。
你在测"东西的形状",不是用户行为;测试结构先行于实现理解。

05 Vertical vs Horizontal · 切片对比

❌ Horizontal · 横向
test1, test2, test3, ...
        ↓
[write all implementation]

commit to test structure before understanding implementation

✅ Vertical · 垂直
test1 → impl1
test2 → impl2  (each informed by prior cycle)
test3 → impl3

each test is a tracer bullet responding to what the last cycle taught you

★ Tracer Bullet · 示踪子弹

第 30 行的 "tracer bullet" 是一个比喻:
每一轮红绿都像一颗子弹,打进去 + 看轨迹 + 调整方向。
横向切片 = 先造一堆子弹再开火(弹道未知)。
垂直切片 = 每发都是探路,根据前一发修正下一发。

06 好测试 vs 坏测试 · 代码对比

① 实现耦合

✅ GOOD · 测行为
test("user can checkout with valid cart", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
❌ BAD · 测内部调用
test("checkout calls paymentService.process", async () => {
  const mockPayment = jest.mock(paymentService);
  await checkout(cart, payment);
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total);
});

② 同义反复

❌ BAD · 重算期望
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, i) => sum + i.price, 0);
  expect(calculateTotal(items)).toBe(expected);
});
✅ GOOD · 已知字面量
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});

07 Seam 纪律 · 测试在哪

SKILL.md 第 18–24 行给出核心 seam 概念:

Seam = 你测试所在的公共边界 —— 在接口处观察行为,不钻到内部。

Tests live at seams, never against internals.

Test only at pre-agreed seams.
Before writing any test, write down the seams under test and
confirm them with the user. No test is written at an unconfirmed
seam.

Ask: "What's the public interface, and which seams should we test?"
★ Pre-Agreed Seam

"Pre-agreed seam" 是 tdd 技能和 implement 技能共享的硬规则:
测试位置必须在写测试之前就和用户约定好。
这和 codebase-design 的"interface is the test surface"是同一思想的两次表达。

08 mocking.md · 系统边界才 mock

✅ 可以 mock
  • 外部 API(支付 / 邮件)
  • 数据库(有时候,首选 test DB)
  • 时间 / 随机性
  • 文件系统(有时候)
❌ 不要 mock
  • 你自己的类 / 模块
  • 内部协作者
  • 任何你控制的东西

可 mock 设计 · 依赖注入

✅ 易 mock
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total);
}
❌ 难 mock
function processPayment(order) {
  const client = new StripeClient(process.env.STRIPE_KEY);
  return client.charge(order.total);
}

可 mock 设计 · SDK-style 接口

每个外部操作一个函数,而不是一个通用 fetcher 加 condition:

✅ GOOD · 每端点一个函数
const api = {
  getUser:    (id) => fetch(`/users/${id}`),
  getOrders:  (userId) => fetch(`/users/${userId}/orders`),
  createOrder:(data) => fetch('/orders', { method: 'POST', body: data }),
};
❌ BAD · 通用 fetcher
const api = {
  fetch: (endpoint, options) => fetch(endpoint, options),
};
// Mock 需要内部条件逻辑

09 关键设计模式

Red-Green as Discipline · 红绿即纪律
不是流程,是纪律。SKILL.md 第 8 行强调"Every section applies on every cycle"。
Pre-Agreed Seam · 预先约定测试边界
测之前先约 seam。没约定的 seam 不写测试。和 implement 共享同一硬规则。
Tracer Bullet · 示踪子弹
每轮红绿 = 一发探路子弹。垂直切片,横向验证想象。
Test Behavior, Not Implementation
测 WHAT,不是 HOW。重构不挂测试。
Independent Truth Source · 独立期望源
期望值不能由代码重算。要从字面量 / worked example / spec 来。
Refactor Outside Loop · 重构出循环
重构属于 code-review,不属于红绿循环。
Mock at System Boundary · 系统边界才 Mock
Mock 你的依赖,不是你的实现。可 mock 是一种设计属性。
SDK-Style Interface for Mockability
每个外部操作一个函数,而不是通用 fetcher。Mock 简单,类型清晰。

10 启发 · 我们可以抄什么?

★ 给测试设计的启示

1. 循环纪律:红绿每轮都重新读所有规则。
2. Seam 预先约:测试边界不是写到一半才决定。
3. 垂直切片:每发都是 tracer bullet。
4. 测行为不测实现:重构不挂。
5. 独立期望源:期望值不能由代码重算。
6. 重构出循环:留给 code-review。
7. 系统边界才 mock:你的实现不 mock。
8. 可 mock 是一种设计属性:依赖注入 + SDK-style 接口。
