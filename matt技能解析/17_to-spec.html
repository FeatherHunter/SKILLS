02 关键边界 · "Do NOT interview"

SKILL.md 第 7 行用大写重申边界:

"This skill takes the current conversation context and codebase understanding and produces a spec ... Do NOT interview the user — just synthesize what you already know."
★ 与 grill-me 的关键区别

to-spec 和 grill-me / grill-with-docs 看似都"用对话产生文档",但方向相反:
· grill-me:模型问,用户答 —— 生成共享理解
· to-spec:模型合成,用户不参与 —— 把已知信息变成 spec
这种"边界硬化"防止模型在 to-spec 里又开始问用户问题。

03 3 步流程

1
Explore the repo
先理解代码库当前状态。若还没探过的话。
用 domain glossary 词汇(CONTEXT.md)贯穿 spec;尊重该区域的 ADR。
和 codebase-design / domain-modeling 共享同套语言。
2
Sketch out the seams
草拟测试 seams。优先复用已有 seam · 选尽可能高的 seam · 新 seam 也越高越好。
少 seam 多好 —— 理想是 1 个 seam。
和用户确认这些 seam 符合期望。
这一步是 to-spec 唯一一处需要用户参与的环节。
3
Write + Publish + Label
按模板写 spec,发布到 issue tracker,打 ready-for-agent label。
不需要额外 triage —— 已经是 agent-ready 状态。

04 Seam 三原则

1
复用优先 · "Existing seams should be preferred to new ones."
2
尽量高 · "Use the highest seam possible."
3
越少越好 · "The fewer seams across the codebase, the better - the ideal number is one."
为什么 seam 越少越好?
codebase-design 的"deep module"原则 —— 一个大接口后藏一个复杂实现,胜过多个小接口。
Seam 越少,实现越深,测试越集中。

05 Spec 完整模板 · 7 节

## Problem Statement

用户面对的问题,从用户视角。

## Solution

解决方案,从用户视角。

## User Stories

LONG, numbered list。每个格式:As an <actor>, I want a <feature>, so that <benefit>

1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending
2. As a mobile bank customer, I want to see recent transactions, so that I can ...
3. As a bank employee, I want to ...

...几十条上百条 ... 穷举所有角度

## Implementation Decisions

列出已做的实现决策:将构建/修改的模块 · 接口修改 · 技术澄清 · 架构决策 · schema 变化 · API 合约 · 特定交互

## Testing Decisions

什么算好测试 · 哪些模块测 · 同类测试的 prior art(代码库里相似的)

## Out of Scope

明确不在范围内的事。

## Further Notes

任何其它备注。

06 代码片段规则 · "Do NOT include file paths"

SKILL.md 第 55 行给出重要的规则:

❌ Do NOT include
  • 具体的 文件路径(可能很快过时)
  • 代码 snippets(同上)
✅ Exception · 唯一例外

如果 prototype 产出的 snippet 编码了一个比散文更精确的决策(state machine / reducer / schema / type shape),可以 inline 到相关决策中,并简短注明"来自 prototype"。
只保留决策丰富的部分 —— 不是完整可运行的 demo。

★ 为什么禁具体路径

文件路径在 PR 后就过时。spec 是"意图的存档",不是"当前结构的快照"。
唯一例外:prototype 已经把决策硬化成代码。

07 "Ready-for-agent" label

第 19 行:"Apply the ready-for-agent triage label - no need for additional triage."

这意味着 to-spec 输出的 spec 直接进 agent-ready 队列,跳过 triage 流程。
这是一个隐含的"信任圈":
· model 自己写的 spec = model 自己要执行的 spec
· 不需要外部人类 / agent 再 review 一遍

隐含流程:
grill-with-docs (用户访谈) → to-spec (合成 spec) → to-tickets (拆 ticket) → implement (执行)
每一步的输出都自动进入下一步的"可执行"队列。

08 关键设计模式

Synthesis, Not Interview · 合成而非访谈
明确划清边界:不向用户问新问题,把已知信息压成 spec。和 grill-me 方向相反。
Seam Sketching · Seam 草图
写 spec 前先确定测试 seam,优先复用,越少越好。和 implement / tdd 共享 seam 纪律。
Inline Template
模板直接写在 SKILL.md 里,不引用外部文件。模型立即可读,无需跳转。
User Story Extensiveness
"LONG, numbered list" —— 用户故事要穷举所有角度,不留死角。
No Path/Code · 禁路径禁代码
spec 是意图存档,不是结构快照。唯一例外是 prototype 硬化的决策。
Auto Ready-for-Agent
model 自己生成的 spec → 直接打 ready-for-agent → 跳过 triage。
User Perspective · 用户视角
Problem / Solution 节都明确说"from the user's perspective"。技术语言留给 Implementation。

09 启发 · 我们可以抄什么?

★ 给文档合成技能的启示

1. 合成而非访谈:明确边界,避免越界问用户。
2. Seam 提前草拟:写之前先定测试边界,spec 才有可执行性。
3. 模板内联:直接写在 SKILL.md,模型一眼看到。
4. 用户故事要 LONG:穷举,不留盲点。
5. 不写路径不写代码:spec 是意图,不是快照。
6. Prototype 决策例外:被 prototype 硬化的代码可以 inline。
7. ready-for-agent 直通:自己生成的 spec 直接进入执行队列。
8. Problem / Solution 用用户视角:Implementation 才用技术语言。
