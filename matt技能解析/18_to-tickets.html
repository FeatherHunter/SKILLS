02 5 步流程

1
Gather context
从当前对话收集上下文。用户可传 spec 路径 / issue number / URL 作参数 —— 抓取并读全文 + 评论。
2
Explore the codebase (optional)
若没探过就探。Ticket 标题描述用 domain glossary 词汇。尊重 ADR。
寻找 prefactor 机会:"Make the change easy, then make the easy change."
3
Draft vertical slices
拆 tracer bullet tickets。每片:
· 窄但完整的路径穿过每层(schema / API / UI / tests)
· 完成时可独立 demo 或验证
· 单次 fresh context window 能装下
· 任何 prefactor 先做
标注 blocked by edges。
4
Quiz the user
给用户展示拆解 · 问:
· 粒度对吗(太粗 / 太细)
· blocking edges 对吗
· 要合并 / 拆分吗
iterate until approved。
5
Publish to the configured tracker
按依赖顺序发布(无 blocker 的先)。
· Local: .scratch/<feature>/issues/NN-slug.md · 用本地模板
· Real tracker: 一张 issue 一 ticket · 用 native blocking 关系
默认打 ready-for-agent · Do NOT close / modify parent issue。

03 Tracer Bullet · 垂直 vs 水平

❌ Horizontal · 横向

一层一层做

✅ Vertical · 垂直

每片跨所有层

每片完成后可独立 demo / 验证 · 不需要等其他层

★ Prefactor First

SKILL.md §23:"Make the change easy, then make the easy change."
在拆 tracer bullet 之前,先看能否 prefactor —— 预先重构让实现更容易。
比如先抽出接口 / 先建假数据。
这种"先修路再开车"的思路,把阻力放在 ticket 系统的边界外。

04 Blocked-by Edges · 依赖图

每个 ticket 标注其他 ticket 的 blockers。无 blockers 的 ticket 立刻可启动。

05 Wide Refactor 例外 · Expand-Contract

SKILL.md 第 40 行用一段极长的文字处理"垂直切片不适用的场景":

Wide refactor = 一个机械改动(重命名列 / 改共享类型),其 blast radius 横扫整个代码库。
一刀下去破坏几千调用点,任何垂直切片都无法单独绿。

解法:Expand-Contract 序列

1
Expand
新形式加在旧形式旁边,什么都不破坏。
2
Migrate (batches)
按 blast radius 分批迁移(per package / per directory),每批一张 ticket,被 expand block。CI 一直绿,因为旧形式还在。
3
Contract
删旧形式。被每个 migrate batch block。当所有调用方都迁移完后做。
极限情况:如果批次也不能单独绿 → 序列仍在,但让它们共享一个 integration branch,所有 batch 都 block 一张 "integrate-and-verify" ticket。绿只在那张上承诺。

两个模板都强调"from the user's perspective, not layer-by-layer implementation"。
这是 tracer bullet 哲学的延续 —— 测用户行为,不测实现细节。

07 关键设计模式

Tracer Bullet Slice · 示踪子弹切片
每片跨所有层,完成时可独立 demo,装进一个 fresh context window。
Blocked-by Edges
每 ticket 显式标注依赖,允许无依赖的 ticket 立即启动。Work the frontier = 找无 blocker 的票。
Prefactor First
"Make the change easy, then make the easy change" —— 先修路再开车。
Expand-Contract for Wide Refactors
不适合切片的大改动用 expand → migrate batches → contract 序列。CI 一直绿(直到最后)。
User Quiz Until Approved
拆解 → 用户审 → iterate 直到批准。发布前最后一道关。
Dependency-Order Publishing
按依赖顺序发布(无 blocker 的先),让 edges 引用真实 identifier。
Don't Close Parent
永远不关 / 改 parent issue —— 用户拥有 parent,模型只管子 ticket。
User Perspective in Description
"What to build" 用用户视角,不用 layer-by-layer 实现描述。

08 启发 · 我们可以抄什么?

★ 给 ticket 设计的启示

1. Tracer Bullet:垂直切片,每片完整跨所有层。
2. Fresh Context Window Sized:每片能装进一个新会话。
3. Prefactor First:先修路再开车。
4. Blocked-by Edges:依赖显式,可并行识别。
5. Work the Frontier:找无 blocker 的票。
6. Expand-Contract:大改动的安全序列。
7. User Quiz:发布前让用户批准。
8. Dependency-Order Publishing:blocker 先,被 block 的后。
9. Parent 不可动:模型只管子 ticket,不碰 parent。
10. 用户视角描述:不写 layer-by-layer 实现。
