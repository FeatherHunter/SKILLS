04 强制 Disclaimer

> This was generated by AI during triage.

SKILL.md 第 13–17 行:"Every comment or issue posted to the issue tracker during triage must start with this disclaimer"

★ AI 标注是底线

AI 介入协作工具时,必须自报身份。这条规则防止"AI 假装人类贡献"造成信任崩塌。
和 ask-matt 的"disable-model-invocation"同源 —— 透明性优先。

05 5 步流程 · Triage 一个 issue

1
Gather context
读完整 issue/PR(body / comments / labels / author / dates;PR 加 diff)。解析已有 triage notes,不要重问已解决问题。
用 domain glossary 探代码库。
跑两个检查:
(a) Redundancy — 按领域概念搜索(不只是措辞),已实现 = wontfix。
(b) Prior rejection — 读 .out-of-scope/*.md,找相似项。
2
Recommend
告诉 maintainer 推荐 category + state,带理由。
加相关代码摘要 + 是否已实现。
等指示。
3
Verify the claim
任何 grilling 之前先验证 claim 站得住。
bug:从 reporter 步骤复现。
PR:确认 diff 做了它说的事 —— checkout,跑相关测试。
报告:confirmed(带 code path) / failed / insufficient detail(强 needs-info)。
confirmed verification = 强 agent brief。
4
Grill (if needed)
如果请求需要 flesh out,跑 /grilling + /domain-modeling。
一次一问 · 锐化领域术语 · 决策落地时更新 CONTEXT.md / ADR inline。
5
Apply the outcome
5 种 outcome 不同动作(见下节)。

06 5 种 outcome 的不同动作

Outcome动作
ready-for-agent 发agent brief comment (AGENT-BRIEF.md)
ready-for-human 同 brief 结构,但注明为何不能委托(判断 / 外部访问 / 设计决策 / 手工测试)
needs-info 发 triage notes 模板
wontfix 关 issue · comment 取决于为什么:

3 种 wontfix 的细分

Already implemented
指出代码在哪。不要写 .out-of-scope/(那是给"被拒绝的",不是"已实现的")。
Rejected (bug)
礼貌解释 + close。
Rejected (enhancement)
写 .out-of-scope/ · comment 链接 · close。

07 "Show what needs attention" 三桶

SKILL.md 第 58–66 行规定 query 时的展示格式,三桶,oldest first:

  1. Unlabeled —— 从未 triage 过
  2. needs-triage —— 评估进行中
  3. needs-info + 自上次 triage 报告者有活动 —— 需要重新评估

PR(若在范围内)也进这三桶,每行标 [PR] / [issue]。
只展示 external PR(tracker 配置定义 external),内部合作者的 PR 不算 triage 工作。
显式 named PR 例外。

设计哲学:"Discovery surfaces only external PRs."
主动建议只看"需要关注的";用户主动说要的 PR 永远处理。
这种"默认窄、显式宽"的设计模式减少噪声。

08 Quick State Override

第 88–90 行处理一个微妙的场景:

If the maintainer says "move #42 to ready-for-agent", trust them
and apply the role directly. Confirm what you're about to do (role
changes, comment, close), then act. Skip grilling.

If moving to ready-for-agent without a grilling session,
ask whether they want to write an agent brief.

两条关键规则:
· 用户直接指令 → 信任(不必 grilling)
· 移动到 ready-for-agent 但没 grilled → 问要不要写 brief

★ Trust + Ask · 信任加追问

"trust + confirm before action" 是另一条反复出现的设计模式:
用户指令 → 信任 → 但确认动作(role 改 / comment / close)→ 再做。
用户没 grilled 就跳到 ready-for-agent → 主动追问 brief。
这种"信任但确认"的设计保护用户意图,同时避免模型脑补。

09 关键设计模式

Two-Axis Labels · 双轴标签
每个 issue = 1 category + 1 state。正交标签,不互相替换。
Mandatory Disclaimer · 强制 AI 标注
每条评论带 "> This was generated by AI during triage." 透明性底线。
Verify Before Grill
grilling 之前先 verify claim。复现 bug / checkout PR 跑测试。confirmed = 强 brief。
Redundancy by Domain Concept
搜索"已实现"时按领域概念,不是按措辞。措辞不同可能描述同一个东西。
Wontfix Sub-Categorization
wontfix 不是单一动作 —— Already implemented / Rejected bug / Rejected enhancement 三种不同处理。
.out-of-scope/ as Rejection KB
只存"被拒绝的 enhancement"。Already implemented 不算(那是"已实现的")。
Trust + Confirm Before Action
用户直接指令 → 信任,但 action 前 confirm。Ready-for-agent 没 grilled → 主动问 brief。
Discovery Surfaces Only External
主动查询只看 external PR。Explicitly named 永远处理。
PR = Issue + Code
PR 是 issue 的特殊形态。同状态机,少量 deltas(看 diff / 跑测试)。

10 启发 · 我们可以抄什么?

★ 给协作工具状态设计的启示

1. 双轴正交标签:category × state,每个对象 2 标签。
2. 强制 AI 标注:每条 AI 写的评论必须自报身份。
3. Verify before grill:grilling 之前先验证 claim。
4. 按概念搜,不按措辞。
5. Wontfix 细分:已实现 vs 拒绝 bug vs 拒绝 enhancement。
6. .out-of-scope/ 只存拒绝,不存"已实现"。
7. Trust + Confirm:用户直接指令信任,但 action 前 confirm。
8. Discovery 默认窄:外部 PR 才显示;explicit 永远显示。
