> 来源：用户 2026-08-08 口述（最高层级，重构优化开发的最重要信息）
> 定位：本文件是**所有场景设计 / 功能定标 / 帮助页结构 / 记录流程设计的源头输入**，优先级最高。
> 归属票：R3 onboarding（帮助页结构）、G1 功能定标（记录结果型 HTML）、G2 场景枚举（场景命名与覆盖）。

## 1. 使用流程（用户视角 · 7 步闭环）

1. 用户说「作息管家 help」→ 拿到 help HTML 文件
2. help HTML 内看到**各个功能域**；每个功能域有 **1 级目录**，点开后看到 **2 级子功能列表**
3. 点开 2 级列表 → 看到**场景列表**；每个场景右侧有「复制 prompt」按钮
4. 点击复制 → 交给 AI → AI 看到 prompt 提示信息，执行相关任务
5. 执行过程中**有必要时** → 出现**过程型 HTML**（填写信息 / 用户确认）
6. 用户确认后 → 过程型 HTML 页面上有「复制 prompt」按钮 → 点击交给 AI → AI 继续执行
7. 最终拿到**结果型 HTML** → 流程结束

> 与交互铁律 v2 对齐：① 一步直达（无过程页）② 多轮过程（过程 HTML → 复制 prompt → 继续 → 结果 HTML）③ 多轮变种。本描述是铁律 v2 的具象化。

## 2. 场景命名原则

- 场景名**不考虑**用户可能说的"很啰嗦、很人类的话"
- 场景名 = 展示清单里的词，用户只说看到词（与 2026-08-07「不脑补变体/入口」原则一致）
- 不做口语变体扩展，variants 留空

## 3. 设计目标（自下而上三层评估）

| 层 | 问题 | 目的 |
|---|---|---|
| 1. 底层支持 | 底层数据库到底存了什么数据 | 有这些数据才可能支持功能 |
| 2. 封装情况 | CLI 层有没有充分封装 | 底层能力是否可被调用 |
| 3. 场景覆盖 | 上层场景是否足够覆盖底层支持的功能 | 能力是否全部暴露给用户 |

## 4. 从上到下的补缺逻辑

- 发现需要什么功能 → 看 CLI 层有没有提供 → 看底层数据库有没有
- 功能重要且需要 → **底层 DB 变更 + CLI 层优化，缺哪个补哪个**
- ⚠️ **动数据库 = 大事，必须开发者（用户）确认**（与 09 §11 人类参与点「数据层」一致）

## 5. 记录后结果型 HTML（每日日程 / 实时计划记录）

**需求**：记录每一笔之后，返回一个**结果型 HTML**，设计好看、信息全面。

**内容需求**：
- 能看到过去几个小时推断了什么（实时记录的回溯）
- 或整天到目前为止的作息表
- 形态参考：高中那种作息表，但要**很漂亮、信息明显**

**设计要求**：
- 呈现什么数据、UI 展示 → 都要设计好
- 规划场景时对呈现的数据做**充分设计**；数据全面 → 以**最好的状态呈现最多的信息**
- 从用户角度出发，可用**各种图表、图形和技术**让用户看到的信息更全面
