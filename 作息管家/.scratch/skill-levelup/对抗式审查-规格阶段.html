规格阶段产出的 4 个矛盾

以「可开源（硬约束）→ 零基础 → 领域第一 → 可交付」第一性为标尺，审查已闭环的 R2/G1/R3/G2 四票。结论：规格阶段不能直接进入实施，有 2 个高危 + 2 个中危矛盾需先解决。

!

核心矛盾：可开源（第一优先级）vs git 历史含真实作息数据（Q10 拍板不清洗）。其余 3 个矛盾围绕实施可行性与规格自洽。

高危矛盾 1 · 可开源 vs git 历史真实数据

第一性追问：目标 1 是「可开源 = 仓库全公开」。但历史 7 个 commit（e6b42b6 ~ ba3a0be）含 `作息管家/.db/schedule_data.db`（3252 条真实作息）+ 2 个备份 JSON + 白名单 YAML。Q10 拍板「不清洗、不提及」——两者直接冲突：任何 clone 都能 `git log -p` 挖出全部作息记录。

git log --all -- '作息管家/.db/' → 7 commits 含 schedule_data.db / backup/*.json Q1 拍板: 可开源(硬约束) → 第一优先级 Q10 拍板: 历史不清理, README 不提及

建议：不等实施阶段——现在重开 Q10。三选一：① filter-repo 清洗（push 前你确认）；② 仓库级公开前把历史归档到私有 branch；③ 接受风险但 README 加「历史 commit 含演示数据」免责声明（至少不做"此地无银"式沉默）。这是唯一我建议打破"已拍板"的项——因为当时拍板时「可开源」还没被定义为第一优先级硬约束，两个决策不在同一认知下做出的。

高危矛盾 2 · scenarios.yaml 合并器 vs R2 删 .notes/

第一性追问：G2 定「81 场景经合并器写入 scenarios.yaml」+ 跨技能规范「yaml 只经合并器写入」。但合并器 = `.notes/_gen_scenarios.py`（docstring 自述"一次性脚本,生成后废弃"），而 R2 处置清单第 1 项 = 删 `.notes/` 整目录（你已拍板）。删了生成器，73→81 靠什么写入？

_gen_scenarios.py:2 """生成 scenarios.yaml — 一次性脚本,生成后废弃""" _notes/ 5 个文件 → R2 清单观察项1 → 你拍板「删除 + 忽略」 SKILL.md:16 场景资产唯一事实源: references/scenarios.yaml(73 场景)

建议：实施前必须定「yaml 写入机制」——要么新建正式的合并器脚本（放 scripts/，非 .notes/），要么把「合并器」定义为 AI 按字段契约手工 patch（现有 73 场景本就是脚本生成+后续手工维护）。现状是"宣称有合并器，实际没有"，这是流程漏洞不是执行细节。

中危矛盾 3 · 复盘场景重叠：复盘今日 vs 复盘区间 vs 复盘本周/本月

第一性追问：G1 定「复盘今日（对照+叙事+健康分）」与「复盘本周/本月（趋势+热力图）」为新场景，G2 又把 start-end 更名「复盘区间」保留。但 SKILL.md 路由已存在「复盘本周 → start-end 工作流 → schedule_replay.html」——同一唤醒词「复盘本周」既命中 start-end（现有）又命中 G1 新场景（计划中），路由冲突未解决。

SKILL.md:478 "复盘本周" → 复盘 start-end → schedule_replay.html G1-A3: 复盘本周 = 7维趋势 + 热力图 + 健康分均值（新模板） G2: 复盘区间(原 start-end) 保留独立场景

建议：规格阶段定死「复盘本周/本月」最终归属——是 start-end 增强（换模板复用现有路由）还是独立新场景（新唤醒词/新路由）？G1 与 G2 的表述不一致，实施阶段必然撞车。

中危矛盾 4 · 周视图 vs 已有「类别深挖 24h×N 热力图」

第一性追问：G1 定新场景「周视图 = 7×24 一周作息总览（网格/热力图）」。但现有 T4 场景 `category_range` 已输出 `record_category.html`（24h × N 天热力图）——周视图与既有热力图渲染能力高度重叠，且 record_category 是按单分类深挖，周视图是全分类总览，但渲染层大概率可复用。

scenarios.yaml:621 category_range → record_category.html(24h × N 天热力图) G1-A6: 周视图 = 7×24 一周作息总览(网格/热力图) → 新模板

建议：实施阶段周视图优先评估复用 record_category 的热力图渲染组件（属于「复用仅必要时」的对立面——这里复用的成本远低于新写）。规格层面补一句：周视图数据层与渲染层复用标注。

审查结论

高矛盾 1（git 历史 vs 可开源）——唯一建议重开已拍板决策的项，需要你定
高矛盾 2（合并器不存在 vs G2 宣称经合并器写入）——流程漏洞，实施前必须定机制
中矛盾 3（复盘本周/本月路由冲突）——G1/G2 表述不一致，需定死归属
中矛盾 4（周视图 vs 既有热力图复用）——实施前补复用标注即可，不阻塞
