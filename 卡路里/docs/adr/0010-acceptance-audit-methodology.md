# 验收与对抗式审核方法论(真实副本端到端 · 数据新鲜度 · 参照系 · 空态)

Status: accepted

目标管理 25 场景验收(2026-08-02 ~ 08-04,#37/#52/#66)沉淀的经验教训。**后续任何模块验收、任何对抗式审查,先读本 ADR。**

## 1. 真实 DB 副本端到端审核(必做)

- **教训**:验收收官后对抗式审核,用真实 DB 副本(拷完整库 + 设目标)端到端渲染,发现「看体重目标进度」完成 **377.5% 荒谬值** —— 用户真实环境从未设过目标,start_weight 快照从未写入,兜底「最早体重记录 71kg」(数月前瘦身历史)与当前旅程无关。
- **原则**:演示环境(mock/临时拷贝)**永远构造不出真实历史差**。每模块验收收尾时,必须用**当日真实 DB 完整副本**跑一遍该模块全链路(设数据 → 渲染 → 目检),把「演示环境通过但真实环境荒谬」的盲区补上。
- 方法:`Copy-Item 真实DB 副本` → 副本上设目标/记录 → 渲染 → 核对数值合理性(完成% ∈ [0,~200]、速率带内、日期合理)。

## 2. 演示环境数据新鲜度(必查)

- **教训**:场景 21 验收时页面显示「昨日无饮水记录」—— 真相是演示 DB 是 08-03 13:22 的拷贝,**不含当天记录**,误判为渲染缺陷。渲染前先 `SELECT date, SUM(...) WHERE date = 昨日` 核对演示数据是否覆盖验证目标。
- **原则**:用临时 DB 渲染前,先核对数据新鲜度(LastWriteTime + 关键日期记录);「无数据」先查环境,再查代码。

## 3. 对比图参照系 = 用户心智(不是实现便利)

- **教训**:目标配置页 mini chart 原为「昨日实际 vs 新目标」,用户调低目标时看到 `+XXX` 以为是「新目标增加」—— 实际是「昨日比新目标多」。参照系错位造成系统性误解。
- **原则**:任何「A vs B」对比图,参照系必须是用户心智(改场景 = 改前 vs 改后,diff = 新−旧;定场景才用昨日校准)。符号方向(正/负)与用户直觉一致,否则必被误读。

## 4. 空态设计三要素

- **教训**:场景 25 预测空态只有一句话「先设体重目标」,用户反馈「什么数据都没有」;且 `empty` 字段传了数据但模板不渲染(死数据)。
- **原则**:空态 = ①为什么没有(主提示)②已有的部分(已有数据 KPI)③怎么获得(步骤指引/入口)。数据字段必须被模板消费,传了不渲染 = 死数据缺陷。

## 5. 其他沉淀

- **模板按形态拆分**(形态不兼容即独立;字段由 render 下发)—— 见 ADR-0009。
