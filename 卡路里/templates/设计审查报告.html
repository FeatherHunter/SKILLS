一句话总结

每个文件都在"模仿 Apple",但 35 个文件模仿的是 4 个不同时期的 Apple —— 有的模仿 iOS HIG,有的模仿 Apple.com 官网,有的误把 Material Design 当 Apple,有的模仿 iOS 通知中心。用户在产品内跳转时,视觉会不断"咯噔"。

单点质量合格(每个文件单独看都不难看,甚至 help_center / weight_log_receipt / home_dashboard 做得不错),但系统性失败:这是典型的"AI 逐文件生成、无全局设计系统约束"的产物。

第一性原理:什么是"好看又好用"

好看 = 克制 + 层级 + 一致

克制
每个像素都要为信息传达服务。删掉渐变文字(38px 深灰渐变不可见)、删掉三色 id-card 渐变(色差极小渲染成脏白底)、删掉金银铜奖牌渐变(和健康追踪克制气质冲突)、删掉 pulse 脉冲(低频场景过度强调)。Apple 的美来自"不做的事"。
层级
用户 0.5 秒内要知道:这一页最重要的数字是什么。56px 大数字(hero-number) > 28px KPI 值 > 17px section h2 > 15px 正文 > 13px hint。每一级字号差至少 4px,字重差至少 100。当前问题:多个报告页 11px 表头 + 15px 正文,层级扁平如 Excel。
一致
同一产品内,主色只能有一个值,输入框只能有一种交互,复制按钮只能在一个位置。当前 4-5 套设计 token 并存,这不是"设计系统",是"设计联邦"。

好用 = 可扫读 + 可预期 + 容错

可扫读
数字用 font-feature-settings:"tnum" 等宽对齐(90% 文件已做到 ✓);时间用 SF Mono 等宽体;表格行有轻分隔线 var(--lineS) 而非无分隔(workout_plan_view 的问题)。
可预期
用户在 home 看到复制按钮在底部,到 weight_log 也应该在底部,到 help_center 不应该跑到 summary 层。当前 5 种位置违反预期,增加认知成本。
容错
复制成功要有反馈。当前多数文件只改文字"✓ 已复制",help_center 的 @keyframes copySuccess 弹性动画 + iOS Toast 是最佳实践,应推广到全库。

二、核心发现:设计系分裂(最严重问题)

三、色板对比(主色差异肉眼可辨)

主色(四种蓝)

#007aff A系
#0071e3 B系
#007AFF C系
#0071e3 D系

四种"蓝"中,A 系 #007aff 是 iOS System Blue 官方值,应作为唯一标准。B/C/D 系的 #0071e3 是 Apple.com 官网用色,在 Safari 渲染下与 #007aff 人眼可辨。

二级灰(三种灰)

#3c3c43 A系
#6e6e73 B系
#8E8E93 C系

C 系把 #8E8E93(三级灰)当二级灰用,在 #F2F2F7 背景上对比度仅 2.8:1,不达 WCAG AA 4.5:1 标准,正文可读性受损。

七、"工具感"问题清单(设计不足)

1. food_library.html — phpMyAdmin 即视感

食品库本该是"浏览发现"场景,做成表格 + 分页。th 11px 小字 + background:var(--soft) 像 Excel 表头。th 用 sticky 但无 max-height 支撑,失效。hover 态仅 4% 蓝透明,不可见。

2. 报告类千篇一律

today_meals / calorie_trend / exercise_summary 等结构都是 meta-bar + h1 + sub + kpi-grid + section(table) + footer,无视觉差异化。th 11px 像 Excel 表头不像产品。

3. workout_plan_view.html 表格无边框

th/td 只有 border-bottom:1px solid var(--lineS)(#e8e8ed 几乎不可见),密集数据可读性差。

4. 复制粘贴时改了 padding 没改结构

crud_view / profile_setup / cron_setup 开头模板几乎一字不差,但 food_search padding 32px vs 这三个 48px。同类页面"像但不像"。

八、已经做对的事(优点)

  • 设计语言大方向正确:90% 文件在 Apple 设计语言框架内(系统字体栈、蓝绿橙红四语义色、卡片化、轻阴影、圆角),没走 Material FAB/Drawer,也没走 Ant 密集表格。
  • 数据可视化有节制:SVG 折线/饼图/ring/heatmap/bar 全手写,无 Chart.js/ECharts 重库,体积小可控。today_water 的 ring + 7 天 bar 是全库最克制有效的可视化。
  • 过程型 HTML + 复制 prompt 模式统一:几乎所有向导/配置类都有 .prompt-box + 复制按钮,把 HTML 当"生成 prompt 的可视化编辑器",这是产品层面的正确决策。
  • 移动端适配覆盖率 80%:28/35 文件有 @media 断点。weight_history 有 640px + 400px 双断点。
  • tabular-nums 普遍使用:90% 文件做到数字等宽对齐,数据密集型页面基本素养。
  • 空状态处理:多数文件有 .empty / .log-empty,不是白屏而是图标 + 标题 + 说明。

十一、设计师的私人想法

1. 为什么选 A 系而非 B 系

B 系占 63%,似乎"少数服从多数"该选 B。但设计不是投票。A 系的 #007aff 是 iOS System Blue 官方值(开发者文档明确),--ink2:#3c3c43 比 B 系 #6e6e73 深,正文对比度更好(WCAG AA 更稳),rgba(60,60,67,.12) 边线比 #d2d2d7 实色更柔和(在白卡上有透明度过渡),字体栈含 "SF Pro Display" 更准确(SF Pro 是 Apple 当前屏幕字体)。A 系是"对的",B 系是"多的"。

2. help_center 是个矛盾体

它既是 TOP 1(动效体系最完整、安全区适配最细),又是"全局不统一的元凶"(自成 D 系,font-size:13px + em/% 单位全库仅此一份)。正确做法不是"贬低它",而是提取它的好实践(copySuccess 动画、Toast、safe-area-inset)推广到全库,同时把它的"独立体系"(13px 基准、em/% 单位)拉回 A 系。让局部最优变全局最优。

3. emoji 不是不能用,是不能用在标题里

Apple HIG 的 <h1> 是纯文字。但 emoji 可以用在 .eyebrow(小标签)或 .icon(KPI 图标位)里,作为"语义辅助"而非"装饰"。我的样例里 KPI 仍有 emoji(🔥🏃⚖️📉),但标题是纯文字"今日概况"。这是 Apple 的做法 —— emoji 是 label 的修饰,不是 title 的主角。

4. 渐变不是不能用,是不能"不可见地用"

plan_builder_wizard 的深灰渐变文字、weight_log_receipt 的 radial 光晕,都是"加了但看不见"的 CSS 噪音。如果渐变要存在,它必须可见且有意义 —— 比如 today_water 的 ring 进度色从蓝到绿的过渡,是"达标"的视觉信号。不可见的渐变就该删掉,减少 CSS 体积。

5. "工具感"比"AI 味"更难治

AI 味是"加了不该加的",删掉就好(2 小时)。工具感是"少了该有的",要补结构(2 天)。food_library 从表格改卡片化,要重新设计信息层级;报告类从 11px 表头改 12px + 卡片包裹,要逐个文件调。这是为什么 P2 的"表格去工具感"要 1 天,比 P2"去 AI 味"的 0.5 天多一倍。

6. 一个被忽视的细节:font-feature-settings:"tnum"

90% 文件做到了数字等宽,但 help_center 没有(D 系 13px 基准下数字对齐更敏感)。这是"数据感"的基石 —— 没有它,数字会跳动;有了它,数字像表格一样稳。统一 token 时要把这条写进 _tokens.css 的 body 里,一劳永逸。
