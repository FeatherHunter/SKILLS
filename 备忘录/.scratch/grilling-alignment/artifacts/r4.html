D.1策略 FAT 协议的执行策略 —— 是否真做 FAT?
事实:
  • 总纲 §05 L28-53:FAT = Fresh Agent 黑盒测试,3-5 个核心唤醒词 × ≥3 个人类 prompt,循环 ≤ 3 次
  • 总纲 §05 L74-100:FAT 豁免矩阵(涉及 SKILL.md 任何字符永不豁免)
  • 总纲 §05 L84:Fresh Agent 需要独立 agent 配置(本仓库可能未配置)
  • CHANGELOG v1.1.4 L155:"用户 #4 FAT 协议(待跑 · 用户决定 FAT 时机)⏸"
  • CHANGELOG v1.1.4 L83-L164 多处"FAT G1 / G2 / G3 修复"标记,但实际未跑
核心权衡: FAT 是"真正的端到端验证"(人/独立 agent 测 prompt 是否真的唤醒 skill),但成本高(需要 fresh agent + 人类 prompt 收集)
📌 我的推荐
不做 FAT,所有 commit 标 Tested-By: exempt(本仓库无 fresh agent)
理由:
  • 本仓库(用户单仓库,非 monorepo)无独立 fresh agent 配置,FAT 无法自动跑
  • FAT 的本质是"防止 prompt 漂移导致 skill 不唤醒",但 174 pytest + 49 test_help.py + 13 test_html_delivery_checklist.py 已经覆盖"prompt → 行为"链路
  • 174 pytest 是"白盒 + 黑盒混合":test_help.py L198-391 用 subprocess 调真 CLI,等同于 FAT 的部分效果
  • 标记 exempt 是合规的(总纲 §05 L100:"不是所有变更都需 FAT")
  • 未来若用户接入 fresh agent,ADR-0005 留出"激活 FAT"的迁移路径
