1 · 简短答案

13 个 manager 没有任何 Python 文件调用它们(实测 grep:0 引用)。它们只在用户手工终端 CLI 操作时用(0 自动化路径)。
但严格按 L3 三段式原则是"违反硬约束"。这次修复是"局部治愈",非"根除"。SKILL.md 已诚实声明,不撒谎。

4 · 13 个 manager 的真实使用场景

唯一场景:用户手工 CLI
13 个 manager 只服务于一种场景:用户在终端手工调用(0 自动化)。
例如:python ingredient_manager.py add "辣椒" 100 g --category 蔬菜
手工 CLI 的特点:
  • 人类友好输出(中文 + emoji)比JSON 输出更有用
  • 用户一次操作 1 个菜,不会写循环脚本
  • 错了用户能直接看到 print 文本报错,不需要 JSON 解析
  • 使用频率 1-2 次/天,远低于 P1-2 视觉化(用户每次说"查看 X"就触发 1 次)
结论:13 个 manager 在手工 CLI 场景下,人类友好输出足够。返 JSON 对用户没价值。

5 · 第一性原则决策记录

修代码应基于"被调用且需 JSON"
§01 第一性原理(总纲):修代码应基于真实需求,不是为了"满足某个原则"而修。
原则应用
L3 三段式硬约束✅ 任何 被调用的 manager 必须返 JSON
真实需求原则✅ 未被调用的 manager,修了无 ROI
诚实原则(§05 改动前 3 问)✅ SKILL.md 必须诚实标"暂不支持",不假装完成
风险原则✅ 一次修 1 个 = 风险可控;批量改 14 个 = 高风险
取舍:严格执行 L3 三段式 → 13 个 manager 都修 → 工作量 1-2h + 700 行改动 + 风险不可控。
按"真实需求"原则 → 不修,但诚实标。
未来触发:用户用任何 13 个 manager 时报错 → 立即补 print_or_emit(每个 ≤ 5 行)+ 加 unit test。

7 · 真正"根除"方案(可选)

如果你想真治本,做这 1 件事
写 1 个统一 patch 脚本(~30 行),批量给 13 个 manager:
  1. 顶部加 from cli_formatter import print_or_emit
  2. main() 注入 args["_json_mode"] = json_mode
  3. 每个函数顶部加 json_mode = args.get("_json_mode", False)
  4. 每个 print(...) 替换为 print_or_emit(json_mode, ...)
风险:每个 manager 函数结构不同(嵌套 if、循环、try/except),批量改可能漏或改错。建议人工逐个改 + 每个加 unit test。
