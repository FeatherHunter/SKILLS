💡 架构反思:18 manager 怎么诞生的

2026-07-27 · 不是"AI 写错",是"快速开发的合理 trade-off"

1 · 直接回答你的疑问

不是写错,是 L4 阶段的"按表 1:1"设计 + 计划驱动的全功能集开发。
这暴露了一个AI 开发的常见模式:"计划驱动 + 快速推进"。 当初 L1-L4 阶段 5 天内完成 7 轮重构,目标是"覆盖完整功能",不是"先验证路径再扩展"。

2 · 18 manager 的诞生逻辑(2026-07-22 L4 阶段)

为什么写这么多
L4 阶段原则:"每个业务表 1 个 manager,db 抽象统一"
设计原则应用
每个表 1 个 manager17 张表 → 17 个 manager(还有 1 个是 recipe_manager 主管多表)
db 抽象db.execute/query/transaction 统一入口
CLI 入口稳定每个 manager 有独立的 argparse 入口
可单独使用用户能 python ingredient_manager.py add 单独编辑
这是行业"标准做法"(Django 的 1 model 1 view,Flask 的 1 resource 1 controller)。
但这个项目——私有大厨是"个人手写本级别",不是"生产级 SaaS"。L4 这种工业级抽象对单用户单设备是过度工程。

3 · AI 开发的 3 个常见陷阱

当时如果用这些原则,不会过度设计
  1. YAGNI(You Ain't Gonna Need It)未贯彻 — 13 个 manager 的"批处理/单独管理"场景从未在 P1-2 视觉化路径中需要。该等需求出现时再写,而不是"先全做"
  2. 使用模式分析缺失 — L4 阶段没问"这 17 个 manager 谁会调?调几次?手工还是自动化?" 直接按表结构 1:1 写完
  3. "宁多勿少"倾向 — AI 倾向"写全避免漏",删除难。**该克制**
但这不全是 AI 错——L4 阶段还有"完整功能集"承诺,SKILL.md 第 56 行写"8 大功能"是当时规划。

4 · 现实使用 vs 当初设计

P1-2 视觉化实际只调 4 个
manager设计用途实际使用
recipe_manager菜谱 CRUD✅ recipe_render / cooking_render / shopping_render / render_data 全部依赖
history_manager烹饪历史✅ render_data history/stats
shopping_manager采购清单✅ shopping_render
relation_manager派生关系✅ render_data relations
nutrition_manager营养信息🔧 Phase 7.4 修复后:P0-3 跨 Skill 路由(用户主动调用)
13 个其他 manager子表 CRUD❌ 0 自动化调用(实测 grep 0 引用)
使用率:5/18 = 28%(其中 1 个刚补,4 个是核心)

5 · 我的反思(作为 reviewer)

为什么没在审查时指出
我之前审查时 关注了:
  • ✅ P0-1 HELP 契约(没有)
  • ✅ P0-3 跨 Skill 路由(没声明)
  • ✅ P0-4 FAT 预演
  • ✅ P1-1 变体管理
  • ✅ P1-2 视觉化(50% 子命令不工作)
但我没质疑 "为什么 18 个 manager"。错失机会。
更好的审查应该:
  1. 问"这 18 个 manager 谁在调?"
  2. 问"3 个月后这 13 个会用吗?"
  3. 如果都是"将来可能用" → 警告"过度设计",建议删除未用的

6 · 当前最优解(按"商业态度")

3 个选项,各有取舍
选项说明取舍
A · 保持现状 13 个 manager 继续作为手工 CLI 入口,不修 --json。SKILL.md 诚实声明 推荐 · 0 风险,等用户用到再补
B · 批量补 --json 用 print_or_emit 模式批量改 13 个 manager,各加 unit test 1-2h + 700 行改动,治标(L3 闭环)
C · 架构重构 删 13 个 manager,合并到 1 个"super_manager.py"(动态 dispatch) 不推荐 · 破坏性大,违背"修改不破坏现有 print() UX"原则
我的建议:保持 A。等用户用任何 13 个 manager 报错 → 立即补 5 行(用 nutrition_manager 模式)。触发式修复最经济。

7 · 这次审查的真正教训

不只是私有大厨 — 是 AI 开发的通用问题
"按表 1:1 写 N 个 manager"是工业标准,但不适用于"个人级应用"。
下次新 skill 设计应:
  1. 先写 1 个 super_manager.py(统一 CRUD 入口,按表名 dispatch)
  2. 用户用 1 个脚本管 17 张表,不是 17 个脚本
  3. 复杂度降低 17 倍,bug 减少
  4. 真的需要分离时再拆(例如 recipe_manager 太大)
但这只能下次再做。私有大厨已 commit,改架构破坏性大,不值得现在做。
