4 · 写操作(add)实测

测试 add 是否真写库
✅ 写操作真写库:实测 ingredient_manager.py add 辣椒炒肉 --name "测试食材Z" --quantity 100 --unit g --category 蔬菜 ...
输出 "✅ 食材添加成功!" → DB 行数从 11 增到 12 → 已清理恢复。
🟡 写操作风险点:
  1. 没有 --dry-run 选项——误调 add 直接入库,无回滚(只能手工 SQL DELETE)
  2. add 操作无确认交互——按 SKILL.md "操作规范" 应展示修改前/后让用户确认,但实际 add() 函数直接 INSERT
  3. 错误的参数被静默忽略——比如 add "测试分类"(把"测试分类"当 recipe_id)只返 "未找到食谱",不报警

5 · 子命令命名不一致小 BUG

用户写 "list" 期望得到列表,实际要写 "list-by-recipe"
根因:这些 manager 的 if action == "list": 分支期望参数是"list_items(args)"
但函数内部实现的不是"列 X",是"列某菜的 X"——子命令名 + 函数名不一致
manager用户期望实际子命令
step_ingredient_managerlistlist-by-step / list-by-ingredient
technique_managerlistlist-by-recipe / list-by-step
影响:用户查 SKILL.md 命令,用户期望 list 子命令 = 列某菜的 X——但实际要带 by-recipe / by-step 等冗词

6 · 综合结论

不是假模块 · 真业务跑得通
✅ 13 个 manager 的底层功能都通的:
  • SQL 查询:13/13 跑通
  • db 写入(add):测试 1 个跑通
  • 错误处理:不存在的菜/字段返友好错误,无 Traceback
🟡 但有 UX 问题(非功能性):
  • 子命令命名不直观(step_ingredient list / technique list 都崩)
  • 没有 list-all 能力(无法列"所有 X")
  • tips / techniques 表 0 行(用户从没 add 过)
  • 写操作无 --dry-run,无确认交互
真正风险点:
  1. 用户可能从来没发现这些 bug——因为没人用
  2. 支持文档也没有——SKILL.md 没列这 13 个的子命令说明
  3. 无 tests 覆盖——P1-3 测试只测 5 个核心 manager,这 13 个无回归保护
